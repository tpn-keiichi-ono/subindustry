# 設計

スプレッドシート「シナリオ攻略先リスト」に組み込む Apps Script（コンテナバインド・V8）の設計をまとめます。
運用の手順は [OPERATIONS.md](OPERATIONS.md) を参照してください。

> **シート名について**：シート名は設定で変えられます。このドキュメントでは、差分追跡の対象のシート（今の名前は「スーパー・GMS」「コンビニ」「百貨店」。前の名前は新FMT・新FMT2）を「新FMT」、
> リクエストを登録するシート（今の名前は「サービスリクエスト」）を「リクエスト」、タスクのシート（今の名前は「サービス案タスク管理」）を「タスク管理」と書きます。
> 今の名前と書いてある場所は、OPERATIONS.md の「シート名の一覧」を見てください。

## 全体像

| 仕組み | ファイル | 何をするか |
|---|---|---|
| 差分追跡 | `test.gs` | 追跡シートのセルの変更を、文字単位の差分・編集者・変更時点の行全体つきで記録する |
| クレデンシャル・オファリング履歴 | `CredentialHistory.gs`・`CredentialDialog.html` | 得意先ごとの履歴を登録・編集・削除する。メニュー（`onOpen`）とボタン列の起動もここ |
| 変更履歴 | `Changehistory.gs`・`ChangeHistoryDialog.html` | 行（得意先）ごとの変更をタイムラインで見せる |
| 履歴サイドバー | `HistorySidebar.gs`・`HistorySidebarView.html`・`AuthorizeView.html` | 選んだ行に合わせて、上の2つの要約を表示する。まだ承認していない人には承認の入口を出す |
| アカウントプランシート作成 | `コード.gs`・`Loading.html` | E列に得意先がある行ごとに、テンプレートのファイルをコピーして URL を M列に入れる |
| 列の保護 | `自動入力部分のシート保護.gs` | 名前が「案件_」で始まるシートの決まった列を編集不可にする |
| オポチュニティキャンバス | `OpportunityCanvas.gs`・`OpportunityCanvasDialog.html` | 追跡シートの1行（1件の案件）の値を、キャンバスの枠に並べてモーダルで見せる |
| サンプルデータ | `サンプルデータ.gs` | 画面の確認用に、選んだ行の得意先へサンプルの履歴を追加する・まとめて削除する |
| サービス管理 | `ServiceManagement.gs`・`RequestPickerView.html`・`RequestListDialog.html` | 新FMT のリクエストを選択パネル（サイドバー）で選んで「リクエスト」シートに登録し、リクエストをもとにサービス案を考えて名前でまとめる・棄却する |
| タスク管理 | `TaskManagement.gs` | 別のシート「タスク管理」で、サービス案ごとの検討の進捗をタスクで管理する |
| 会議サマリ | `MeetingSummary.gs` | RX Business MTG（パイプライン会議）の事前資料（16:9 の Google スライドと PDF）を、サブインダストリー（追跡シート）ごとに作ってドライブに保存する（サマリー・パイプラインの変化・前回から変わった案件・期待値の大きい案件の状況・課題、扉、Appendix。書くのは事実だけ） |

ファイル名は Apps Script エディタ側の名前に合わせています（`clasp pull` で同じ名前になるように）。
差分追跡のファイルが `test.gs` という名前なのはそのためです。
ファイルはリポジトリ直下に置きます。フォルダに入れると、同期したときにエディタのファイル名にフォルダ名が付き（`src/HistorySidebarView` など）、
`createTemplateFromFile('HistorySidebarView')` が HTML を見つけられなくなるためです。

### 1つのグローバルスコープ

Apps Script はプロジェクトの全ファイル（リポジトリ直下の `.gs`）を1つのグローバルスコープに読み込みます。

- ファイルをまたいで関数・定数を使えます。たとえば `CredentialHistory.gs` は `DIFF_RULES` や `diffAppend_()` を、
  `Changehistory.gs`・`HistorySidebar.gs` は `cred*` の関数を使います。
- 同じ名前の `const` があると読み込みで失敗し、同じ名前の `function` はどちらか一方しか動きません。
  `onOpen` はプロジェクトに1つだけ（`CredentialHistory.gs`）で、ほかのメニューはそこから呼びます（`svcAddMenu_()`、`CRED_OPTIONS.accountPlanMenu` が true なら `apAddMenu_()`）。
  メニューは追加した順に左から並ぶので、「🟩RXビジネスMTG用」→「🟪RXサービスMTG用」（→「アカウントプランシート作成」）の順に呼びます。
  単純トリガーの `onEdit` は置いていません（ボタン列はインストール型の `onCredentialLauncherEdit` 1つ）。
- 別のファイルの関数を「無くても動く」ように使うときは `typeof 関数名 === 'function'` で確かめてから呼びます
  （例：`recordDiffEdit` の `credIsLauncherEdit_`）。

## シートと保存場所（データモデル）

### 追跡シート（`新FMT`・`新FMT2`）

`DIFF_RULES` に書いたシートです。2行目が見出しで、追跡範囲は `D3:AF` です。見出し行には次が必要です。

| 見出し | 数 | 用途 |
|---|---|---|
| `最終更新日時` | ちょうど1つ | 差分追跡が変更した行に日時を入れる（「（自動入力）」の付いた見出しも可）。追跡範囲から自動で外す |
| `得意先` | ちょうど1つ | 履歴の照合に使う。全角・半角と空白の違いは無視する（`credNormalize_`） |
| `クレデンシャル`（改行）`オファリング登録` | ちょうど1つ | ボタン列（チェックボックス）。**追跡範囲の外** |
| `変更履歴` | ちょうど1つ | ボタン列（チェックボックス）。**追跡範囲の外** |

ボタン列のチェックは差分として残したくないため、追跡範囲に含まれていると `setupCredentialLauncher()` などが止まります。

### `変更履歴_差分`（追記のみ）

1セル1行です。列は次の9列で、`Changehistory.gs`・`HistorySidebar.gs` は B〜I 列を位置で読みます（列の順番を変えないでください）。

`記録日時`・`イベントID`・`編集者メールアドレス`・`シート`・`セル`・`列名`・`種類`・`変更前`・`変更後`

- 文字列はすべてリッチテキストで書きます（`=` で始まっても数式にならない）。空欄は `（空欄）` と書きます。
- 前の版にあった `差分`（文字単位の差分の色付き表示）と `確認済み`（チェックボックス）は、セル数を節約するためにやめました。
  文字単位の差分は、変更履歴の画面（`getChangeHistoryData`）が変更前・変更後からその場で作ります。
  前の版の11列のシートは左の9列が同じなので、そのまま読み書きでき、`compactDiffRecords()` で2列を削除します。
- 古い版の列構成（8・9・10列）が見つかったときは、`diffLogSheet_()` が足りない列を差し込みます。
- シートを作るとき、使わない右の列・下の行を削除し（`diffTrimGrid_`）、記録を足すときは必要な行だけ足します。
  空のセルもスプレッドシートの上限（1,000万セル）に数えられるためです。

### `変更時点スナップショット`（追記のみ）

イベントID × 変更した行ごとに1行です。列は次の8列です。

`記録日時`・`イベントID`・`編集者メールアドレス`・`シート`・`行番号`・`変更セル`・`得意先`・`行の内容`

- `行の内容` は、その行の見出しと値を `[[見出し, 値], …]` の JSON で1つのセルにまとめたものです（見出しの順。空欄の項目とボタン列は持たない）。
  見出しごとに1セルずつ写すと、1回の編集で約40セル使っていたためです。1つのセルの上限を超えるときは、長い値から省略します（`diffSnapshotContent_`）。
- `得意先` は `行の内容` にも入っていますが、サイドバー・変更履歴が得意先で記録を探すため、別の列にも置きます。
- 見出しは、同じ見出しが2つある列は `見出し [列記号]`、見出しの無い列は `D列（見出しなし）` になります。値は表示値（`getDisplayValues`）です。
- 前の版（固定の6列のあとに見出しごとの列が並ぶ）のシートには、`得意先`・`行の内容` の列が無ければ右端に足し、新しい行はこの2列だけに書きます。
  読み手（`Changehistory.gs`）は、`行の内容` が空の行を見出しごとの列から読みます。
  `compactDiffRecords()` が前の版の行を `行の内容` にまとめ（値は変えない）、見出しごとの列を削除します。
  時間内に終わらないときは途中で止め、もう一度実行すると続きから行います（見出しごとの列は、すべての行をまとめてから削除する）。

### `__CHAR_DIFF_<シートID>`（非表示）

比較基準です。追跡シートと同じ位置に、セルの値を「型の1文字＋値」で入れます。
`S`（文字列）・`N`（数値）・`B`（真偽値）・`D`（日時。ミリ秒）・`F`（数式）。空欄は空のままです。
先頭が `=` にならないので、比較基準の中で数式が動くことはありません。
比較基準は追跡範囲の右端の列・追跡シートの行数までにします（`setupDiffTracking()` で使わない列・行を削除する）。
セルごとに比べる仕組みの中心なので、形は変えていません（記録が増えても大きくならない）。

### `クレデンシャル履歴_記録`

1件1行です。列は**見出し名**で見分けるので並べ替えは自由ですが、見出し名は変えないでください。足りない列は右端に追加します。

`ID`・`登録日時`・`得意先`・（入力項目：`予定日`・`実施日`・`種別`・`役職`・`氏名`・`名称`・`フリーコメント`・`担当者名`・`担当部署`）・`紐づくクレデンシャルID`・`登録者`・`登録元（登録時の行）`・`更新者`・`更新日時`・`削除者`・`削除日時`

- 入力項目は `CRED_OPTIONS.fields` で決まり、`label` が見出しになります。
- 文字列は先頭に `'` を付けて書きます（`credText_()`）。数式・日付・数値に変わりません。
- 削除は既定で「削除者・削除日時を入れて非表示」（`deleteMode: 'soft'`）です。
- 以前の版の見出し（`日付`→`実施日`、`備考`→`フリーコメント`）は自動で書き換え、`宛先` 列は読み取りだけに使います。

### プロパティ・キャッシュ

| 場所 | キー | 中身 |
|---|---|---|
| ドキュメント | `CHAR_DIFF_STATE_V1` | 追跡シートごとの状態（比較用シートのID、シート名、`DIFF_RULES` の内容、最終更新日時の列、行数・列数、停止中か） |
| ドキュメント | `CHAR_DIFF_DIRTY_V1_<シートID>` | 取りこぼしの印（回収されると消える） |
| ドキュメント | `CHAR_DIFF_ROWCHECK_V1_<シートID>` | 行の確かめの印（構成の変更でロックが取れなかったとき。回収で行数・ずれだけを確かめると消える） |
| ドキュメント | `CRED_DIALOG_SIZE_V1_<メール>` | その人のブラウザに合わせたモーダルの大きさ |
| ドキュメント | `HS_AUTO_OFF_<メール>` | 前の版でサイドバーの自動表示をオフにした人（今は使わない。`removeHistorySidebarAutoOpen()` などで消す） |
| ユーザー | `CRED_COLUMN_WIDTHS_V1` | その人の列幅 |
| ユーザーキャッシュ | `HS_CUSTCOL_<シートID>` | 得意先列の位置（10分） |

### イベントID

`接頭辞-yyyyMMdd-HHmmss-8桁` です。接頭辞で記録のきっかけが分かります。

| 接頭辞 | きっかけ | 編集者 |
|---|---|---|
| `EVT` | セルの編集（`recordDiffEdit`） | 編集した人（取れなければ `取得不可`） |
| `REC` | 取りこぼしの回収（`catchUpDiffTracking`） | `不明（取りこぼし回収）` |
| `ROW` | 行の追加・削除・ずれの突き合わせ（`diffResyncRows_`） | 行を追加・削除した人／`不明（行の追加・削除）`（編集トリガーから突き合わせたときも、編集した範囲の変更は `EVT`） |
| `CRD` | クレデンシャル履歴の登録・編集・削除 | 操作した人 |
| `SMP` | サンプルデータ（`サンプルデータ.gs`）。過去の日時で記録する | `サンプルデータ` |

## 処理の流れ

### 差分追跡

インストール型トリガーが3つあります（`setupDiffTracking()` が設置）。

1. **編集（`recordDiffEdit`）**：編集された範囲だけを比較基準と比べ、変わったセルごとに差分を記録します。
   順番は「最終更新日時 → 差分ログ → スナップショット → 比較基準の更新」です（スナップショットに最終更新日時が入るように、また記録が書けてから基準を進めるように）。
   その前に、行数の変化と行のずれ（下記）を確かめ、あれば先に行を突き合わせます。
2. **構成の変更（`pauseDiffOnStructureChange`）**：
   - 行数だけが変わったとき：比較基準の行と今の行を突き合わせ（`diffResyncRows_`）、
     消えた行を `行削除`、増えた行を `行追加`、同じ行で変わったセルはセルの変更として記録し、比較基準を取り直します。
   - 行の追加・削除の通知なのに行数が変わっていないとき（削除と追加がトリガーより先に両方起きた）：操作したシート（アクティブなシート）だけ行のずれを確かめ、ずれていれば同じように突き合わせます。
   - 列の追加・削除、シートの削除：そのシートの追跡を止めます（`DIFF_RULES` の列指定がずれるため）。
3. **取りこぼしの回収（`catchUpDiffTracking`、5分ごと）**：印の付いたシートだけを処理します。行数の変化・行のずれがあれば突き合わせ、
   無ければ、データのある最後の行までを比較基準と比べて記録します（「行の確かめ」の印だけなら、全セルは比べません）。

ロックが取れないとき（ほかの実行が書き込み中）は、エラーにせず印を付けて回収に任せます。
編集のときは、そのシートに「取りこぼし」の印を付けます。構成の変更のときは、行数・列数が変わったシートと操作したシートだけに「行の確かめ」の印を付けます（全シートを全セル比較にしない）。
記録の途中でエラーが起きたときは、そのシートの追跡を止めます（編集のときはトーストでも知らせます）。

#### 行の突き合わせと、行のずれ（v6）

- **突き合わせ（`diffResyncRows_`）**：比較基準と今の行を、行の中身で LCS により対応させます（`diffAlignRows_`。前後の一致を除く）。
  対応しなかった行は `diffPairRows_` で組にします。見分け列（`DIFF_ROW_OPTIONS.keyHeaders`：`得意先`・`案件名`）の値が同じ行は、離れていても同じ行とみなし（移動・並べ替え・ずれたあとの編集）、変わったセルだけを記録します。
  残りは、すき間ごとに同じ数なら位置で組にし、数が違えば `行削除`・`行追加` にします。移動しただけの行は何も記録しません。
- **ずれの検知（`diffRowsShifted_`）**：ある行の見分け列の値が、比較基準では別の行にあった値なら「ずれた」とみなします。
  比較基準のどこにも無い値（新しく入力した・書き換えた得意先）は、ふつうの変更として扱います。編集で見分け列そのものを変えた行は手がかりにしません。
  読むのは見分け列をまたぐ1つの範囲（シートと比較基準）を、データのある最後の行までだけです。
- **編集トリガーから突き合わせたとき**：編集した範囲の変更はふつうの編集（`EVT`・編集した人）として記録し、それ以外の未記録の変更は `ROW`・編集者 `不明（行の追加・削除）` で記録します（編集した人の変更にしない）。
- **調べるシート**：編集トリガーは編集したシート、変更トリガーは行数が変わったシートと操作したシート、取りこぼし回収は印の付いたシートだけです。追跡シートが11個あっても、1回の処理で全シートを読むことはありません。
  変更トリガーの通知にはシートの情報が無いため、操作したシートはアクティブなシートで判断します。取れなかったシートのずれは、そのシートの次の編集・取りこぼし回収で気づきます。
- **見分けられない場合**：`得意先`・`案件名` がどちらも同じ行が複数あると、並べ替えのあとに組を取り違えることがあります（同じ得意先の中での取り違えなので、ほかの得意先の履歴には混ざりません）。

### クレデンシャル・オファリング履歴

1. ボタン列をチェックすると `onCredentialLauncherEdit`（インストール型 onEdit。2つのボタン列で共通）が動き、
   見出し行を1回読んでどちらのボタンかを判断し、すぐにモーダルを開いてチェックを戻します。
2. モーダルは開いてから `getCredentialDialogData()` で履歴を読み込みます（ボタンを押してから開くまでを速くするため）。
3. 登録・編集・削除は、画面を先に更新し、サーバーへは1件ずつ順番に送ります。サーバー側では
   - ドキュメントロックを取り（`credWithLock_`）、
   - 行の得意先が開いたときと同じか（`credTarget_`）、
   - 編集・削除なら、開いたときの内容から他の人が変えていないか（`credExisting_`）
   を確かめてから書き込み、`変更履歴_差分` にも `CRD` で記録します。差分ログへの記録に失敗しても本体の保存は取り消さず、警告を返します。
4. 予定と実績：`実施日` が空なら「予定」、入っていれば「実績」です。どちらか一方の日付が必須です。
5. 紐づけ：オファリングは、同じ得意先のクレデンシャルに紐づけられます（1つのクレデンシャルに複数）。
   紐づくオファリングがあるクレデンシャルは種別を変えられません。クレデンシャルを削除すると、オファリングは紐づけなしで残ります。

### 変更履歴

`変更時点スナップショット` から「シート＋得意先」が一致する記録を新しい順に最大300件読み、
同じイベントIDの `変更履歴_差分` から、その行のセルの変更前・変更後を取り出します。
差分ログが見つからない記録は、1つ前のスナップショットとの違い（最終更新日時は除く）で補います。
記録は行の順ではなく `記録日時` の順に並べ替えてから使います（サンプルのように、過去の日時の記録があとから足されることがあるため）。サイドバーも同じです。

行番号は行の追加・削除や並べ替えで変わるため、行番号では探しません。得意先名を変える前の記録は表示されません。
同じイベントに複数の行の記録があるときは、セルの行番号で分けます（`chgRecordOfRow_`。サイドバーも同じ）。削除された行の記録（`N行（削除前の行番号）`）は、残っている行の履歴には出しません。

### 履歴サイドバー

- Apps Script にはサイドバーへ選択の変化を知らせる仕組みが無いため、サイドバーから「今選ばれている行」を問い合わせ続けます
  （操作中は0.25秒、しばらく操作がなければ1.2秒・4秒と間隔を空ける。前の問い合わせが返ってから次を送る）。
  同じ行なら得意先を読まずに返します。
- 履歴は全得意先ぶんを1回でまとめて読み込み（`getSidebarBundle()`）、行が変わるたびには読みません。1分ごとに読み直します。
  変更の記録は、シート・得意先ごとに新しい方から `HS_OPTIONS.eventsPerCustomer`（30回）まで読みます。それより古い記録がある行は
  `changesMore` で知らせ、一覧の最後に「それより前は「変更の詳細」で確認できます」と出します。
- 画面は「表示中の行」のカードと、「クレデンシャル」「変更履歴」の2つのタブです。
  - 得意先名の右の「アカウントプラン」は、`HS_OPTIONS.accountPlan` のシート（既定は `33シナリオ攻略先リスト`、E列が得意先、M列が URL）から
    同じ得意先（`credNormalize_` で照合。同じ得意先が複数あれば上の行）の URL を探し、新しいタブで開くリンクにします。
    セルに URL がそのまま無いときは `HYPERLINK` の数式とセルのリンクも見ます。`http(s)` 以外はリンクにせず、URL が無い得意先では押せない表示（灰色）にします。
  - クレデンシャル：オファリングは紐づくクレデンシャルの下に字下げして並べます。項目を押すと、その履歴を編集する状態でモーダルを開きます。
    予定（実施日が空）の項目は日付の前に「予定」、予定日を過ぎていれば「期限超過」を付けます。
  - 変更履歴：変更を項目（列）ごとに1件として、日ごとにまとめて新しい順に並べます。期間（過去7日・14日・30日・すべて・日付の指定）、
    7日ぶんの帯で選んだ日、項目（複数選択）で絞り込めます。「変更の詳細」は変更履歴のモーダルを開きます（日・項目で絞り込んでいるときは、表示中のいちばん新しい変更の位置で開く）。
- サイドバーは、利用者がメニュー「🟩RXビジネスMTG用」＞「履歴サイドバーを開く」（`openHistorySidebar`）で開きます。
  開いているシートが対象（`DIFF_RULES` のシート）でなければ開かず、対象のシートを `ui.alert` で知らせます（`hsIsTargetSheet_`）。
  「権限を承認する（初回のみ）」も、対象外のシートでは承認だけしてサイドバーは開かず、トーストで知らせます。
  開いたあとに別のシートへ移ったときは、これまでどおりサイドバーの中に「対象外のシート」と出します。
  前の版はスプレッドシートを開いたときにインストール型の起動時トリガー（`autoOpenHistorySidebar`）で自動で開いていましたが、やめました
  （サイドバーは同時に1つしか出せず、サービスリクエストの選択パネルと入れ替わるため、利用者が開くものにした）。
  前の版のトリガーが残っていても、`autoOpenHistorySidebar` はそのトリガーと各自のオフの設定を外すだけで、サイドバーは開きません
  （関数を消すと、残ったトリガーが「関数が見つからない」エラーになるため名前を残している）。管理者は `removeHistorySidebarAutoOpen()` でも外せます。
- サイドバーから呼ぶ関数（`getSidebarSelection`・`getSidebarBundle`）は、開いた本人の権限で動きます。メニューから開くと、まだ承認していない人にはその場で承認の画面が出ます。
  一部の権限を外して承認した人などで呼び出しが失敗したときは、再試行の間隔を延ばし（10秒）、「権限の承認が必要です」と「承認する」ボタンを表示します。
  承認が済めば、開き直さなくても次の問い合わせから表示が始まります（ボタンを押してから5分間は3秒ごとに問い合わせる）。
- 「承認する」ボタンは、Google の承認の画面を新しいタブで開きます（サイドバーの中からは承認の画面を出せないため）。
  行き先は、承認の案内を初めて出すときに `getAuthorizationLink()` で問い合わせます。開いた本人の権限で動くので、
  承認が足りなければ `ScriptApp.getAuthorizationInfo(FULL).getAuthorizationUrl()` が承認の画面の URL を返します（ウェブアプリの用意は要らない）。
  前の版はサイドバーを起動時トリガー（管理者の権限）で開いていたため、この URL が空になり、ウェブアプリが必要でした。今はメニューから開くので、本人の URL が取れます。
  URL が取れないとき（問い合わせ自体が失敗したときなど）は、承認用のウェブアプリ（`doGet`。「ウェブアプリにアクセスしているユーザー」として実行。`HS_OPTIONS.authorizeUrl`。
  `…/exec` の形でなければ使わない）を開き、どちらも無ければメニューでの承認を案内します。
  ウェブアプリは、まだ承認していない人には Google の承認画面を出し、承認が済むと `AuthorizeView` で「権限の承認が完了しました」と出します（一部の権限を外した人には、もう一度承認するリンクを出す）。
  承認は済んでいるのに呼び出しが失敗するとき（`required: false`）は、複数の Google アカウントでのログインを案内します（ボタンは出さない）。
  サービスリクエストの選択パネルも同じ `getAuthorizationLink()` を使います。
- 読み取りだけなのでロックは取りません。

### オポチュニティキャンバス

サイドバーの「キャンバス」（またはエディタから `openOpportunityCanvas()` を実行）で、その行の値をキャンバスの枠に並べて表示します（読み取りだけ）。

- どの列をどの枠に出すかは `OC_OPTIONS.sections` の見出し名で決めます。列の位置ではなく見出しで探すので、列を動かしても使えます（改行・空白、全角・半角の違いは無視）。
  見つからない見出しはモーダルの下に「見つからない列があります」と出します。
- 枠の内容と合う列だけを入れます。新FMT に当てはまる列が無い枠（利用の指標・予算・ビジネス上の課題）は出しません。枠の名前は日本語です。
- 出すのは追跡シートの行に入力されている値だけです（クレデンシャル・オファリングの履歴や体制は含めません）。値を自動で考えて埋めることはせず、空のセルは「未入力」と出します。
- 見出しの上に案件名・得意先・案件ステータス・最終更新日時、右上にアカウントプランへのリンク（行の「アカウントプラン（リンク）」、無ければ 33シナリオ攻略先リスト）。
- 「印刷・PDF」は、決まった幅（1400px）で並べてから A4 横1枚に収まるよう縮めて印刷します（印刷画面で PDF に保存できる）。
- 右上の「− 倍率 ＋」でキャンバスを拡大・縮小できます（50〜200%。倍率を押すと 100%）。「全体を表示」は、キャンバス全体がスクロールせずに見えるいちばん大きい倍率（100% まで）にし、モーダルの大きさが変わったら合わせ直します。
  倍率はキャンバス（`#canvas`）にだけ CSS の `zoom` でかけ、見出しと操作ボタンの大きさは変えません。文字が大きくなるぶん枠の中で折り返すので、横にはスクロールしません。倍率はブラウザ（`localStorage`）に覚え、印刷のときは 100% に戻します。
- 見出し・メニュー・ボタンの名前は日本語だけにします（「オポチュニティキャンバス」。英語の「Opportunity Canvas」は出さない）。

| 番号 | 枠 | 新FMT の列 |
|---|---|---|
| 1 | 課題 | クライアントが置かれている状況・課題・現在の解決策 |
| 1 | 解決策のアイデア | 案件のスコープ・サブインシナリオ |
| 2 | 顧客・ユーザー | サブインダストリー・先方部門・先方担当役職・先方担当氏名・本案件におけるターゲットユーザー |
| 3 | 現在の解決策 | スコープに対する競合他社 |
| 4 | 使われ方・導入効果 | 想定される価値創出のケース／期待される導入効果 |
| 5 | 導入戦略 | 提案を勝ち取るための戦略・差異化要素・活動状況 |
| 6 | ビジネス上の効果・指標（下の段） | 想定売上規模（百万）・期待値調整済 想定売上規模（百万）・受注月・売上開始月 |

### アカウントプランシート作成（`コード.gs`）

`showLoadingDialog()`（エディタから実行。`CRED_OPTIONS.accountPlanMenu` が true ならメニュー「アカウントプランシート作成」→「作成開始」）→ シート名を入力 → 対象件数（E列が入力済みで M列が空）を確認 → 実行、の順です。
メニューは、利用者のメニューを2つ（🟩・🟪）にするため、ふだんは出していません。
1行ずつテンプレートをコピーして M列に URL を入れ、5分たったら中断します（もう一度実行すると、M列が空の行だけを続けて処理します）。

- 1行ごとにドキュメントロックを取り、ロックの中で「行の内容が読み込んだときと同じか」を確かめてからコピーします
  （処理中に行が挿入・削除されても、違う行に URL を入れないように）。ロックが取れなければ、コピーせずに止めます。
- 追跡シートに書き込んだときは取りこぼしの印を付けます。スクリプトの書き込みでは編集トリガーが動かないためで、
  次の回収で `REC`（編集者 `不明（取りこぼし回収）`）として記録されます。

### サービス管理（`ServiceManagement.gs`）

流れは「リクエスト（新FMT の Z列）→ サービス案（リクエストをもとに考え、名前でまとめる）→ タスク（サービス案の検討の進捗）」です。

- サービスは最初から決まっているものではなく、リクエストをもとに考えるものなので、サービスの一覧のシートは持ちません。
  `リクエスト` の `サービス案` の列に付けた名前がサービス案で、同じ名前を付けたリクエストが1つのサービス案にまとまります（多対1）。
- `リクエスト` シート：1行が1件のリクエスト。列は左から次のとおりです。
  - `ID`（SR-0001 の形。スクリプトが振る。下の「ID」）
  - 取り込み元から書く列（選択パネルで選ぶとスクリプトが書く。入力規則なし）：`サブインダストリー`・`得意先`・`案件名`・
    リクエストした営業の `アカウント責任者部署`・`アカウント責任者`・`BX部署`・`BX担当`（取り込み元の列と同じ並び）・`リクエスト`。
    営業の4列は `SVC_OPTIONS.sourceOptionalHeaders` で、見出しが無いシートでは空として読みます（必須なのは `sourceHeaders` の4つだけ）。
  - 人が入れる列：`判断`（プルダウン）・`サービス部門からのフィードバック`・`サービス案`（まとめる先の名前）・
    サービス部門として対応する `主管本部`・`担当者`（判断のほかは自由に入力・入力規則なし。`SVC_OPTIONS.inputKeys`）。
  前からあるシートに足す列は、`insertAfter` の見出しのすぐ右に、`insertBefore` の見出しのすぐ左に差し込みます（`taskEnsureHeader_`。ID は左端、営業の4列は案件名の右、
  フィードバックは判断の右、主管本部はサービス案の右、担当者は主管本部の右）。列がまだ無いシート（`setupRequestSheet()` の前）でも、
  追加・読み取りはある列だけで動きます。
  差し込んだ列は左の列の入力規則を引き継ぐことがあるので、自由に入力する列の入力規則は `svcApplyRules_` で外します。
  使わなくなった列（`removedColumns`：`メモ`・`追加日`・前の版の `取り込み日`）は、`setupRequestSheet()` が確認してから削除します（`taskDeleteColumns_`）。
- シートを足した・名前を変えたあとの設定は `setupAfterSheetChange()`（`test.gs`）でまとめて行います。先に `diffCheckSheets_()` で全シートの見出しを読むだけで確かめ、
  足りなければ何も変えずに知らせます（途中で止まって、差分追跡だけ・ボタン列だけが設定された状態にしないため）。
  ボタン列は使うシートだけに置けばよく、見出しの無いシートは飛ばします（`credColumnByHeader_` の `optional`。`setupCredentialLauncher()`・`setupChangeHistoryLauncher()` も同じ）。
  そのあと `setupDiffTracking()`・`setupCredentialLauncher()`・`setupChangeHistoryLauncher()`・`svcSetupRequestSheet_()` を順に呼びます（どれも何度実行してもよい）。
- シート名を変えた追跡シート：差分追跡の記録（`変更履歴_差分`・`変更時点スナップショット`）はシート名で残り、記録は書き換えないので、
  `DIFF_RULES` の `formerNames` に前の名前を書きます。読み手（`Changehistory.gs`・`HistorySidebar.gs`）は `diffSheetNameResolver_()` で前の名前を今の名前にそろえて見ます。
- 読むシート（`svcSourceSheets_`）：`DIFF_RULES` で `requests: true` を付けたシートです。新FMT の名前と見出しの行を `DIFF_RULES` の1か所に置くため、
  `SVC_OPTIONS` には読むシートを書きません（シート名が2か所にあると、片方だけ直す間違いが起きるため）。
- 選択パネル（`RequestPickerView`。メニュー「🟪RXサービスMTG用」→「リクエストを追加」→ `openRequestPicker()`）：
  - `リクエスト` のシート（`SVC_OPTIONS.requestSheet`）を開いているときだけ開きます。ほかのシートでは開かず、`ui.alert` で開けるシートを知らせます。
  - パネルから呼ぶ関数は、開いた本人の権限で動きます。`openRequestPicker()` は最初に `ScriptApp.requireAllScopes()` を呼び、
    承認が足りない人（初めて使う人・一部の権限を外して承認した人）には、メニューを押したときに承認の画面を出します。
    開いたあとに呼び出しが権限で失敗したとき（承認の取り消し・権限が増える更新など）は、パネルに「承認する」ボタンを出します（履歴のサイドバーと同じ `getAuthorizationLink`）。
  - 開いたとき・再読み込みのとき（`getRequestPickerData()`）に、新FMT をすべて読み直し（`svcSourceRecords_`。得意先・案件名・リクエストの組で1つ。全角・半角と空白の違いは無視）、
    `リクエスト` にまだ無いもの（`svcRegistered_`）だけを返します。新FMT の編集を見張る処理は無く、パネルを開くたびに最新を読むので取りこぼしがありません。
    サブインダストリー・得意先・案件名が空のリクエストも出します（登録はできる。絞り込みでは空の値も選べる）。
  - 絞り込み（サブインダストリー → 得意先 → 案件名。左で選んだものに合う値だけを右のプルダウンに出す）と、文字での検索（空白で区切った語をすべて含むもの）は
    画面の中だけで行います（サーバーを呼ばない）。一度に出すのは200件までで、残りは絞り込んでもらいます。
  - 「追加」（`addServiceRequest(key)`）：ロックの中で新FMT と `リクエスト` を読み直し、まだ無ければ、最後の行の下の A〜D に書きます。
    最後の行は `リクエスト` の列（A〜H）のどれかに値のある行で見ます（判断だけを書いた行にリクエストを書き足さないため。ほかの列は見ない）。
    行が足りなければ足し、足した行にも判断のプルダウンを付けます。判断などは入れません。
    同じリクエストがすでにある（ほかの人が先に追加した）・新FMT から消えたときは書かずに知らせ、どの場合もパネルの新しい内容（`svcPickerData_`）を返します。
  - 前の版は、セルの連動プルダウンで A〜D を選び、候補を非表示の `__REQUEST_LISTS` シートの数式で作り、単純トリガーの `onEdit` で整えていました。
    行の並べ替え・追加でプルダウンだけがずれる、`onEdit` が30秒で止まって候補が一斉にエラーになる、差分追跡とロックを取り合う、
    新FMT の変更が候補に反映されない、といったことが続いたため、パネルで選ぶ形に変えました（`onEdit` は置いていない）。
    前の版の A〜D の入力規則と `__REQUEST_LISTS` は、選択パネルを開いたとき・「追加」のとき・`setupRequestSheet()` のときに外します（`svcRemoveLegacyLists_`）。
    外したら（または無かったら）印を付け（`SVC_OPTIONS.legacyDoneKey`）、それからはパネルを開いたとき・追加のときには確かめません（入力規則・メモを読むのは時間がかかるため。`setupRequestSheet()` では毎回確かめる）。
    候補に無い値を拒否する入力規則が残っていると、スクリプトの書き込み（`setValue`）もその規則のヘルプの文で止まるためです。A〜D には入力規則を付けないので、残っていれば列ごと外します。
- 一覧のモーダル（`RequestListDialog`）：パネルの件数のバッジ（未登録・登録済み）を押すと `openRequestListDialog(kind)` で開きます（押したバッジのタブで開く）。
  `getRequestListData()` が新FMT と `リクエスト` を読んで、未登録（シート・A〜D）と登録済み（行番号・A〜D・判断・サービス案・担当者・取り込み元のシート）を返します。
  読むだけなのでロックは取りません。登録済みで新FMT に見つからないものには「取り込み元に無し」の印を付けます（シートのメモの代わり）。
  モーダルからも追加・削除できます。追加（`addServiceRequestFromList(key)`）はパネルの追加と同じ処理（`svcAddRequest_`）で、一覧の新しい内容を返します。
  削除（`deleteServiceRequest(row, key)`）は、ロックの中で `リクエスト` を読み直し、一覧を読んだときの行が同じキーならその行を、
  並べ替え・行の追加などで行がずれていれば同じキーの行を探して削除します（同じキーの行が複数あって1つに決まらない・見つからないときは削除しない）。
  判断・サービス案などの入力も行ごと消えるので、モーダルで「削除する」「やめる」を出して確かめます（入力のある行には「判断などの入力も消えます」と出す）。
  削除したリクエストは未登録に戻ります。パネルは、モーダルを閉じて戻ってきたとき（ポインタが入る・フォーカスが戻る）に裏で読み直します。
- ID（`svcEnsureIds_`・`svcTakeIds_`）：登録したリクエストに `SR-` と4桁の番号を振ります（`SVC_OPTIONS.idPrefix`・`idDigits`）。
  - 振る番号は、シートの ID の列にある最大の番号と、これまでに振った最大の番号（ドキュメントのプロパティ `idCounterKey`）の大きいほうの次です。
    手で書いた ID（全角や番号だけの `12` も番号として読む）とも、削除した行の ID とも重なりません（番号は使い回さない）。
  - 番号を決めて書くところまでをロック（`taskWithLock_`）の中で行うので、同時に追加しても重なりません。
  - 追加したとき・パネルを開いたとき・`setupRequestSheet()` のときに、リクエストのある行のうち ID の無い行と、
    上の行と同じ ID・読めない ID の行（行のコピーなど）に新しい番号を振ります（上の行の ID は残す）。振り直したときは知らせます。
  - モーダルの削除は ID で行を決めます（同じ ID で同じリクエストの行が1つなら、その行。無ければ行番号とキーで探す）。
- 新FMT に合わせる（`svcSync_`。パネルを開いたとき・`setupRequestSheet()` のとき。ロックの中）：登録した行だけを合わせます（行は足さない）。
  取り込み元から書く列のうち、リクエストを見分ける列（得意先・案件名・リクエスト）のほか（サブインダストリー・営業の4列）を、
  新FMT の同じリクエストの値にそろえます（変わった行の範囲だけを列ごとに1回で書く。全角・半角と空白だけの違いなら変えない）。
  新FMT が正なので、`リクエスト` でこれらの列を手で直しても、パネルを開くと新FMT の値に戻ります。
  新FMT に無い行（リクエスト・得意先・案件名が書き換わった・消えた）は消さず、メモも付けません
  （セルのメモは人が書くものとし、スクリプトは付けない。行番号は `diagnoseRequestSources()` で確かめる）。
  前の版で `リクエスト` のセルに付けたメモ（`legacyNotes` で始まるもの）は外します（利用者が書いたメモは変えない）。
  書き換わったリクエストは、新しいリクエストとしてパネルに出ます。パネルを開いたときにロックが取れなければ（5秒）、合わせずに一覧だけを出します。
- 文字列は先頭に `'` を付けて書きます（`credText_`）。書き込みはロックの中で行います（`taskWithLock_`）。
  このロックはドキュメントロックではなくスクリプトロックです。サービス管理・タスク管理はサービスリクエスト・タスク管理のシート（差分追跡の対象外）
  だけに書き、取り込み元は読むだけなので、差分追跡・クレデンシャル履歴などと同じシートに同時に書くことはありません。
  ドキュメントロックを使っていたときは、取り込み元の編集のたびに動く差分追跡（ロックを60秒まで待つ）や取りこぼしの回収の後ろに並ばされ、
  選択パネルの「追加」が20秒待ちきれずに「他の処理が実行中です」で止まることがありました。サービス管理・タスク管理の処理どうしは、このロックで1つずつ動きます。
  ロックを取っている間は、スクリプトのキャッシュに処理の名前・実行した人・時刻を残し（`TASK_OPTIONS.lockHolderKey`）、待ちきれなかった人のエラーに出します。
  パネルとモーダルは「他の処理が実行中です」のとき、1.5秒おいて2回まで自動でやり直します。`diagnoseServiceLock()` で、ロックの種類と今の使われ方を確かめられます。
- 前の版の見出し（`サービス`）は、見出しの用意（`taskEnsureHeader_` の `aliases`）で `サービス案` に書き換えます。
  前の版で全件を自動で取り込んだ行は「登録した行」として残るので、`removeUntouchedRequests()` で手を付けていない行（判断が未判断か空で、フィードバック・サービス案・主管本部・担当者が空）を
  確認してから削除できます（続いている行はまとめて `deleteRows`。データの行をすべて消すときは、先に空の行を1つ足す）。削除したリクエストはまたパネルに出ます。
- `diagnoseRequestSources()`（読むだけ）：シートごとに、リクエストのある行の数と、パネルに出ないもの（登録済み・ほかの行やシートと同じリクエスト）の数を出します。
  読むシートをすべて読めたときは、`リクエスト` で新FMT に見つからない行の行番号も出します。

### タスク管理（`TaskManagement.gs`）

シート `タスク管理` の1行が1件のタスクで、サービス案ごとの検討の進捗を管理します。
列は `サービス案`・`タスク`・`本部`・`担当者`・`期限`・`状況`・`メモ` で、今は手で行を追加します（自動で行を作る処理は無い）。
`本部` は担当者とセットで入れる本部名です（前からあるシートには、`タスク` のすぐ右＝担当者の左に差し込む）。

- タスクは、`リクエスト` に登録したリクエストを ID とリクエストで選んで対応付けます（`サービス案` の列。「SR-0001 会員の購買分析をしたい」の形）。
  ID とリクエストは1対1なので、タスクは1件のリクエスト（とそのサービス案）に付きます。案件には対応付けません（案件はリクエストからたどれる）。
  前の版はサービス案の名前を選んでいました（ID で選ぶので、サービス案の名前を変えてもタスク管理は直さなくてよい）。
- 候補は、スクリプトが非表示のシート `__TASK_CHOICES`（`SVC_OPTIONS.taskChoiceSheet`）の A 列に、ID の順に書きます（`svcTaskChoices_`・`svcWriteTaskChoices_`）。
  リクエストは改行・続いた空白を1つの空白にし、`taskChoiceLength`（40文字）より長いものは「…」で切ります。行は候補の数だけにし、使わない列・行は持たせません。
  `サービス案` の入力規則は、この候補の範囲を参照し、候補に無い値は入力できないようにします（`svcServiceRule_`）。
  一覧から作るプルダウン（`requireValueInList`）は項目の数に上限がある（500件）ので、範囲の参照にしています。数式で候補を作らないのは、テストで確かめられず、ID で合わせ直す処理もスクリプトに要るためです。
- 候補は、選択パネルを開いたとき・追加・削除のとき・`setupRequestSheet()`・`setupTaskSheet()` のとき（すべてロックの中）に合わせます（`svcLinkTaskServiceColumn_`）。
  合わせられなかったとき（保護で書けない・前の版の関数が残っているなど）は黙らずに、パネルの読み込み（`getRequestPickerData()` の `warning`）・追加・削除の結果（`warning`）で知らせ、
  パネル・モーダルに赤で出します（追加・削除そのものは済ませる。ほかの処理が実行中でロックを取れないときは知らせない）。
  原因は `diagnoseTaskChoices()`（読むだけ）で、コードの版（関数の中身に今の版の処理があるか。同じ名前の関数が別のファイルに残っていると前の版が動く）・
  候補のシートと今のリクエストの違い・プルダウンの参照先・最後に合わせた時刻・シートの保護を確かめられます。
  - 候補が変わったら書き直し、候補の行数・タスク管理の列や行数が変わったら、`サービス案` の全行の入力規則を付け直します（参照する範囲は付けたときの範囲で決まるため）。
  - 入力済みのタスクのうち候補に無い値は、同じ ID の候補（リクエストを書き換えたなど）に、前の版の値（サービス案の名前）はそのサービス案のリクエストが1件だけならそのリクエストに書き換えます（`svcRelinkTaskValues_`）。
    決まらないもの（同じ名前のリクエストが複数ある・リクエストを削除した）は残し、件数を知らせます（セルの右上が赤くなるので、選び直してもらう）。
    書き換えるセルだけに書きます（候補に無い値のままのセルに書くと、入力規則で止まるため）。
  - 毎回すべてを確かめると読み込みが遅くなった（行ごとの問い合わせで1,000行で数十秒）ため、確かめた記録（候補の要約・候補のシート・列・行数・時刻。`SVC_OPTIONS.taskLinkKey`）を残し、
    どれも変わらなければ `taskLinkCheckMinutes`（30分）に1回だけ確かめます。確かめるときも入力規則は1回で読み、全行の種類と、先頭・真ん中・最後の行の参照するシートだけを見ます。
  - 候補のシートを作るとき、`insertSheet` は作ったシートを開くので、開いていたシートに戻します。
- タスク管理シートの編集で動く処理はありません（単純トリガーの `onEdit` は置いていない）。
- `setupTaskSheet()` はシートが無ければ作り、見出しが空なら書きます。見出しがあるシートは書き換えず、足りない列だけを右端に足します（`taskEnsureHeader_`。リクエスト シートでも同じ）。
  全行（最後の行まで）に、サービス案・期限（日付）・状況（一覧）の入力規則を付けます。
- 前の版（案件の連動プルダウン `サブインダストリー`・`得意先`・`案件名` の列がある）のシートは、`ui.alert` で確認してからその列を削除し（`taskDeleteColumns_`）、
  `サービス案` の列を左端に動かします（`moveColumns`）。ほかの列の値は残ります。確認はロックを取る前に行います（答えるまでほかの処理を待たせないため）。

### 会議サマリ（`MeetingSummary.gs`）

RX Business MTG（パイプライン会議）の **事前資料**（16:9 の Google スライドと PDF）を、サブインダストリー（追跡シート）ごとに作ります。

- 会議の形：月1回（第一週の金曜 9:00〜10:30）。サブインダストリーごとに報告4分＋フィードバック3分。目的は、案件の進捗・受注見込みを確かめ、
  優先順位と次のアクションを決めること。資料は会議の前に配り、参加者（営業の統括・リーダー、BX、サブインダストリーのリーダー）が通読してから会議に臨みます。
- **資料には、シートと変更の記録から分かる事実だけを書きます。** 論点・決めてほしいこと・支援の要否・深掘りする案件などの判断は、各サブインダストリーのリーダーが
  会議で話すことです。資料が判断を先に書くと、読み手を誤った方向に導くおそれがあるため入れません（前の版にあった「本日の論点」「決めてほしいこと」「決めること」・
  結論の帯・★・赤枠の強調はやめました）。
- 見出し（タイトル）はどのシートでも同じ（`MTG_TITLES`）にし、同じ位置に同じ情報が来るようにします。シートごとの状態は、見出しの下のリード文に事実として書きます。
- 使う言葉の意味は下の「数え方」で決め、資料の中ではその意味でだけ使います（資料に用語の定義・ステータスの分類のページは置かない。2026/10 に不要とした）。
  判断や評価を含む言葉（「悪い動き」「重点」「要対応」「打開」など）は使いません。
- 「動いた・止まった・入力に漏れのある案件」のふるい分けに絞り、個別の案件を深く見るのはオポチュニティキャンバスなど別の画面で行います。
  文はすべてシートと変更の記録から作ります（記入欄は置かない。推進リーダーは残した Google スライドに書き足せる）。

- 管理者がエディタで `createMeetingSummaries()`（試すときは `previewMeetingSummaries()`）を実行し、`ui.prompt` で作るシート（空欄ならすべて）と今回の会議日（`10/23`・`2026/10/23`）を入力します。
  会議の前に作る人が決まっていて、利用者向けのメニューは2項目に絞っているため、メニューには置きません。
- 「前回から」の基準は **前回の会議**：シートごとに、会議日と資料を作った日時をドキュメントのプロパティ `MTG_MEETINGS_<シート名>`（`[{date, cutoff}]`）に残し、
  今回の会議日より前でいちばん新しい会議の `cutoff` より後の変化を出します（`cutoff` ちょうどの記録は前回の資料に入っているので数えない）。
  同じ会議日で作り直したら `cutoff` を上書きします（基準は変わらない）。記録が無ければ、前の版の `MTG_LAST_<シート名>`、それも無ければ `MTG_OPTIONS.firstDays`（14日）前から。
  `previewMeetingSummaries()` は会議日を記録しないので、試作を何度作っても本番の「前回から」は変わりません（ファイル名に「試作」）。
- **基準**：旧フォーマットからの移行など、案件をまとめて貼り付けたあとに `setMeetingBaseline()` で今を基準として記録します（同じ `MTG_MEETINGS_<シート名>` に
  `{date, cutoff, baseline: true}`。シートごとに1つで、記録し直すと置き換える）。前回の会議より後の基準（会議日が今回の会議日まで）があれば、「前回から」は基準の `cutoff` から
  （貼り付けた行の「行追加」・空の行への入力を「新規」に数えないため）。会議の資料を作っても基準は消しませんが、そのあとの会議は前回の会議のほうが新しいので会議から数えます。
  停滞は、ステータスが最後に変わった記録（案件ができた記録も）が基準より前なら「N日以上」にします（貼り付けた時が「案件ができた」記録になり、本当の日数は分からないため）。
- 試作のときは、その会議日の最初の試作の入力内容のチェックの結果（種類＋案件のキーのハッシュ）を `MTG_DRAFT_<シート名>` に覚え、
  同じ会議日の資料（Appendix ③）に「試作の時点から N件が解消、新たに N件」を出します（試作を各リーダーに見せて、会議の前に入力を直してもらう運用）。

#### 数え方（どのページでも同じ）

- **ステータスの分類**：進行中・受注・失注・保留。`MTG_OPTIONS.statusKinds` に書いたステータスはそのとおりに、ほかはことばで決めます（失注 `lostWords` → 保留 `holdWords` → 受注 `wonWords`。
  「受注見込み」などは `notWonWords` で進行中。空も進行中）。期待値は進行中だけを数えます。プルダウンの選択肢に無い値は、入力内容のチェックの「選択肢外のステータス」に出します。
- **前回の時点の値**：案件ごとに、前回以降で最初の変更の「変更前」（その項目の変更が無ければ今の値）。変更の記録は `変更時点スナップショット`（イベントID＋行番号）の得意先＋案件名で案件に結び付けます。
  得意先・案件名を書き換えた記録・空の行に入れた記録は、前の名前（キー）を今の名前につなげます（あとから案件名を入れた案件・名前を直した案件も1つの案件になる）。
  空の行に得意先か案件名を入れた記録・`行追加` は「案件ができた」記録です。スナップショットの無い記録は数えず、件数を Appendix ① に書きます。サンプル（`SMP-`）・クレデンシャルの記録（`CRD-`）は数えません。
- **前回からの変化の区分**：案件ごとに1つ（`MTG_CATEGORIES` の順で最初に当たるもの）。新規 > 受注 > 失注 > 保留 > 復帰（受注・失注・保留 → 進行中）> 前進 > 後退（進行中どうしで、
  プルダウンの並び順で比べる）> 延期 > 前倒し（受注月）> 増額 > 減額（期待値）> 変更（プルダウンに無い値どうし）> 活動の更新（活動状況の前回の値と今の値が違う）> 更新のみ。
  行を削除した案件は「削除」で、失注には数えません
  （`行削除` の「変更前」を、シートの見出しで区切って読む。見出し・値に改行があるため）。前回より後に足して消した行は出しません（区分の決め方は資料には書かない）。
- **期待値の増減**：前回の時点で進行中だった案件の期待値（前回の値）から今の進行中の期待値までを、案件ごとに 新規・増額・復帰・減額・受注・失注・保留・削除 に分けます。
  進行中から外れた案件は前回の期待値の分だけ減らすので、「前回 + 内訳の合計 = 今回」が必ず成り立ちます。期待値が空の案件は0として数え、件数をリード文に書きます。
- **停滞**：進行中で、ステータスが最後に変わってから（または案件ができてから）`stallDays`（45日）以上同じ。変わった記録が無ければ、記録を読んだ期間の始まり
  （`変更履歴_差分` の最初の行と `lookbackDays`（180日）前の新しいほう）と最終更新日時の古いほうから「N日以上」。行の更新ではなくステータスで見るのは、活動状況だけ書き足してステータスが同じ案件も拾うためです。
- **受注月超過**：進行中で、受注月が今月より前。**延期n回**：記録を読んだ期間の中で受注月が後ろの月に変わった回数。
- **期待値の大きい案件**：進行中の案件を期待値の大きい順に `mainRows.focus`（5件）。当てはまる状況（停滞・受注月超過・延期n回）を事実として並べます（判断の言葉は付けない）。
- **入力内容のチェック**：予定日超過（このシートに進行中の案件がある得意先の、予定日を過ぎて `overdueDays`（90日）以内で実施日が空のクレデンシャル・オファリング。責任者は当社の担当者）・
  受注月超過（延期の回数つき）・未入力（`required`）・資料なし（進行中で `columns.record`（商談記録（ＵＲＬ））が空。提案資料・商談の音声の格納先）・更新なし（最終更新日時が `noUpdateDays`（30日）以上前）・金額の不整合（期待値 > 想定売上）・月の不整合（売上開始月 < 受注月）・
  選択肢外のステータス・デリバリー担当なし（前回から受注で デリバリー担当 が空）。シートに無い列の種類は出しません。
  会議の前に入力を直してもらうためのもので、Appendix に置きます。種類の説明は置かず、案件ごとの一覧の「内容」に、何が当てはまったかを書きます。
- **今期に受注予定の期待値**：受注月が今期（`fiscalStartMonth`（4月）から12か月）の進行中の案件の期待値（受注月別の表の 1Q〜4Q の合計）。
  前の版にあった今期の帯（今期の受注・着地見込み・目標の達成率）は、前回からの変化を見る資料には要らないため置きません。
- 記録は追記なので、下から `logChunkRows` 行ずつ、読む期間（前回と `lookbackDays` 日前の古いほう）より前に届いたら止めます。サンプルの記録は過去の日時で足されるので、止める判断には使いません。

#### スライドの構成

見出しは固定（`MTG_TITLES`）、リード文は状態を事実として書きます（1つ目の文は黒で1行、改行のあとの補足はグレーで小さく）。

表紙：いただいた表紙のひな形（Google スライド。`setMeetingTemplate()` で登録）の1枚目をそのまま使い、決まった文字を置き換えます
（`XXXXXX` → サブインダストリー、`XXXXX` → 会議の名前と「事前資料」（試作は【試作】）、`2026年 4月 17日` → 会議日（曜日つき）、`XXXX` → 空）。
その下に、データの時点・期間を白い小さな字で足します。
出典の行・ページ番号は置きません（ページ番号は表紙を1枚目として数えるので、PDF のページと同じ番号になる）。

本編（1枚あたり1分で読める量）：

1. サマリー：リード文は「期待値は N百万円（前回比 ±N）、進行中 N件。前回から受注・失注・前進・後退・新規の件数」の1行。
   4つの数字（進行中の期待値・受注／失注・前進／後退・停滞。箱には数字だけを置く。前回比・件数はリード文、想定売上は内訳の表にあるため）、
   前回からの状況の内訳（区分は どのシートでも同じ：新規・前進／受注／失注・後退・削除／受注月の延期・超過／停滞。区分ごとの件数・想定売上・案件の名前
   （想定売上の大きい順に `mainRows.deals` 件まで。3行（表が入りきらなければ2行）に入る件数まで並べ、残りは「ほか N件」））。
2. パイプラインの変化：期待値の増減の滝の図（前回 → 内訳 → 今回。凡例つき。縦軸は0から）、ステータス別・受注月（今期の四半期）別の件数と期待値の表。
   リード文は 前回 → 今回・増えた分と減った分・内訳で最も大きいもの・今期に受注予定の期待値と最も多い四半期。
3. 前回から変わった案件：ステータス・期待値・受注月・活動状況が変わった案件を、区分の順（`MTG_MOVE_ORDER`。活動の更新は最後）に上位 `mainRows.changes`（7件）。
   「前 ▶ 今」と今の活動状況（会議で「この期間に活動のあった案件と活動の内容」を見るため）。区分はセルに重ねたラベル。
   リード文は件数だけ（区分ごとの件数はサマリーにある）。入りきらなければ、補足に区分の順と「全件は Appendix ①」。
4. 期待値の大きい案件の状況・課題：進行中の案件を期待値の大きい順に5件。期待値／想定売上・ステータスと同じ日数・受注月・活動状況・活動における課題・
   当てはまる状況（停滞・受注月超過・延期n回。ラベル）。リード文は件数と、進行中の期待値に占める割合だけ（当てはまる状況の数はラベルで分かる）。

扉（表紙のひな形の複製。見出しを「Appendix」にし、ほかの決まった文字は空。その下に Appendix ごとに1行で、見出し（「（一覧）」などは付けない）と始まりのページ。
作った Appendix だけを出す。出典の行・ページ番号は置かない）のあとに、

#### スライドの作り方

- スライドは Slides API（拡張サービス「Google Slides API」。`appsscript.json` の `enabledAdvancedServices`）で作ります。
  表紙・扉のひな形が登録してあれば（`mtgTemplateId_()`）、ひな形を保存先のフォルダにコピー（`makeCopy`）して、その中に作ります。
  ひな形の2枚目以降は消し、1枚目を複製（`duplicateObject`）して扉にし、1枚目・扉の決まった文字（`MTG_OPTIONS.templateTexts`）を `replaceAllText` で置き換えます
  （長いものから。`XXXXXX` を `XXXXX` より先に）。ほかのスライドは白紙のスライド（`BLANK`）を表紙の次から順に足すので、扉は本編のあとになります。
  ひな形が無ければ、`Slides.Presentations.create`（`pageSize` 720 × 405pt）で新しく作って保存先のフォルダに移し、表紙・扉は緑の地に白い字で描きます（`mtgTemplateFallback_`）。
  何枚かずつ（`batchRequests` 件まで）`batchUpdate`（白紙のスライド・テキストの箱・図形・表）で書きます（Slides API は1分あたりの書き込みの回数に上限があるため、まとめて送る）。
  最後に、足したスライドに付いたレイアウトの枠（ひな形の白紙のレイアウトにあるページ番号・日付・フッター）を消します（`mtgPlaceholderRequests_`。ページ番号が2つ出ないように）。
  表の列は 32pt 以上にします（それより狭いとエラーになる）。
  `getAs('application/pdf')` で PDF にして同じフォルダに保存します。`MTG_OPTIONS.keepSlides` が `false` なら Google スライドはゴミ箱に移します。
  失敗したときは作りかけのスライドをゴミ箱に移し、会議日も記録しません。拡張サービスが無いときは、追加のしかたを案内して止めます。
  - スプレッドシートを PDF に書き出す方法（前の版）は A4 で、16:9 にできないためやめました（`UrlFetchApp` も使わなくなった）。
  - Slides の権限（プレゼンテーション）が要ります。メニューは `requireAllScopes()` ですべての権限を確かめるので、入れたあとは利用者も1回承認し直します。
- スライドの形（`MTG_SLIDE`。pt）：左右の余白 30（中身の幅 660）、タイトル（`titleY` 18・21pt）、リード文（`leadY` 46。1つ目の文 10.5pt、補足 9pt）、
  中身（`top` 98〜`bottom` 373。サマリーは `summaryTop` 72 から）、区切り線（`ruleY` 377）、出典の行とページ番号（`footY` 380）。
  サマリーの数字のタイル・表、滝の図の高さも中身の上端・下端から決めます。表紙と扉はタイトル・リード文・出典の行・ページ番号を置かず、ひな形の決まった文字の置き換え（`template`）と一覧。
  部品は「箱」（`type: 'box'`）・「表」（`type: 'table'`）の2つで、`mtgSlides_` が部品の並びを作り、
  `mtgSlideRequests_` が Slides API のリクエストにします（テスト・見た目の確認は部品の並びで行う。部品の `role` は役割の目印で、スライドには使わない）。
  - 箱の `spans`（`[{start, end, bold, color, size}]`）で一部の文字の書式を変えます（得意先だけ太字、期待値だけ大きく緑、日数だけグレーなど）。
    表のセルは `parts`（改行で分けた部分ごとの書式）で書き、`mtgRow_` が折り返したあとの位置の `spans` にします。
  - 区分・当てはまる状況のラベル（角の丸い四角）は、表のセルの上に重ねた箱です（`mtgPills_`。セルの文字は空）。行の高さは見積もりどおりになる
    （見積もりは多めで、Google スライドは `minRowHeight` より低くしない）ので、位置は列の幅・行の高さから決めます。
  - 部品は 720 × 405pt のスライドを基準に作り、資料のページの大きさに合わせて位置・大きさ・文字を拡大します（`mtgSlideRequests_` の `scale`。
    ひな形が 960 × 540pt なら 4/3 倍）。字は箱ごとに `font` で変えられます。
  - 前の版では表紙を部品で描いていました（グラデーションを、回した細い長方形を並べて塗る）が、Google スライドでは帯の間に白いすき間が出てデザインが崩れたため、
    ひな形をそのまま使うようにしました。
  - パイプラインの変化の右の表は、行を低くして多く入れるため、Slides API の表ではなく箱で描きます（`mtgMiniTable_`。表はセルの余白で行が高くなる）。
  - 文字は `mtgWrap_` で、見積もりの幅（`mtgCharWidth_`：全角は文字の大きさ、半角の英大文字は 0.75 倍、ほかの半角は 0.6 倍。BIZ UDPゴシックで測った幅より少し大きめ。
    箱の左右の余白 14.4pt を引き、さらに 8% の余裕）で先に行に分け、行数を超えたら「…」で切ります。行の高さは文字の大きさの 1.5 倍で見積もります（BIZ UDPゴシックは約 1.1 倍）。
    行の頭に来ない文字（、。）」など）は本当の幅に収まればぶら下げ、半角の語（「2026/12」など）は途中で切りません。表の行の高さは、いちばん行数の多いセルに合わせます（`mtgLineHeight_`）。
  - 表の空のセルにも空白を1つ入れて書式を付けます（空のままだと既定の大きな文字の高さで行が伸びる）。セルの間は薄いグレーの線（0.75pt）。
  - タイトルは1行に収まるように 21 → 19 → 17pt と小さくし、それでも入らなければ「…」で切ります。
    リード文の1つ目の文は 10.5 → 10 → 9.5pt で1行に収め、入らなければ2行（補足は1行まで）にします。

## 判断の理由

- **比較の基準は「最後に取り込んだ値」**：承認済みの値ではありません。取り込みの間にあった途中の状態は残らないため、完全な監査証跡ではありません。数式は計算結果ではなく式で比べます。
- **シートの文字列は数式にならない方法で書く**：利用者の入力が `=` で始まると、そのまま `setValue` すれば数式として動きます。差分ログはリッチテキスト、記録シートは先頭の `'` で防ぎます。
- **ロックが取れない編集をエラーにしない**：同時に何人も編集すると、編集トリガーが重なってロック待ちになります。止めるより印を付けて回収するほうが、追跡を続けられます。
- **行の追加・削除では止めない、列の変化では止める**：行の増減は突き合わせで追えますが、列が動くと `DIFF_RULES` の列指定そのものがずれるため、人が確認してから取り直します。
- **行のずれは見分け列で確かめる**：並べ替え・ドラッグでの移動、トリガーより先に削除と追加が続いた場合は、シートの大きさが変わらないので行数では気づけません。そのまま比べると別の行の値が「変更前」になり、取りこぼし回収ではずれた行がすべて「変わった」と記録されてしまうため、得意先・案件名の位置で確かめます。全列を比べないのは、毎回の編集で読む量を小さくするためです。
- **追跡シートが多くても、関係するシートだけを読む**：トリガーは3つのままで全シートをまかなうため、1回の処理では、編集したシート・行数が変わったシート・操作したシート・印の付いたシートだけを読みます。印は全シートぶんを `getProperties()` 1回で読みます。
- **編集者は `e.user` から取る**：インストール型トリガーはトリガーの所有者の権限で動くので、`Session.getEffectiveUser()` は所有者を返してしまいます。
- **トリガーの所有者は1人（管理者）**：同じトリガーを複数人が設置すると二重に記録されます。設置する関数は「1つだけ存在する」ことを保証します。
- **メニューは「履歴サイドバーを開く」「権限を承認する（初回のみ）」だけ**：承認の画面は、本人がメニューなどから関数を実行したときにしか出せません（サイドバー・ボタンからは出せない）。
  そのため、利用者向けの入口として、サイドバーを開く項目と承認の項目をメニュー「🟩RXビジネスMTG用」に置きます（どちらも、まだ承認していない人には承認の画面が出る）。
  「権限を承認する」は `ScriptApp.requireAllScopes()` で、承認の画面で一部の権限を外した人にも承認し直してもらい、サイドバーを開き直します。
  管理者の作業（ボタン列の設定・サンプル履歴など）や選んだ行のモーダルを開く処理は、エディタから関数を実行します。
  メニューの名前は `CRED_OPTIONS.menuTitle`（🟩RXビジネスMTG用）・`SVC_OPTIONS.menuTitle`（🟪RXサービスMTG用）の1か所にだけ書きます。
  サイドバー・承認のページの案内に出す名前は、テンプレートの値（`menuTitle`）で渡します（HTML に名前を書かない）。
  管理者がエディタから実行する処理の確認・結果の画面（`ui.alert`・トースト）のタイトルも、機能ごとにメニューの名前にそろえます
  （差分追跡・ボタン列・履歴サイドバー・サンプル履歴は 🟩、サービスリクエスト・タスク管理は 🟪。差分追跡は `diffAdminTitle_()`）。
  編集した人に出す知らせ（差分追跡の停止・行の追加や削除の反映など）とモーダルを開けなかったときの知らせは、内容が分かる名前のままにします。
- **ボタンはチェックボックス＋インストール型 onEdit 1つ**：どの行から押したかが分かるよう各行のチェックボックスをボタンにし、承認の要るモーダルを開くためにインストール型の onEdit を使います。ボタン列が増えてもトリガーは増やしません。
- **モーダルの大きさ**：`showModalDialog` は開くときの大きさしか指定できないため、開いたあとに `google.script.host.setWidth()` でブラウザ幅の95%に広げ、次回のためにその大きさを覚えます。

  区切り線の下に件数と「条件をクリア」。
- 追加した結果は、見出しのカードの中（件数の下）に出し、件数と一緒に見られるようにします（成功は `--teal-wash`、失敗は `#FCEDEC` の地と `--danger` の文字。× で閉じる）。
- 一覧のカード：1件ずつ、上にシート名のバッジ（「クレデン」のバッジと同じ色）とサブインダストリー（シート名と同じなら出さない）、得意先／案件名と右に「追加」（枠線 `#CFE3DC`・文字 `--cred`・高さ 28px）、
  その下にリクエストの文。リクエストの文は2行までにし（`-webkit-line-clamp`）、収まらないものだけに「もっと見る」（開くと「閉じる」）を出します。
  開いたものは、絞り込み・追加で一覧を描き直しても開いたままにします。探した語には印（`mark`）を付けます。中身に合わせた高さで、入りきらないときはカードの中でスクロールします。
- 追加している間は、押したボタンを `--cred` の塗りで「追加中…」にし、ほかの「追加」と再読み込みは押せなくします。
- 権限の承認のカード：読み込み・追加・一覧を開くのが権限で失敗したら、ほかのカードの代わりに出します（形・色は履歴のサイドバーの承認の案内と同じ。小見出しは `--danger` の点）。
  「承認する」は `getAuthorizationLink()` の URL（Google の承認の画面。取れなければ承認用のウェブアプリ）を新しいタブで開き、どちらも無ければメニュー「リクエストを追加」での承認を案内します。
  承認は済んでいるのに失敗するとき（`required: false`。複数のアカウントでログインしているなど）は、そのことを案内します。
  出している間は10秒ごと（「承認する」を押してから5分間は3秒ごと）に裏で読み直し、読めたらカードを閉じて一覧を出します（開き直さなくてよい）。

### 一覧のモーダル（`RequestListDialog`）

パネルの件数のバッジから開く、未登録・登録済みのリクエストの一覧です。ほかのモーダルと同じ大きさ（ブラウザ幅の95%。`credDialogSize_`・`saveCredentialDialogSize`）・見出しの形にしています。

- 見出し：小見出し「サービスリクエスト」の下に、タブ（未登録・登録済み。件数のバッジ付き。履歴のサイドバーのタブと同じセグメント）、右にキーワードの欄と再読み込み（取得した時刻は title）。
- 一覧は表で、見出しの行は上に固定します。未登録はシート（バッジ）・サブインダストリー・得意先・案件名・リクエスト、
  登録済みは行・サブインダストリー・得意先・案件名・リクエスト・判断（サービス化検討は `--teal-soft`、棄却は取り消し線）・サービス案・担当者。
  右端は操作の列で、未登録は「追加」（パネルと同じ枠線 `#CFE3DC`・文字 `--cred`）、登録済みは「削除」（枠線 `#F3CFCB`・文字 `--danger`）。
  「削除」を押すと、その場で「削除する」（`--danger` の塗り）と「やめる」に変わります。
- 追加・削除の結果は、見出しの下に知らせます（成功は `--teal-soft`、失敗は `#FCEDEC` の地と `--danger` の文字。× で閉じる）。
  処理している間は、押したボタンを「追加中…」「削除中…」にし、ほかの追加・削除と再読み込みは押せなくします。
- リクエストの文は3行までにし、収まらないものだけ「もっと見る」を出します。空の値は「—」。探した語には印（`mark`）を付けます。

### 書き方の決まり

- 画面に出す文字は `textContent` で入れます（HTML として解釈しない）。`innerHTML` 系は固定のアイコン（SVG）だけに使います。
- サーバーの関数は `google.script.run` から呼べるよう、末尾に `_` を付けません。
- `Loading.html`（アカウントプランシート作成）は別の機能の画面で、この決まりの前からある簡単な画面です。

## テスト

### ロジック（`npm test`）

`tests/lib/gas-mock.js` が Apps Script のモックです。リポジトリ直下の `*.gs` を Node.js の vm に1つのグローバルスコープとして読み込み、
`SpreadsheetApp`・`PropertiesService`・`LockService`・`ScriptApp`・`HtmlService` などをこのプロジェクトが使う範囲だけ再現します。

- `createGas()` でテスト1件ぶんの環境を作ります。`tests/lib/fixture.js` の `setupProject()` は、新FMT・新FMT2 を作って管理者のセットアップまで済ませます。
- 利用者の操作は `gas.edit(sheet, 'F3', '受注')`（編集イベントを返す）・`gas.change('INSERT_ROW')`・`gas.select(sheet, 'E4')` で再現します。
- スクリプトの書き込みは `gas.writes` に「ロックを持っていたか」と一緒に残るので、書き込みがロックの中かを確かめられます。
- `setValue` の文字列は手入力と同じく変換します（`'` で始まれば文字列のまま、`=` なら数式、日付・数字は日時・数値）。
- vm の中で作られた値は `plain()` で普通のオブジェクトにしてから `deepStrictEqual` で比べます。
- テストはシート名の設定に左右されません。モックが `DIFF_RULES` を `新FMT`（`requests: true`）・`新FMT2` に、リクエスト・タスク管理のシート名を `リクエスト`・`タスク管理` に置き換えます。
  本物の設定は `createGas({realSheetNames: true})` で読み、形と名前の重なりを `tests/project.test.js` で確かめます。
- 数式は計算しません（表示は空）。
- `ui.prompt` で続けて聞く処理（会議サマリのシートと会議日など）は、`gas.promptAnswers` に答えを順に入れます（空になったら `gas.promptAnswer`）。
- Google Slides API（拡張サービス）は `gas.decks` に作ったスライドと `batchUpdate` のリクエストを残します。有効にしていないプロジェクトは `createGas({noSlides: true})`、失敗は `gas.slidesError` で再現します。
- 使う API がモックに無ければ、モックに足してください。

### チェック（`npm run check`）

`scripts/check-syntax.js` が、`.gs`・`.html` がフォルダの中に無いか・構文・`.gs` と `.html` の同名・トップレベルの名前の重複・`onOpen` の数・
HTML ファイル名・メニューや `google.script.run` から呼ぶ関数の有無を確かめます。

### 画面（`.html`）

Playwright（Chromium）で HTML を開き、`google.script.run` をモックに差し替えると表示を確かめられます。

1. HTML の `<?= 名前 ?>` を値に置き換えて、一時ファイルに書き出します。
2. `page.addInitScript()` で `window.google = {script: {run, host}}` を入れます。`run` は `withSuccessHandler`・`withFailureHandler` を受け取り、
   呼ばれた関数名に応じてテスト用のデータを返す Proxy にします。`host` は `setWidth`・`setHeight`・`close` を空の関数にします。
3. `page.goto('file://…')` で開きます（`page.setContent()` では `addInitScript` が効きません）。
4. `#loading` が非表示になるのを待ってからスクリーンショットを撮ります。

Google Fonts が読み込めない環境では代わりのフォントで表示されるので、文字の幅は実際と少し違います。

### 会議サマリのスライド

`mtgSlides_(summary)` の戻り値（箱と表の部品の並び。位置と大きさは pt）を HTML の絶対配置に置き換え、1280 × 720px（1pt = 1280/720px）で Playwright のスクリーンショット・PDF にすると、
Google スライドに送らずに見た目を確かめられます。箱・セルの余白は Slides の既定（左右 7.2pt・上下 3.6pt）、字は BIZ UDPゴシック（Google Fonts の BIZ UDPGothic の TTF を `@font-face` で読む）にします。
文字の折り返しは `mtgWrap_` の見積もりで先に分けてあるので、HTML で行数が増えるところは見積もりが甘いところです。Slides の字の幅は少し違うので、最後は本物のスライドで確かめてください。
