# 設計

スプレッドシート「シナリオ攻略先リスト」に組み込む Apps Script（コンテナバインド・V8）の設計をまとめます。
運用の手順は [OPERATIONS.md](OPERATIONS.md) を参照してください。

> **シート名について**：シート名は設定で変えられます。このドキュメントでは、差分追跡の対象のシート（今の名前は「スーパー・GMS」「コンビニ」「百貨店」「化粧品・トイレタリー」「飲料・食品」「地方銀行」「自動車販売」「住設」「電鉄・不動産」「エネルギー」「生協」の11シート。前の名前は新FMT・新FMT2）を「新FMT」、
> リクエストを登録するシート（今の名前は「サービスリクエスト」）を「リクエスト」、タスクのシート（今の名前は「サービス案タスク管理」）を「タスク管理」と書きます。
> 今の名前と書いてある場所は、OPERATIONS.md の「シート名の一覧」を見てください。

差分追跡のファイルが `test.gs` という名前なのはそのためです。
ファイルはリポジトリ直下に置きます。フォルダに入れると、同期したときにエディタのファイル名にフォルダ名が付き（`src/HistorySidebarView` など）、
`createTemplateFromFile('HistorySidebarView')` が HTML を見つけられなくなるためです。

### 1つのグローバルスコープ

Apps Script はプロジェクトの全ファイル（リポジトリ直下の `.gs`）を1つのグローバルスコープに読み込みます。

- ファイルをまたいで関数・定数を使えます。たとえば `CredentialHistory.gs` は `DIFF_RULES` や `diffAppend_()` を、
  `Changehistory.gs`・`HistorySidebar.gs` は `cred*` の関数を使います。
- 同じ名前の `const` があると読み込みで失敗し、同じ名前の `function` はどちらか一方しか動きません。
  `onOpen` はプロジェクトに1つだけ（`CredentialHistory.gs`）で、ほかのメニューはそこから呼びます（`svcAddMenu_()`、`CRED_OPTIONS.accountPlanMenu` が true なら `apAddMenu_()`）。
  メニューは追加した順に左から並ぶので、「🟩RXビジネスMTG用」→「🟪RXサービスMTG用」（→「アカウントプランシート作成」）の順に呼びます。
  単純トリガーの `onEdit` は置いていません（ボタン列はインストール型の `onCredentialLauncherEdit` 1つ）。
- 別のファイルの関数を「無くても動く」ように使うときは `typeof 関数名 === 'function'` で確かめてから呼びます
  （例：`recordDiffEdit` の `credIsLauncherEdit_`）。

## シートと保存場所（データモデル）

### 追跡シート（`新FMT`・`新FMT2`）

`DIFF_RULES` に書いたシートです。2行目が見出しで、追跡範囲は `D3:AF` です（シートがそれより狭いとき（2026/10/26 から A〜AA の27列）は、シートの中まで読みます。`diffRuleRange_`。範囲の右端（AF）を列の数として行・列の番号で指すと、シートの外を指して止まるため。移行ツールはこれで止まっていた）。見出し行には次が必要です。

| 見出し | 数 | 用途 |
|---|---|---|
| `最終更新日時` | ちょうど1つ | 差分追跡が変更した行に日時を入れる（「（自動入力）」の付いた見出しも可）。追跡範囲から自動で外す |
| `得意先` | ちょうど1つ | 履歴の照合に使う。全角・半角と空白の違いは無視する（`credNormalize_`） |
| `クレデンシャル`（改行）`オファリング登録` | ちょうど1つ | ボタン列（チェックボックス）。**追跡範囲の外** |
| `変更履歴` | ちょうど1つ | ボタン列（チェックボックス）。**追跡範囲の外** |

ボタン列のチェックは差分として残したくないため、追跡範囲に含まれていると `setupCredentialLauncher()` などが止まります。

### `変更履歴_差分`（追記のみ）

1セル1行です。列は次の9列で、`Changehistory.gs`・`HistorySidebar.gs` は B〜I 列を位置で読みます（列の順番を変えないでください）。

`記録日時`・`イベントID`・`編集者メールアドレス`・`シート`・`セル`・`列名`・`種類`・`変更前`・`変更後`

- 文字列はすべてリッチテキストで書きます（`=` で始まっても数式にならない）。空欄は `（空欄）` と書きます。
- 前の版にあった `差分`（文字単位の差分の色付き表示）と `確認済み`（チェックボックス）は、セル数を節約するためにやめました。
  文字単位の差分は、変更履歴の画面（`getChangeHistoryData`）が変更前・変更後からその場で作ります。
  前の版の11列のシートは左の9列が同じなので、そのまま読み書きでき、`compactDiffRecords()` で2列を削除します。
- 古い版の列構成（8・9・10列）が見つかったときは、`diffLogSheet_()` が足りない列を差し込みます。
- シートを作るとき、使わない右の列・下の行を削除し（`diffTrimGrid_`）、記録を足すときは必要な行だけ足します。
  空のセルもスプレッドシートの上限（1,000万セル）に数えられるためです。

### `変更時点スナップショット`（追記のみ）

イベントID × 変更した行ごとに1行です。列は次の8列です。

`記録日時`・`イベントID`・`編集者メールアドレス`・`シート`・`行番号`・`変更セル`・`得意先`・`行の内容`

- `行の内容` は、その行の見出しと値を `[[見出し, 値], …]` の JSON で1つのセルにまとめたものです（見出しの順。空欄の項目とボタン列は持たない）。
  見出しごとに1セルずつ写すと、1回の編集で約40セル使っていたためです。1つのセルの上限を超えるときは、長い値から省略します（`diffSnapshotContent_`）。
- `得意先` は `行の内容` にも入っていますが、サイドバー・変更履歴が得意先で記録を探すため、別の列にも置きます。
- 見出しは、同じ見出しが2つある列は `見出し [列記号]`、見出しの無い列は `D列（見出しなし）` になります。値は表示値（`getDisplayValues`）です。
- 前の版（固定の6列のあとに見出しごとの列が並ぶ）のシートには、`得意先`・`行の内容` の列が無ければ右端に足し、新しい行はこの2列だけに書きます。
  読み手（`Changehistory.gs`）は、`行の内容` が空の行を見出しごとの列から読みます。
  `compactDiffRecords()` が前の版の行を `行の内容` にまとめ（値は変えない）、見出しごとの列を削除します。
  時間内に終わらないときは途中で止め、もう一度実行すると続きから行います（見出しごとの列は、すべての行をまとめてから削除する）。

### `__CHAR_DIFF_<シートID>`（非表示）

比較基準です。追跡シートと同じ位置に、セルの値を「型の1文字＋値」で入れます。
`S`（文字列）・`N`（数値）・`B`（真偽値）・`D`（日時。ミリ秒）・`F`（数式）。空欄は空のままです。
先頭が `=` にならないので、比較基準の中で数式が動くことはありません。
比較基準は追跡範囲の右端の列・追跡シートの行数までにします（`setupDiffTracking()` で使わない列・行を削除する）。
セルごとに比べる仕組みの中心なので、形は変えていません（記録が増えても大きくならない）。

### `クレデンシャル履歴_記録`

1件1行です。列は**見出し名**で見分けるので並べ替えは自由ですが、見出し名は変えないでください。足りない列は右端に追加します。

`ID`・`登録日時`・`得意先`・（入力項目：`予定日`・`実施日`・`種別`・`役職`・`氏名`・`名称`・`フリーコメント`・`担当者名`・`担当部署`）・`紐づくクレデンシャルID`・`登録者`・`登録元（登録時の行）`・`更新者`・`更新日時`・`削除者`・`削除日時`

- 入力項目は `CRED_OPTIONS.fields` で決まり、`label` が見出しになります。
- 文字列は先頭に `'` を付けて書きます（`credText_()`）。数式・日付・数値に変わりません。
- 削除は既定で「削除者・削除日時を入れて非表示」（`deleteMode: 'soft'`）です。
- 以前の版の見出し（`日付`→`実施日`、`備考`→`フリーコメント`）は自動で書き換え、`宛先` 列は読み取りだけに使います。

## 処理の流れ

### 差分追跡

インストール型トリガーが3つあります（`setupDiffTracking()` が設置）。

1. **編集（`recordDiffEdit`）**：編集された範囲だけを比較基準と比べ、変わったセルごとに差分を記録します。
   順番は「最終更新日時 → 差分ログ → スナップショット → 比較基準の更新」です（スナップショットに最終更新日時が入るように、また記録が書けてから基準を進めるように）。
   その前に、行数の変化と行のずれ（下記）を確かめ、あれば先に行を突き合わせます。
2. **構成の変更（`pauseDiffOnStructureChange`）**：
   - 行数だけが変わったとき：比較基準の行と今の行を突き合わせ（`diffResyncRows_`）、
     消えた行を `行削除`、増えた行を `行追加`、同じ行で変わったセルはセルの変更として記録し、比較基準を取り直します。
   - 行の追加・削除の通知なのに行数が変わっていないとき（削除と追加がトリガーより先に両方起きた）：操作したシート（アクティブなシート）だけ行のずれを確かめ、ずれていれば同じように突き合わせます。
   - 列の追加・削除：値は変わらないので、その場でそのシートの比較基準を取り直して（`diffRebaselineSheet_`）記録を続けます。取り直せない（見出しが足りないなど）ときだけ止めます。
   - シートの削除（名前の変更）：そのシートの追跡を止めます。
3. **取りこぼしの回収（`catchUpDiffTracking`、5分ごと）**：印の付いたシートだけを処理します。行数の変化・行のずれがあれば突き合わせ、
   無ければ、データのある最後の行までを比較基準と比べて記録します（「行の確かめ」の印だけなら、全セルは比べません）。

ロックが取れないとき（ほかの実行が書き込み中）は、エラーにせず印を付けて回収に任せます。
編集のときは、そのシートに「取りこぼし」の印を付けます。構成の変更のときは、行数・列数が変わったシートと操作したシートだけに「行の確かめ」の印を付けます（全シートを全セル比較にしない）。
#### 止めない・止まっても自動で立て直す（2026/10/17）

前の版は、記録の途中のエラー（一時的な Sheets のエラーも）・2,000セルを超える貼り付け・列の追加で、そのシートの追跡を止め、
管理者が `setupDiffTracking()` を実行するまで止まったままでした（時間がたつと「差分追跡は止まっています」のエラーが続く原因）。今は：

- **編集の記録のエラー**：止めずに取りこぼしの印を付け、取りこぼし回収で記録し直します（エラーにしない）。
  比較基準が使えない（比較用シートが無い・構成が違う。`diffStructureError_`）ときだけ、そのシートを止めます（トーストで「5分ほどで自動で再開します」）。
  止まっているシートの編集も、エラーにせず印だけを付けます。
- **大きな編集**（`maxCellsPerEdit` を超える）：止めずに、取りこぼし回収（`catchUpChunkCells` ずつ比べる）に任せます。
- **取りこぼし回収のエラー**：印を残して次の回でやり直し、`maxCatchUpFailures`（3）回続けて失敗したら止めます（回数は `CHAR_DIFF_FAIL_V1_<シートID>`）。
- **止めるときは理由を残す**（`diffPause_` の `pausedReason`・`pausedAt`）。`diagnoseDiffState()` と、止まっているシートの知らせに出します。
- **自動の立て直し**（`diffHealPaused_`。取りこぼし回収のはじめ）：止まっているシートと、一度は設定したのに状態が無いシート（設定が途中で止まった・あとから足した）を立て直します。
  比較基準がそのまま使える（構成が同じ・比較用シートがある）なら再開して印を付け、止まっていた間の変更も回収で記録します（`resumedAt`）。
  使えない（比較用シートが無い・列が変わった・回収が続けて失敗した）なら、今の値で比較基準を取り直します（`rebuiltAt`。止まっていた間の変更は記録されないが、
  会議サマリは時点コピーと比べるので資料には出る）。取り直せない（見出しが足りないなど）ときは止めたまま `healError` を残し、`healRetryMinutes`（30分）あけて試します。

#### 行の突き合わせと、行のずれ（v6）

- **突き合わせ（`diffResyncRows_`）**：比較基準と今の行を、行の中身で LCS により対応させます（`diffAlignRows_`。前後の一致を除く）。
  対応しなかった行は `diffPairRows_` で組にします。見分け列（`DIFF_ROW_OPTIONS.keyHeaders`：`得意先`・`案件名`）の値が同じ行は、離れていても同じ行とみなし（移動・並べ替え・ずれたあとの編集）、変わったセルだけを記録します。
  残りは、すき間ごとに同じ数なら位置で組にし、数が違えば `行削除`・`行追加` にします。移動しただけの行は何も記録しません。
- **ずれの検知（`diffRowsShifted_`）**：ある行の見分け列の値が、比較基準では別の行にあった値なら「ずれた」とみなします。
  比較基準のどこにも無い値（新しく入力した・書き換えた得意先）は、ふつうの変更として扱います。編集で見分け列そのものを変えた行は手がかりにしません。
  読むのは見分け列をまたぐ1つの範囲（シートと比較基準）を、データのある最後の行までだけです。
- **編集トリガーから突き合わせたとき**：編集した範囲の変更はふつうの編集（`EVT`・編集した人）として記録し、それ以外の未記録の変更は `ROW`・編集者 `不明（行の追加・削除）` で記録します（編集した人の変更にしない）。
- **調べるシート**：編集トリガーは編集したシート、変更トリガーは行数が変わったシートと操作したシート、取りこぼし回収は印の付いたシートだけです。追跡シートが11個あっても、1回の処理で全シートを読むことはありません。
  変更トリガーの通知にはシートの情報が無いため、操作したシートはアクティブなシートで判断します。取れなかったシートのずれは、そのシートの次の編集・取りこぼし回収で気づきます。
- **見分けられない場合**：`得意先`・`案件名` がどちらも同じ行が複数あると、並べ替えのあとに組を取り違えることがあります（同じ得意先の中での取り違えなので、ほかの得意先の履歴には混ざりません）。

### クレデンシャル・オファリング履歴

**2026/10 から一旦使っていません**（`CRED_OPTIONS.enabled: false`。`credEnabled_()`）。止めている間は、開く・登録する入口（`credShowDialog_`・`credOpenLauncherDialog_`
のクレデンシャル・`saveCredentialEntry` などの登録・編集・削除・`setupCredentialLauncher`）を `credRequireEnabled_()` で止め、
サイドバーの束（`getSidebarBundle`）はクレデンシャルを読まずに `credentialsEnabled: false` を返します（画面はクレデンシャルのタブを隠して変更履歴だけにする。
開いた直後も出さないよう、テンプレートの `data-credentials` でも渡す）。会議サマリは入力内容のチェックの種類から「予定日超過」を除きます（`mtgAlertTypes_`。表の列も減る）。
記録のシート・コードは残すので、`true` に戻せば元どおりです。テストは機能を確かめるため `true` にして動かします（`tests/lib/gas-mock.js`。止めた状態のテストは個別に `false`）。

1. ボタン列をチェックすると `onCredentialLauncherEdit`（インストール型 onEdit。2つのボタン列で共通）が動き、
   見出し行を1回読んでどちらのボタンかを判断し、すぐにモーダルを開いてチェックを戻します。
2. モーダルは開いてから `getCredentialDialogData()` で履歴を読み込みます（ボタンを押してから開くまでを速くするため）。
3. 登録・編集・削除は、画面を先に更新し、サーバーへは1件ずつ順番に送ります。サーバー側では
   - ドキュメントロックを取り（`credWithLock_`）、
   - 行の得意先が開いたときと同じか（`credTarget_`）、
   - 編集・削除なら、開いたときの内容から他の人が変えていないか（`credExisting_`）
   を確かめてから書き込み、`変更履歴_差分` にも `CRD` で記録します。差分ログへの記録に失敗しても本体の保存は取り消さず、警告を返します。
4. 予定と実績：`実施日` が空なら「予定」、入っていれば「実績」です。どちらか一方の日付が必須です。
5. 紐づけ：オファリングは、同じ得意先のクレデンシャルに紐づけられます（1つのクレデンシャルに複数）。
   紐づくオファリングがあるクレデンシャルは種別を変えられません。クレデンシャルを削除すると、オファリングは紐づけなしで残ります。

### 変更履歴

`変更時点スナップショット` から「シート＋得意先」が一致する記録を新しい順に最大300件読み、
同じイベントIDの `変更履歴_差分` から、その行のセルの変更前・変更後を取り出します。
差分ログが見つからない記録は、1つ前のスナップショットとの違い（最終更新日時は除く）で補います。
記録は行の順ではなく `記録日時` の順に並べ替えてから使います（サンプルのように、過去の日時の記録があとから足されることがあるため）。サイドバーも同じです。

行番号は行の追加・削除や並べ替えで変わるため、行番号では探しません。得意先名を変える前の記録は表示されません。
同じイベントに複数の行の記録があるときは、セルの行番号で分けます（`chgRecordOfRow_`。サイドバーも同じ）。削除された行の記録（`N行（削除前の行番号）`）は、残っている行の履歴には出しません。

### 履歴サイドバー

- Apps Script にはサイドバーへ選択の変化を知らせる仕組みが無いため、サイドバーから「今選ばれている行」を問い合わせ続けます
  （操作中は0.25秒、しばらく操作がなければ1.2秒・4秒と間隔を空ける。前の問い合わせが返ってから次を送る）。
  同じ行なら得意先を読まずに返します。
- 履歴は全得意先ぶんを1回でまとめて読み込み（`getSidebarBundle()`）、行が変わるたびには読みません。1分ごとに読み直します。
  変更の記録は、シート・得意先ごとに新しい方から `HS_OPTIONS.eventsPerCustomer`（30回）まで読みます。それより古い記録がある行は
  `changesMore` で知らせ、一覧の最後に「それより前は「変更の詳細」で確認できます」と出します。
- 画面は「表示中の行」のカードと、「クレデンシャル」「変更履歴」の2つのタブです。
  - 得意先名の右の「アカウントプラン」は、`HS_OPTIONS.accountPlan` のシート（既定は `33シナリオ攻略先リスト`、E列が得意先、M列が URL）から
    同じ得意先（`credNormalize_` で照合。同じ得意先が複数あれば上の行）の URL を探し、新しいタブで開くリンクにします。
    セルに URL がそのまま無いときは `HYPERLINK` の数式とセルのリンクも見ます。`http(s)` 以外はリンクにせず、URL が無い得意先では押せない表示（灰色）にします。
  - クレデンシャル：オファリングは紐づくクレデンシャルの下に字下げして並べます。項目を押すと、その履歴を編集する状態でモーダルを開きます。
    予定（実施日が空）の項目は日付の前に「予定」、予定日を過ぎていれば「期限超過」を付けます。
  - 変更履歴：変更を項目（列）ごとに1件として、日ごとにまとめて新しい順に並べます。期間（過去7日・14日・30日・すべて・日付の指定）、
    7日ぶんの帯で選んだ日、項目（複数選択）で絞り込めます。「変更の詳細」は変更履歴のモーダルを開きます（日・項目で絞り込んでいるときは、表示中のいちばん新しい変更の位置で開く）。
- サイドバーは、利用者がメニュー「🟩RXビジネスMTG用」＞「履歴サイドバーを開く」（`openHistorySidebar`）で開きます。
  開いているシートが対象（`DIFF_RULES` のシート）でなければ開かず、対象のシートを `ui.alert` で知らせます（`hsIsTargetSheet_`）。
  「権限を承認する（初回のみ）」も、対象外のシートでは承認だけしてサイドバーは開かず、トーストで知らせます。
  開いたあとに別のシートへ移ったときは、これまでどおりサイドバーの中に「対象外のシート」と出します。
  前の版はスプレッドシートを開いたときにインストール型の起動時トリガー（`autoOpenHistorySidebar`）で自動で開いていましたが、やめました
  （サイドバーは同時に1つしか出せず、サービスリクエストの選択パネルと入れ替わるため、利用者が開くものにした）。
  前の版のトリガーが残っていても、`autoOpenHistorySidebar` はそのトリガーと各自のオフの設定を外すだけで、サイドバーは開きません
  （関数を消すと、残ったトリガーが「関数が見つからない」エラーになるため名前を残している）。管理者は `removeHistorySidebarAutoOpen()` でも外せます。
- サイドバーから呼ぶ関数（`getSidebarSelection`・`getSidebarBundle`）は、開いた本人の権限で動きます。メニューから開くと、まだ承認していない人にはその場で承認の画面が出ます。
  一部の権限を外して承認した人などで呼び出しが失敗したときは、再試行の間隔を延ばし（10秒）、「権限の承認が必要です」と「承認する」ボタンを表示します。
  承認が済めば、開き直さなくても次の問い合わせから表示が始まります（ボタンを押してから5分間は3秒ごとに問い合わせる）。
- 「承認する」ボタンは、Google の承認の画面を新しいタブで開きます（サイドバーの中からは承認の画面を出せないため）。
  行き先は、承認の案内を初めて出すときに `getAuthorizationLink()` で問い合わせます。開いた本人の権限で動くので、
  承認が足りなければ `ScriptApp.getAuthorizationInfo(FULL).getAuthorizationUrl()` が承認の画面の URL を返します（ウェブアプリの用意は要らない）。
  前の版はサイドバーを起動時トリガー（管理者の権限）で開いていたため、この URL が空になり、ウェブアプリが必要でした。今はメニューから開くので、本人の URL が取れます。
  URL が取れないとき（問い合わせ自体が失敗したときなど）は、承認用のウェブアプリ（`doGet`。「ウェブアプリにアクセスしているユーザー」として実行。`HS_OPTIONS.authorizeUrl`。
  `…/exec` の形でなければ使わない）を開き、どちらも無ければメニューでの承認を案内します。
  ウェブアプリは、まだ承認していない人には Google の承認画面を出し、承認が済むと `AuthorizeView` で「権限の承認が完了しました」と出します（一部の権限を外した人には、もう一度承認するリンクを出す）。
  承認は済んでいるのに呼び出しが失敗するとき（`required: false`）は、複数の Google アカウントでのログインを案内します（ボタンは出さない）。
  サービスリクエストの選択パネルも同じ `getAuthorizationLink()` を使います。
- 読み取りだけなのでロックは取りません。

### アカウントプランシート作成（`コード.gs`）

`showLoadingDialog()`（エディタから実行。`CRED_OPTIONS.accountPlanMenu` が true ならメニュー「アカウントプランシート作成」→「作成開始」）→ シート名を入力 → 対象件数（E列が入力済みで M列が空）を確認 → 実行、の順です。
メニューは、利用者のメニューを2つ（🟩・🟪）にするため、ふだんは出していません。
1行ずつテンプレートをコピーして M列に URL を入れ、5分たったら中断します（もう一度実行すると、M列が空の行だけを続けて処理します）。

- 1行ごとにドキュメントロックを取り、ロックの中で「行の内容が読み込んだときと同じか」を確かめてからコピーします
  （処理中に行が挿入・削除されても、違う行に URL を入れないように）。ロックが取れなければ、コピーせずに止めます。
- 追跡シートに書き込んだときは取りこぼしの印を付けます。スクリプトの書き込みでは編集トリガーが動かないためで、
  次の回収で `REC`（編集者 `不明（取りこぼし回収）`）として記録されます。

### サービス管理（`ServiceManagement.gs`）

流れは「リクエスト（新FMT の Z列）→ サービス案（リクエストをもとに考え、名前でまとめる）→ タスク（サービス案の検討の進捗）」です。

- サービスは最初から決まっているものではなく、リクエストをもとに考えるものなので、サービスの一覧のシートは持ちません。
  `リクエスト` の `サービス案` の列に付けた名前がサービス案で、同じ名前を付けたリクエストが1つのサービス案にまとまります（多対1）。
- `リクエスト` シート：1行が1件のリクエスト。列は左から次のとおりです。
  - `追加日`（スクリプトが行を足した日。パネル・まとめて取り込むで足した行はその日、手で足した行は ID を振った日。日付として書き、表示は yyyy/mm/dd。
    前の版の見出し `取り込み日` は、見出しの用意で `追加日` に書き換えて値を使う）
  - `ID`（SR-0001 の形。スクリプトが振る。下の「ID」）
  - 取り込み元から書く列（選択パネルで選ぶとスクリプトが書く。入力規則なし）：`サブインダストリー`・`得意先`・`案件名`・
    リクエストした営業の `アカウント責任者部署`・`アカウント責任者`・`BX部署`・`BX担当`（取り込み元の列と同じ並び）・`リクエスト`。
    営業の4列は `SVC_OPTIONS.sourceOptionalHeaders` で、見出しが無いシートでは空として読みます（必須なのは `sourceHeaders` の4つだけ）。
  - 人が入れる列：`判断`（プルダウン）・`サービス部門からのフィードバック`・`サービス案`（まとめる先の名前）・
    サービス部門として対応する `主管本部`・`担当者`（判断のほかは自由に入力・入力規則なし。`SVC_OPTIONS.inputKeys`）。
  前からあるシートに足す列は、`insertAfter` の見出しのすぐ右に、`insertBefore` の見出しのすぐ左に差し込みます（`taskEnsureHeader_`。追加日は ID の左、ID はサブインダストリーの左、営業の4列は案件名の右、
  フィードバックは判断の右、主管本部はサービス案の右、担当者は主管本部の右）。列がまだ無いシート（`setupRequestSheet()` の前）でも、
  追加・読み取りはある列だけで動きます。追加日の目印の ID もまだ無いシートでは、ID を差し込んでから、その左に追加日を差し込みます。
  差し込んだ列は左の列の入力規則を引き継ぐことがあるので、自由に入力する列の入力規則は `svcApplyRules_` で外します。
  使わなくなった列（`removedColumns`：`メモ`）は、`setupRequestSheet()` が確認してから削除します（`taskDeleteColumns_`）。
  `追加日` は前の版で使わなくなった列でしたが、2026/11 にまた使うようにしました（前からある `追加日`・`取り込み日` の列は、その位置のまま値を使う）。
- シートを足した・名前を変えたあとの設定は `setupAfterSheetChange()`（`test.gs`）でまとめて行います。先に `diffCheckSheets_()` で全シートの見出しを読むだけで確かめ、
  足りなければ何も変えずに知らせます（途中で止まって、差分追跡だけ・ボタン列だけが設定された状態にしないため）。
  ボタン列は使うシートだけに置けばよく、見出しの無いシートは飛ばします（`credColumnByHeader_` の `optional`。`setupCredentialLauncher()`・`setupChangeHistoryLauncher()` も同じ）。
  そのあと `setupDiffTracking()`・`setupCredentialLauncher()`・`setupChangeHistoryLauncher()`・`svcSetupRequestSheet_()` を順に呼びます（どれも何度実行してもよい）。
- シート名を変えた追跡シート：差分追跡の記録（`変更履歴_差分`・`変更時点スナップショット`）はシート名で残り、記録は書き換えないので、
  `DIFF_RULES` の `formerNames` に前の名前を書きます。読み手（`Changehistory.gs`・`HistorySidebar.gs`）は `diffSheetNameResolver_()` で前の名前を今の名前にそろえて見ます。
- 読むシート（`svcSourceSheets_`）：`DIFF_RULES` で `requests: true` を付けたシートです。新FMT の名前と見出しの行を `DIFF_RULES` の1か所に置くため、
  `SVC_OPTIONS` には読むシートを書きません（シート名が2か所にあると、片方だけ直す間違いが起きるため）。
- 選択パネル（`RequestPickerView`。メニュー「🟪RXサービスMTG用」→「リクエストを追加」→ `openRequestPicker()`）：
  - `リクエスト` のシート（`SVC_OPTIONS.requestSheet`）を開いているときだけ開きます。ほかのシートでは開かず、`ui.alert` で開けるシートを知らせます。
  - パネルから呼ぶ関数は、開いた本人の権限で動きます。`openRequestPicker()` は最初に `ScriptApp.requireAllScopes()` を呼び、
    承認が足りない人（初めて使う人・一部の権限を外して承認した人）には、メニューを押したときに承認の画面を出します。
    開いたあとに呼び出しが権限で失敗したとき（承認の取り消し・権限が増える更新など）は、パネルに「承認する」ボタンを出します（履歴のサイドバーと同じ `getAuthorizationLink`）。
  - 開いたとき・再読み込みのとき（`getRequestPickerData()`）に、新FMT をすべて読み直し（`svcSourceRecords_`。得意先・案件名・リクエストの組で1つ。全角・半角と空白の違いは無視）、
    `リクエスト` にまだ無いもの（`svcRegistered_`）だけを返します。新FMT の編集を見張る処理は無く、パネルを開くたびに最新を読むので取りこぼしがありません。
    サブインダストリー・得意先・案件名が空のリクエストも出します（登録はできる。絞り込みでは空の値も選べる）。
  - 絞り込み（サブインダストリー → 得意先 → 案件名。左で選んだものに合う値だけを右のプルダウンに出す）と、文字での検索（空白で区切った語をすべて含むもの）は
    画面の中だけで行います（サーバーを呼ばない）。一度に出すのは200件までで、残りは絞り込んでもらいます。
  - 「追加」（`addServiceRequest(key)`）：ロックの中で新FMT と `リクエスト` を読み直し、まだ無ければ、最後の行の下に書いてから、
    そのサブインダストリーの行の最後に動かします（下の「行の並び」）。
    最後の行は `リクエスト` の列（A〜H）のどれかに値のある行で見ます（判断だけを書いた行にリクエストを書き足さないため。ほかの列は見ない）。
    行が足りなければ足し、足した行にも判断のプルダウンを付けます。判断などは入れません。
    同じリクエストがすでにある（ほかの人が先に追加した）・新FMT から消えたときは書かずに知らせ、どの場合もパネルの新しい内容（`svcPickerData_`）を返します。
  - 前の版は、セルの連動プルダウンで A〜D を選び、候補を非表示の `__REQUEST_LISTS` シートの数式で作り、単純トリガーの `onEdit` で整えていました。
    行の並べ替え・追加でプルダウンだけがずれる、`onEdit` が30秒で止まって候補が一斉にエラーになる、差分追跡とロックを取り合う、
    新FMT の変更が候補に反映されない、といったことが続いたため、パネルで選ぶ形に変えました（`onEdit` は置いていない）。
    前の版の A〜D の入力規則と `__REQUEST_LISTS` は、選択パネルを開いたとき・「追加」のとき・`setupRequestSheet()` のときに外します（`svcRemoveLegacyLists_`）。
    外したら（または無かったら）印を付け（`SVC_OPTIONS.legacyDoneKey`）、それからはパネルを開いたとき・追加のときには確かめません（入力規則・メモを読むのは時間がかかるため。`setupRequestSheet()` では毎回確かめる）。
    候補に無い値を拒否する入力規則が残っていると、スクリプトの書き込み（`setValue`）もその規則のヘルプの文で止まるためです。A〜D には入力規則を付けないので、残っていれば列ごと外します。
- まとめて取り込む（メニュー「🟪RXサービスMTG用」→「サブインダストリーのシートから取り込む」→ `importServiceRequests()`）：
  新FMT（`requests: true` のシート。今は11のサブインダストリーのシート）のリクエストのうち、まだ `リクエスト` に無いものをすべて、
  最後の行（`svcRegistered_`）の下に取り込み元の順（シートの順・行の順）に書き、それぞれのサブインダストリーの行の最後に動かします（下の「行の並び」）。
  書く列は追加日・ID と取り込み元から書く列（サブインダストリー・得意先・案件名・営業の4列・リクエスト。`setupRequestSheet()` で作った並びでは A〜J）で、
  判断などは入れません。
  - 重ならないようにする決まりはパネルと同じです。得意先・案件名・リクエストの組（全角・半角と空白の違いは無視。`svcRequestKey_`）で
    1件とし、シートをまたいで同じものは最初の1件だけにします（`svcSourceRecords_`）。`リクエスト` にあるものは書かないので、何度押しても重なりません。
  - 書く前に、取り込む件数とシートごとの内訳を `ui.alert` で見せて確かめます（確認はロックを取る前。答えるまでほかの処理を待たせないため）。
    書くときはロック（`taskWithLock_`）の中で取り込み元と `リクエスト` を読み直します（`svcImportRequests_`）。確かめている間にほかの人がパネルから
    追加したものも重なりません。新しく書くものが無ければ確かめずに、登録済みの行を合わせるだけにします。
  - パネルを開いたときと同じく、前の版のプルダウンを外し（`svcRemoveLegacyLists_`）、登録済みの行を取り込み元に合わせ（`svcSync_`）、
    ID を直して（`svcEnsureIds_`）から、新しい ID をまとめて振ります（`svcTakeIds_`）。書き込みは列ごとに1回（行の数によらない）です。
    行が足りなければ足し、足した行にも判断のプルダウンを付けます。最後にタスク管理の候補を合わせます（`svcRefreshTaskChoices_`）。
  - 終わったら、取り込んだいちばん上の行を選び、件数・ID・シートごとの内訳と、登録済みで書かなかった件数・ほかと同じでまとめた件数・
    取り込み元に見つからない行（書き換え・削除された可能性）を知らせます。取り込み元で書き換えたリクエストは、パネルと同じく新しいリクエストとして取り込み、前の行は残します。
  - 一度取り込んだリクエストは、行を削除しても次からは取り込みません（下の「一度取り込んだリクエストの覚え」）。確認の画面にもそう書きます。
- 一度取り込んだリクエストの覚え（非表示のシート `SVC_OPTIONS.importedSheet`＝`__REQUEST_IMPORTED`）：A 列に、リクエストのキー（`svcRequestKey_`）の要約
  （`svcImportedKey_`＝`svcTextHash_`）を1件1行で持ちます。まとめて取り込む・自動の取り込みのたびに、そのとき `リクエスト` にあるリクエストと取り込んだリクエストを足します
  （`svcRememberImported_`。まだ無いものだけを下に足す。使わない列は持たない）。まとめて取り込む・自動の取り込みは、覚えにあるリクエストを取り込みません。
  - 「不要な行は `リクエスト` で削除する」運用で、削除した行が次の取り込みで戻らないようにするためです。選択パネル・一覧のモーダルは覚えを見ないので、削除したリクエストも未登録に出て、手で追加し直せます。
  - 取り込み元で得意先・案件名・リクエストを書き換えると、キーが変わるので新しいリクエストとして取り込みます。
  - 覚えを消す（シートを削除する）と、そのとき `リクエスト` に無いリクエストは、次のまとめて取り込むでまた入ります。
- 自動の取り込み（`serviceImportTick`。時間主導トリガー）：`installServiceImportTrigger()`（管理者がエディタから1回実行する）が、
  `SVC_OPTIONS.autoImportMinutes`（5分）ごとのトリガーを1つだけ作ります（前からあるものは消して作り直す。トリガーの所有者は実行した人）。止めるのは `removeServiceImportTrigger()`。
  - 中身はメニューのまとめて取り込むと同じ（`svcImportRequests_`）で、画面は出さず、結果は実行ログに書きます。
  - ロックを `autoImportLockWaitMs`（10秒）だけ待ち、取れなければその回は飛ばします（選択パネルの追加などを長く待たせないため。次の回に取り込む）。
  - 覚えのシートが無いときは動きません。覚えが無いまま取り込むと、それまでに削除した行が戻るためです。
    `installServiceImportTrigger()` は始める前に、取り込み元にあって `リクエスト` に無いリクエスト（削除した行を含む）を、今取り込むか（はい）、取り込まずに覚えるか（いいえ）を聞きます。
  - 5分にしたのは、1回に取り込み元の11枚のシートを読むためです（1分だと1日1,440回になり、トリガーの1日の実行時間の上限とロックの待ち合いに響く）。差分追跡の回収（`catchUpDiffTracking`）と同じ間隔です。
- 一覧のモーダル（`RequestListDialog`）：パネルの件数のバッジ（未登録・登録済み）を押すと `openRequestListDialog(kind)` で開きます（押したバッジのタブで開く）。
  `getRequestListData()` が新FMT と `リクエスト` を読んで、未登録（シート・A〜D）と登録済み（行番号・A〜D・判断・サービス案・担当者・取り込み元のシート）を返します。
  読むだけなのでロックは取りません。登録済みで新FMT に見つからないものには「取り込み元に無し」の印を付けます（シートのメモの代わり）。
  モーダルからも追加・削除できます。追加（`addServiceRequestFromList(key)`）はパネルの追加と同じ処理（`svcAddRequest_`）で、一覧の新しい内容を返します。
  削除（`deleteServiceRequest(row, key)`）は、ロックの中で `リクエスト` を読み直し、一覧を読んだときの行が同じキーならその行を、
  並べ替え・行の追加などで行がずれていれば同じキーの行を探して削除します（同じキーの行が複数あって1つに決まらない・見つからないときは削除しない）。
  判断・サービス案などの入力も行ごと消えるので、モーダルで「削除する」「やめる」を出して確かめます（入力のある行には「判断などの入力も消えます」と出す）。
  削除したリクエストは未登録に戻ります。パネルは、モーダルを閉じて戻ってきたとき（ポインタが入る・フォーカスが戻る）に裏で読み直します。
- ID（`svcEnsureIds_`・`svcTakeIds_`）：登録したリクエストに `SR-` と4桁の番号を振ります（`SVC_OPTIONS.idPrefix`・`idDigits`）。
  - 振る番号は、シートの ID の列にある最大の番号と、これまでに振った最大の番号（スクリプトのプロパティ `idCounterKey`）の大きいほうの次です。
    手で書いた ID（全角や番号だけの `12` も番号として読む）とも、削除した行の ID とも重なりません（番号は使い回さない）。
    これまでに振った最大の番号は、エディタの「プロジェクトの設定」→「スクリプト プロパティ」で見られます。前の版はドキュメントのプロパティの同じ名前に置いていたので、
    残っていれば大きいほうを引き継いで消します（`svcLastIssuedId_`・`svcSetLastIssuedId_`）。値を手で小さくしても、シートの最大の番号より小さい番号は振りません。
  - 番号を決めて書くところまでをロック（`taskWithLock_`）の中で行うので、同時に追加しても重なりません。
  - 追加したとき・パネルを開いたとき・`setupRequestSheet()` のときに、リクエストのある行のうち ID の無い行と、
    上の行と同じ ID・読めない ID の行（行のコピーなど）に新しい番号を振ります（上の行の ID は残す）。振り直したときは知らせます。
  - モーダルの削除は ID で行を決めます（同じ ID で同じリクエストの行が1つなら、その行。無ければ行番号とキーで探す）。
  - ID を振った行の追加日が空なら、今日の日付を入れます（`svcFillAddedAt_`。手で足した行は、ここで初めて追加日が入る）。
  - 追加日を履歴から入れる（`fillAddedAtFromHistory()`。管理者がエディタから実行する。何度実行してもよい）：`リクエスト` は差分追跡の対象外で、行を足した日の記録がありません。
    そこで、追加日が空の行に、取り込み元にリクエストが書かれた日（リクエスト記入日）を入れます（`svcHistoryAddedAt_`）。`変更履歴_差分` のうち、その行のシート
    （`svcGroupRanker_` と同じ決め方）の「サービスのリクエスト」の列で、変更後が今の文（全角・半角と空白の違いは無視）の記録を探し、いちばん新しい記録の日を使います。
    記録のセルの行番号は行の追加・削除でずれるので、同じシートの複数の行に同じ文のリクエストがあると、どの行の記録か決められません。
    そのような行には入れず、記録が無い行（差分追跡を始める前に書かれた）と合わせて行番号を知らせます。追加日が入っている行は変えません。
  - 1番から振り直す（`renumberRequestIds()`。管理者がエディタから実行する）：行をサブインダストリーの順に並べてから、
    リクエストのある行に上から SR-0001 と振り、これまでに振った最大の番号をその数にします（削除した番号も使い直す）。確認はロックを取る前です。
    - タスク管理の「サービス案」は ID の番号で結び付け直す（`svcRelinkTaskValues_`）ので、そのままだと別のリクエストに付いてしまいます。
      そのため、振り直すときに同じリクエストの新しい ID の候補の文に書き換えます（`svcRemapTaskIds_`。候補に無い値を拒否する入力規則で書けないので、
      先に列の入力規則を外し、`svcLinkTaskServiceColumn_` で付け直す）。今は無いリクエスト（削除した）を指していた値は、先頭に
      `SVC_OPTIONS.orphanTaskPrefix`（「（削除済み）」）を付けて残します（番号で別のリクエストに付け直されないように。セルの右上が赤くなる）。
      ID の無い値（前の版のサービス案の名前）はそのままにし、`svcLinkTaskServiceColumn_` がサービス案の名前で結び付けます。
    - リクエストの無い行に残っている ID は消します（次に振る番号が、その番号から続かないように）。
    - RX Service Meeting の本番の記録（`smtgMeetings_`）があれば振り直しません。記録はリクエストの判断と最大の ID を番号で残しているので、
      振り直すと、次の会議の「前回以降の動き」（新規リクエスト・判断の変更）が正しく出なくなるためです。
- 行の並び（`svcArrangeRows_`。追加・まとめて取り込む・`renumberRequestIds()` のとき。ロックの中）：`リクエスト` の行を、サブインダストリーの順
  （読むシートの順＝`DIFF_RULES` の順）に並べます。行のサブインダストリーは、取り込み元にあるリクエストなら読んだシート、無いもの（手で書いた・取り込み元で書き換えた）は
  「サブインダストリー」の値がシートの名前（前の名前も）か、そのシートのリクエストのサブインダストリーと同じシートです（`svcGroupRanker_`。どれでもなければ最後）。
  - 同じサブインダストリーの中は今の並びのまま動かさないので、最後の行の下に足した行（スクリプトが足した行も、手で足した行も）は、そのサブインダストリーの行の最後に入ります。
    リクエストの無い行（判断だけの行・空の行）は、いちばん下にまとめます（消さない）。
  - 並べるのは見出しの下から、リクエストの列のどれかに値のある最後の行までです。行ごと（ほかの列・書式・メモも）動かします。
    右端に一時の列を足して順番を書き、その列で並べ替えて（`Range.sort`）から列を消します。並びが変わらなければ何も書きません。
  - 追加・取り込みで並べ替えられなかったとき（フィルタ・結合したセルなど）は止めずに、足した行を最後の行の下に残して知らせます（`svcArrangeRowsSafely_`）。
    `renumberRequestIds()` では、並べ替えられなければ振り直しません。
  - パネルを開いたとき・`setupRequestSheet()` のときは並べ替えません（開いただけで行が動かないように）。
- 新FMT に合わせる（`svcSync_`。パネルを開いたとき・`setupRequestSheet()` のとき。ロックの中）：登録した行だけを合わせます（行は足さない）。
  取り込み元から書く列のうち、リクエストを見分ける列（得意先・案件名・リクエスト）のほか（サブインダストリー・営業の4列）を、
  新FMT の同じリクエストの値にそろえます（変わった行の範囲だけを列ごとに1回で書く。全角・半角と空白だけの違いなら変えない）。
  新FMT が正なので、`リクエスト` でこれらの列を手で直しても、パネルを開くと新FMT の値に戻ります。
  新FMT に無い行（リクエスト・得意先・案件名が書き換わった・消えた）は消さず、メモも付けません
  （セルのメモは人が書くものとし、スクリプトは付けない。行番号は `diagnoseRequestSources()` で確かめる）。
  前の版で `リクエスト` のセルに付けたメモ（`legacyNotes` で始まるもの）は外します（利用者が書いたメモは変えない）。
  書き換わったリクエストは、新しいリクエストとしてパネルに出ます。パネルを開いたときにロックが取れなければ（5秒）、合わせずに一覧だけを出します。
- 文字列は先頭に `'` を付けて書きます（`credText_`）。書き込みはロックの中で行います（`taskWithLock_`）。
  このロックはドキュメントロックではなくスクリプトロックです。サービス管理・タスク管理はサービスリクエスト・タスク管理のシート（差分追跡の対象外）
  だけに書き、取り込み元は読むだけなので、差分追跡・クレデンシャル履歴などと同じシートに同時に書くことはありません。
  ドキュメントロックを使っていたときは、取り込み元の編集のたびに動く差分追跡（ロックを60秒まで待つ）や取りこぼしの回収の後ろに並ばされ、
  選択パネルの「追加」が20秒待ちきれずに「他の処理が実行中です」で止まることがありました。サービス管理・タスク管理の処理どうしは、このロックで1つずつ動きます。
  ロックを取っている間は、スクリプトのキャッシュに処理の名前・実行した人・時刻を残し（`TASK_OPTIONS.lockHolderKey`）、待ちきれなかった人のエラーに出します。
  パネルとモーダルは「他の処理が実行中です」のとき、1.5秒おいて2回まで自動でやり直します。`diagnoseServiceLock()` で、ロックの種類と今の使われ方を確かめられます。
- 前の版の見出し（`サービス`）は、見出しの用意（`taskEnsureHeader_` の `aliases`）で `サービス案` に書き換えます。
  前の版で全件を自動で取り込んだ行は「登録した行」として残るので、`removeUntouchedRequests()` で手を付けていない行（判断が未判断か空で、フィードバック・サービス案・主管本部・担当者が空）を
  確認してから削除できます（続いている行はまとめて `deleteRows`。データの行をすべて消すときは、先に空の行を1つ足す）。削除したリクエストはまたパネルに出ます。
- `diagnoseRequestSources()`（読むだけ）：シートごとに、リクエストのある行の数と、パネルに出ないもの（登録済み・ほかの行やシートと同じリクエスト）の数を出します。
  読むシートをすべて読めたときは、`リクエスト` で新FMT に見つからない行の行番号も出します。

### タスク管理（`TaskManagement.gs`）

シート `タスク管理` の1行が1件のタスクで、サービス案ごとの検討の進捗を管理します。
列は `サービス案`・`タスク`・`本部`・`担当者`・`状況`・`メモ` で、今は手で行を追加します（自動で行を作る処理は無い）。`期限` の列は 2026/10 にやめました。
`本部` は担当者とセットで入れる本部名です（前からあるシートには、`タスク` のすぐ右＝担当者の左に差し込む）。

- タスクは、`リクエスト` に登録したリクエストを ID とリクエストで選んで対応付けます（`サービス案` の列。「SR-0001 会員の購買分析をしたい」の形）。
  ID とリクエストは1対1なので、タスクは1件のリクエスト（とそのサービス案）に付きます。案件には対応付けません（案件はリクエストからたどれる）。
  前の版はサービス案の名前を選んでいました（ID で選ぶので、サービス案の名前を変えてもタスク管理は直さなくてよい）。
- 候補は、スクリプトが非表示のシート `__TASK_CHOICES`（`SVC_OPTIONS.taskChoiceSheet`）の A 列に、ID の順に書きます（`svcTaskChoices_`・`svcWriteTaskChoices_`）。
  リクエストは改行・続いた空白を1つの空白にし、`taskChoiceLength`（40文字）より長いものは「…」で切ります。行は候補の数だけにし、使わない列・行は持たせません。
  `サービス案` の入力規則は、この候補の範囲を参照し、候補に無い値は入力できないようにします（`svcServiceRule_`）。
  一覧から作るプルダウン（`requireValueInList`）は項目の数に上限がある（500件）ので、範囲の参照にしています。数式で候補を作らないのは、テストで確かめられず、ID で合わせ直す処理もスクリプトに要るためです。
- 候補は、選択パネルを開いたとき・追加・削除のとき・`setupRequestSheet()`・`setupTaskSheet()` のとき（すべてロックの中）に合わせます（`svcLinkTaskServiceColumn_`）。
  合わせられなかったとき（保護で書けない・前の版の関数が残っているなど）は黙らずに、パネルの読み込み（`getRequestPickerData()` の `warning`）・追加・削除の結果（`warning`）で知らせ、
  パネル・モーダルに赤で出します（追加・削除そのものは済ませる。ほかの処理が実行中でロックを取れないときは知らせない）。
  原因は `diagnoseTaskChoices()`（読むだけ）で、コードの版（関数の中身に今の版の処理があるか。同じ名前の関数が別のファイルに残っていると前の版が動く）・
  候補のシートと今のリクエストの違い・プルダウンの参照先・最後に合わせた時刻・シートの保護を確かめられます。
  - 候補が変わったら書き直し、候補の行数・タスク管理の列や行数が変わったら、`サービス案` の全行の入力規則を付け直します（参照する範囲は付けたときの範囲で決まるため）。
  - 入力済みのタスクのうち候補に無い値は、同じ ID の候補（リクエストを書き換えたなど）に、前の版の値（サービス案の名前）はそのサービス案のリクエストが1件だけならそのリクエストに書き換えます（`svcRelinkTaskValues_`）。
    決まらないもの（同じ名前のリクエストが複数ある・リクエストを削除した）は残し、件数を知らせます（セルの右上が赤くなるので、選び直してもらう）。
    書き換えるセルだけに書きます（候補に無い値のままのセルに書くと、入力規則で止まるため）。
  - 毎回すべてを確かめると読み込みが遅くなった（行ごとの問い合わせで1,000行で数十秒）ため、確かめた記録（候補の要約・候補のシート・列・行数・時刻。`SVC_OPTIONS.taskLinkKey`）を残し、
    どれも変わらなければ `taskLinkCheckMinutes`（30分）に1回だけ確かめます。確かめるときも入力規則は1回で読み、全行の種類と、先頭・真ん中・最後の行の参照するシートだけを見ます。
  - 候補のシートを作るとき、`insertSheet` は作ったシートを開くので、開いていたシートに戻します。
- タスク管理シートの編集で動く処理はありません（単純トリガーの `onEdit` は置いていない）。
- `setupTaskSheet()` はシートが無ければ作り、見出しが空なら書きます。見出しがあるシートは書き換えず、足りない列だけを右端に足します（`taskEnsureHeader_`。リクエスト シートでも同じ）。
  全行（最後の行まで）に、サービス案・状況（一覧）の入力規則を付けます。
- 前の版（案件の連動プルダウン `サブインダストリー`・`得意先`・`案件名` の列がある）のシートは、`ui.alert` で確認してからその列を削除し（`taskDeleteColumns_`）、
  `サービス案` の列を左端に動かします（`moveColumns`）。ほかの列の値は残ります。確認はロックを取る前に行います（答えるまでほかの処理を待たせないため）。
  使わなくなった `期限` の列も同じく確認してから削除します（`TASK_OPTIONS.removedColumns`。案件の列ではないので、サービス案は動かさない）。
  画面に出せないとき（エディタだけで実行）は聞けないので、列は残します（`diffUiOrNull_`）。

### 会議サマリ（`MeetingSummary.gs`）

RX Business Meeting（パイプライン会議）の **事前資料**（16:9 の Google スライドと PDF）を、サブインダストリー（追跡シート）ごとに作ります。

- 会議の形：月1回（第一週の金曜 9:00〜10:30）。サブインダストリーごとに報告4分＋フィードバック3分。目的は、案件の進捗・受注見込みを確かめ、
  優先順位と次のアクションを決めること。資料は会議の2日前に PDF で配り（入力の締切は3日前）、参加者（営業の統括・リーダー、BX、サブインダストリーのリーダー）が通読してから会議に臨みます。
- **資料には、シートと変更の記録から分かる事実だけを書きます。** 論点・決めてほしいこと・支援の要否・深掘りする案件などの判断は、各サブインダストリーのリーダーが
  会議で話すことです。資料が判断を先に書くと、読み手を誤った方向に導くおそれがあるため入れません（前の版にあった「本日の論点」「決めてほしいこと」「決めること」・
  結論の帯・★・赤枠の強調はやめました）。
- 見出し（タイトル）はどのシートでも同じ（`MTG_TITLES`）にし、同じ位置に同じ情報が来るようにします。シートごとの状態は、見出しの下のリード文に事実として書きます。
- 使う言葉の意味は下の「数え方」で決め、資料の中ではその意味でだけ使います（資料に用語の定義・ステータスの分類のページは置かない。2026/10 に不要とした）。
  判断や評価を含む言葉（「悪い動き」「重点」「要対応」「打開」など）は使いません。
- 「動いた・止まった・入力に漏れのある案件」のふるい分けに絞り、個別の案件を深く見るのは、シートや履歴サイドバー・変更履歴で行います。
  文はすべてシートと変更の記録から作ります（記入欄は置かない。2026/10 から Google スライドは残さない（`keepSlides: false`）。書き足す運用にするときは `true` にし、配る前に Google スライドに書き足して PDF を書き出し直す）。

- 管理者がエディタで `createBusinessMtgSummaries()`（試すときは `previewBusinessMtgSummaries()`）を実行し、`ui.prompt` で作るシート（空欄ならすべて）と今回の会議日（`10/23`・`2026/10/23`）を入力します。
  会議の前に作る人が決まっていて、利用者向けのメニューは2項目に絞っているため、メニューには置きません。
- 「前回から」の基準は **前回の会議**：シートごとに、会議日と資料を作った日時をドキュメントのプロパティ `MTG_MEETINGS_<シート名>`（`[{date, cutoff}]`）に残し、
  今回の会議日より前でいちばん新しい会議の `cutoff` より後の変化を出します（`cutoff` ちょうどの記録は前回の資料に入っているので数えない）。
  同じ会議日で作り直したら `cutoff` を上書きします（基準は変わらない）。記録が無ければ、前の版の `MTG_LAST_<シート名>`、それも無ければ `MTG_OPTIONS.firstDays`（14日）前から。
  `previewBusinessMtgSummaries()` は会議日を記録しないので、試作を何度作っても本番の「前回から」は変わりません（ファイル名に「試作」）。
- **時点コピー**（`mtgSaveCopy_`・`mtgOpenCopy_`。2026/10/17 に「会議時点のコピー」から名前を改めた）：本番の資料を作ったとき（資料を作れたあと）と基準を記録したときに、
  選んだ追跡シートの値を別のスプレッドシート「時点コピー_yyyy-MM-dd HH:mm（資料作成時・会議日 yyyy-MM-dd）」（基準は「（基準）」。日時は実行日時。
  （）は `mtgCopyNote_`・`MTG_OPTIONS.copyKinds`）に保存し、会議の記録に `copy: {id, sheet}` を足します。保存先は会議サマリのフォルダの中の「時点コピー」
  フォルダ（ID は `MTG_COPY_FOLDER_ID`。前の版で作った「会議時点のコピー」フォルダも、ID があればそのまま使う）。
  **日次**（`installDailySheetCopy()`・`saveDailySheetCopy`）：時間主導のトリガー（毎日 `dailyCopy.hour` 時台。`mtgInstallDailyCopyTrigger_` で1つだけ）で、
  すべての追跡シートを「（日次）」で保存し、`dailyCopy.keepDays` 日より古い日次のコピーをゴミ箱に移します（タイトルで見分け、資料作成時・基準は消さない）。
  会議の記録には足しません（比べる時点の候補にだけ出る）。ファイルのコピーだけなのでロックは取りません。
  中身は**スプレッドシート全体**のコピーです（`DriveApp.getFileById(ss.getId()).makeCopy(title, folder)`。すべてのシート・数式・書式・入力規則。1回の Drive の
  呼び出しなので、値を1セルずつ写すより速い）。比べるときは、コピーの追跡シートの値を読みます（追跡シートの数式は同じファイルの定義_ステータスだけを参照するので、
  コピーでも保存した時点の値のまま。IMPORTRANGE は得意先マスタだけで、比較には使わない）。前の版のコピー（追跡シートの値だけ。そのとき選んだシートだけ）も
  そのまま読めます（`mtgResolvePoint_` はコピーを開いてシートを確かめ、無いシートは `noCopy`）。試作は保存しません。古いコピーは消しません（会議日を取り消しても残る）。
  - **前回からの変化は、前回（今回より前の会議・基準）のコピーと今のシートを比べて出します**。差分追跡は止まっていた間・2,000セルを超える貼り付け・
    ほかのスクリプトの書き込み・数式の結果の変化を記録できないので、記録から前回の値を組み立てると抜けるため。
    行は得意先＋案件名で突き合わせ、得意先・案件名を書き換えた案件は変更の記録（`mtgHistory_` の `root`）で前の名前とつなげます。
    コピーに無い案件は新規、今のシートに無い案件は削除、両方にある案件は追跡範囲（`DIFF_RULES` の `ranges`。最終更新日時は除く）の表示の値を比べ、
    違う列が「更新項目」、ステータス・期待値・受注月・活動状況の前回の値はコピーの値です（値が戻っていれば変化なし）。
  - 変更の記録は、名前の書き換えのつなぎ・停滞の日数・受注月の延期の回数（前回より前にさかのぼる数字）にだけ使います。
    コピーでは変わっているのに前回より後の変更の記録が無い案件は `unlogged` に数え、Appendix ① のリード文と終わりの画面に出します（差分追跡が止まっていたことに気づけるように）。
  - コピーが無い（初回・前の版で作った会議）・開けないときは、前の版と同じく変更の記録から出します（開けないときは、終わりの画面と Appendix ① に書く）。
  - スプレッドシートを作る・開く（`SpreadsheetApp.create`・`openById`）ため、権限（スプレッドシートすべて）の承認がもう一度いります。
- **本番の確かめ**（`mtgConfirmFinal_`）：本番は会議日を記録する前に、会議日（曜日）・シートごとの対象期間（前回の会議の資料作成時・基準・直近14日間のどれからか）・
  同じ会議日の資料を作成済みならその日時を出し、「はい」のときだけ作ります。記録した `cutoff` が次の会議の起点になるので、配ったあとに作り直すと、
  配った版と作り直した時の間の変化がどの資料にも出なくなります（画面と `docs/OPERATIONS.md` で「配布後は作り直さない」と知らせる）。
- **会議日の取り消し**（`removeBusinessMtgRecord()`。エディタから実行）：シートと会議日を聞き、その会議日の記録（基準以外）を消します。会議日の打ち間違い・会議が無くなったとき用。
  資料のファイルは消しません。
- **古い版の片付け**（`mtgTrashOld_`）：作ったあと、保存先のフォルダの同じ名前のファイル（作り直す前の Google スライドと PDF）をゴミ箱に移します（古い版を配らないように）。
  ファイル名に会議日（試作は「試作」も）が入るので、ほかの会議日・本番と試作の資料は消しません。終わりの画面にはシートごとの PDF の URL を出します。
- **サブインダストリーごとの Google チャットへの通知**（webhook。2026/10/19 に足した）：`setBusinessMtgSubChats()` でシートごとの webhook を
  スクリプトのプロパティ（`MTG_OPTIONS.subChat.webhookKeyPrefix` ＋ シート名）に残し、独立した2つの関数で送る（どちらも確かめてから送る。`mtgSubChatSend_`）。
  `remindBusinessMtgUpdate()`：管理フォーマットの更新のお願い（`subChat.remind`。締め切りは会議日の `deadlineDays` 日前の `deadlineTime`、
  今の入力状況は `mtgUpdateStats_`（読むだけ：進行中・必須項目が未入力・受注月超過・最終更新から `noUpdateDays` 日以上）、シートのリンクは `#gid=`）。
  `notifySubBusinessMtgSummaries()`：その会議日の本番の PDF（`mtgStoredPdf_`）のリンク（`subChat.summary`）。PDF が無いシートには送らない。
  会議日は聞く（空欄なら会議日程の一覧の今日以降でいちばん近い会議。`mtgSubChatMeeting_`）。送れないスペースがあってもほかは送る（`mtgSubChatPost_`）。
- 全体のスペースへの通知（`setBusinessMtgChat()`・`notifyBusinessMtgSummaries()`。格納先のフォルダの新しい PDF を送っていた）は 2026/10/19 にやめた
  （通知はサブインダストリーごとの2つだけ）。前の版の設定（`MTG_OPTIONS.chat.oldKeys`）と自動通知のトリガー（`mtgNotifyScheduled`。関数は名前だけ残す）は
  `setBusinessMtgSubChats()` で消す（`mtgRemoveLegacyTrigger_`）。会議の時刻の決まり（`chat.meetingTime`）と、会議日程の読み方（`mtgChatSchedule_`）は共通で使う。
  - 送るのは `UrlFetchApp`（`application/json` の `{text}`）。429・5xx は2秒待って1回だけやり直し、だめならエラーにします。
    webhook の URL は鍵を含むので、コード・画面・ログに出しません（`mtgChatSpace_` はスペースの ID だけを出す）。
- **画面**：入力・確かめの画面は `mtgUi_()`（`SpreadsheetApp.getUi()`）でスプレッドシートに出します。エディタがスプレッドシートにつながっていないと
  `getUi()` が止まるので、どうすればよいか（スプレッドシートの「拡張機能」→「Apps Script」から開いたエディタで実行する）を書いて止めます。
  `setBusinessMtgBaseline()` だけは、画面に出せなければ確かめずにすべての追跡シートに記録し、実行ログに書きます（`mtgUiOrNull_()`。聞くことがシートの選択と確かめだけのため）。
- **ファイル名**（`mtgFileName_`）：`MTG_OPTIONS.fileName` の `{date}`（会議日の yyyyMMdd）・`{name}`（シート名）を置き換える
  （`20261023_スーパー・GMS_RX Business Meeting用資料`。試作は末尾に `_試作`）。
- **会議のフォルダへの格納**（`mtgStoreToMeetingFolder_`・`mtgMeetingFolder_`）：本番だけ、資料を作って会議日を記録したあとに、
  事前資料の格納先（全サブインダストリー共通の1つのフォルダ。スクリプトのプロパティ `MTG_MEETING_FOLDER` → `MTG_OPTIONS.meetingFolder`。`mtgMeetingFolderSetting_`）の中から、
  名前が会議日の `meetingFolderDate`（yyMMdd）で始まり、すぐあとが数字でないフォルダを探し、PDF を移します（`moveTo`。保存先と二重にしないため。同じ名前の古い版はゴミ箱へ）。
  見つからない・2つ以上ある・開けない・書き込めないときは止めずに、理由を終わりの画面に出します（資料は保存先にある）。
  あとから `storeBusinessMtgSummaries()`（エディタから実行。シートと会議日を聞く）で、保存先の本番の PDF を同じように格納します。
  会議のフォルダが無ければ作ります（`createMeetingFolder`。名前は `meetingFolderName` の `{date}_{meeting}_第{n}回`（`261023_RX Business Meeting_第5回`）。
  `{n}` は、そのフォルダの中の、この会議日より前の同じ会議のフォルダの「第N回」のいちばん大きい N ＋ 1（`mtgNextMeetingNumber_`。全角の数字も読む。後の会議日のフォルダは数えない））。
  作り直したときは、作ったフォルダが見つかるので、もう1つは作りません。
  会議のフォルダは、名前に含む会議の名前（RX Business Meeting・RX Service Meeting）で見分けます（`mtgFolderIsMeeting_`）。格納先の中に両方の会議のフォルダが並び、
  第N回は会議ごとに数えます。会議の名前を含まない前の版のフォルダ（`261023_第5回会議`）は、RX Business Meeting のフォルダとして使い続けます（2026/10/17 から）。
  前の会議の名前（RX Business MTG・RX Service MTG。`formerMeetingNames`）のフォルダも、同じ会議のフォルダとして見分けます。インデックスの会議名も、前の名前の行（`index.formerKinds`）を
  同じ会議の行として使い、書くときに今の名前に書き換えます。
- **統合版**（`createBusinessMtgCombinedSummary()`・`mtgCombinedRun_`・`mtgCombinedSlides_`。`MTG_OPTIONS.combined`）：すべてのサブインダストリーの資料を作ったあとに、
  別の関数で、全サブインダストリーの資料を1つにまとめた資料を作ります（`{date}_全サブインダストリー_RX Business Meeting用資料`。試作なら試作）。
  資料を作る関数（`createBusinessMtgSummaries()`）とは分けます：11シートの資料と格納で、1回の実行の6分の上限に近いため（2026/10/17 に統合版を続けて作る版でタイムアウトした）。

  各サブインダストリーの表紙のページ。名前とページ番号はそのページへのリンク。ブラウザの Google ドライブのプレビュー画面では PDF の中のページへのリンクは
  動かないので、リード文の補足にそう書く（直接開く URL（`uc?export=view`）はダウンロードになり、個別の PDF へのリンクも使わないことにした）。9件以上なら2列）→「全サブインダストリーの状況」（`mtgOverviewSlide_`）→
  計画に対する積み上げ（全体の `mtgPlanSlide_` とサブインダストリー別の `mtgPlanBySubSlide_`。`plan.enabled` のとき）→ 各サブインダストリーの資料（`mtgSlides_(summary, start, {appendix: false})`。表紙と本編だけで、扉と Appendix ①〜③ は入れない（2026/10/19 から。
  全件の一覧は各サブインダストリーの資料にある。本編の「全件は Appendix ① を参照」は「各サブインダストリーの資料の Appendix ①」と書く）。`DIFF_RULES` の順）。
  ページ番号は資料全体の通し番号です
  （`mtgSlides_(summary, start)`・`mtgNumberSlides_(frame, slides, offset)`）。各資料の出典の行はそのサブインダストリーの名前のままです。
  「全サブインダストリーの状況」は、サブインダストリーごとの進行中案件・期待値合計・増減・変化のある案件・停滞・確認事項（各資料のサマリーと同じ数え方）と、
  その資料の表紙のページの表で、いちばん下に合計を置きます。増減の列の見出しは、いちばん多い比べ方（前回比・10/17比（基準）・直近14日間の増減）で、
  ほかの比べ方のシートはセルの1行目に何との比かを書きます。作れない値は灰色の「データなし」、合計は作れたシートの分だけで ※ を付け、意味を出典の行の後ろに書きます
  （どのシートも作れなければ合計も「データなし」）。リード文は1行（11サブインダストリーと合計を1ページに入れるため。入らなければ表の字を 7pt まで小さくする）。
  本番は、各サブインダストリーの資料と同じ会議のフォルダ（事前資料の格納先の中の `yyMMdd_RX Business Meeting_第N回`。`mtgMeetingFolder_`）に格納し、
  インデックスの「全サブインダストリー」の列に書きます。`createBusinessMtgCombinedSummary()` は会議日を聞き、すべてのシートの会議サマリを今の値で作り直してまとめ
  （`mtgSummaries_`。会議日・時点コピーは記録しない）、本番として作ります。実行の条件は、すべてのシートにその会議日の本番の記録と PDF（会議のフォルダか保存先。`mtgStoredPdf_`）があること
  （インデックスのその会議日の行に空のセルが無いこと）で、満たさなければ足りないサブインダストリーを知らせて、何も作らずに終えます（試作も作らない）。
  資料を区切って作っている途中（下の「6分の上限」）なら止めます。`createBusinessMtgSummaries()` は本番なら、終わりの画面に、この会議日の本番の資料（記録と PDF）が
  まだできていないサブインダストリーを出し（`mtgMeetingPending_`。サブインダストリーごとに作ってもよい）、すべてそろったらこの関数を案内します。
  - **統合版も区切って続ける**（`mtgCombinedStart_` → `mtgCombinedRun_`。2026/11/05）：11シートを読んで80ページを超える資料にすると、1回の実行の6分に入らない
    （Sheets API で読んでも1シート 30〜160秒、スライドは1シートの資料で約67秒）。個別の資料と同じ仕事の置き場（`MTG_JOB`・`MTG_JOB_ITEM_n`）とトリガー
    （`continueBusinessMtgSummaries`。`job.kind: 'combined'` なら `mtgCombinedRun_` で続ける）を使う。順に、①資料（Google スライド）を始める（`mtgDeckStart_`）→
    ② 3シートずつ読んで中身を作り、資料ごとにスライドを足す（`mtgDeckAdd_`。スライドの番号（`job.page`）は、前のページの数（`mtgCombinedFrontCount_`：5。計画を出さなければ 3）から数える。
    見積もりは `summaryMs`・`deckMs`）→ ③ 前のページ（表紙・目次・状況・計画。`mtgCombinedFront_`）を番号 0 から足し、仕上げる（`mtgDeckFinish_`：ひな形の元のページと
    レイアウトの枠を消し、目次のリンクを付け、番号の順に並べ（`updateSlidesPosition`）、背景の画像を付けて PDF に。`mtgDeckSave_`）→ 会議のフォルダとインデックス

  （変更のあとの行の表示値。期待値など数式の列も、その時点の計算した値）から取ります（その後 `since` まで変更が無いので、`since` の時点の値そのもの）。
  前回より前の記録が無ければ、前回以降で最初の変更の「変更前」（その項目の変更が無ければ今の値）。期待値の列が数式（最初の行に数式。

  変わっていれば、シートの数式と同じく前回の想定売上 × 前回のステータスの率（`MTG_OPTIONS.statusTable`）で求めます。推定では補いません。
  変更の記録は `変更時点スナップショット`（イベントID＋行番号）の得意先＋案件名で案件に結び付けます。
  得意先・案件名を書き換えた記録・空の行に入れた記録は、前の名前（キー）を今の名前につなげます（あとから案件名を入れた案件・名前を直した案件も1つの案件になる）。
  空の行に得意先か案件名を入れた記録・`行追加` は「案件ができた」記録です。スナップショットの無い記録は数えず、件数を Appendix ① に書きます。サンプル（`SMP-`）・クレデンシャルの記録（`CRD-`）は数えません。

  ステータスの進み具合で比べる。`定義_ステータス` があれば期待値の率の大きい順、率が同じなら定義の下の行ほど進んでいる
  （A-受注済み(100%) > B-クロージング中(70%) > C-稟議対応中 > C-選定対応中 > C-提案中(50%) > D-課題整理中 > D-ヒアリング中(20%) > 創注-仮検討(10%)。
  プルダウンは A から並ぶので、プルダウンの順では比べない）。定義のシートが無ければプルダウンの順（下ほど進んでいる）。`mtgStatusRank_`）> 延期 > 前倒し（受注月）> 増額 > 減額（期待値）> 変更（プルダウンに無い値どうし）> 活動更新（活動状況の前回の値と今の値が違う）> その他更新（ほかの項目だけ）。
  行を削除した案件は「削除」で、失注には数えません
  （`行削除` の「変更前」を、シートの見出しで区切って読む。見出し・値に改行があるため）。前回より後に足して消した行は出しません（区分の決め方は資料には書かない）。
  資料に並べる順は `MTG_MOVE_ORDER`（受注 → 失注・保留・後退・削除 → 新規・前進・復帰 → 活動更新 → 延期・前倒し・増額・減額・変更）で、
  サマリーの動きの表の行・本編の「前回から変化のある案件」・Appendix ① のどれも同じ順です。「変化のある案件」はその他更新を除く件数で、その他更新は「ほかに、その他の項目のみの更新 N件」と件数だけ書きます。
- **期待値の増減**（`mtgBridge_`）：前回の時点で失注でなかった案件の期待値（前回の値）から今の失注でない案件の期待値までを、案件ごとに 新規・期待値増・復帰・期待値減・失注・削除 に分けます
  （`MTG_BRIDGE`。2026/11/05 から対象は失注を除くすべての案件で、受注・保留になっても外れない（前の版は進行中だけで、受注・保留の内訳と白抜きの受注の棒があった））。
  対象から外れた案件は前回の期待値の分だけ減らすので、「前回 + 内訳の合計 = 今回」が必ず成り立ちます。期待値が空の案件は合計に含めず（0 と同じ扱い）、件数をリード文に書きます。
  件数（`startCount`・`endCount`）・想定売上（`amountStart`・`amountEnd`）も同じ対象で数え、サマリーの数字に使います。

  （`変更履歴_差分` の最初の行と `lookbackDays`（180日）前の新しいほう）と最終更新日時の古いほうから「N日以上」。行の更新ではなくステータスで見るのは、活動状況だけ書き足してステータスが同じ案件も拾うためです。

  サマリーではその案件だけ名前を出します（活動のある停滞案件と、何も動いていない停滞案件を分ける）。

  まだ数えられない（M/d から数える）」と書きます（0件を「停滞なし」と読ませない。件数・想定売上は「—」）。

  （`mtgFlagTexts_`。判断の言葉は付けない。単語のラベルだけでは入力した人に判定の中身が分からないため、2026/10/19 に文にした）。

  差分追跡は記録の仕組みなので、資料に出さない列も記録します（記録は書き換えない決まりのため、資料の側で除く）。
- **RXシナリオ構成別の期待値**（`createBusinessMtgScenarioSummary()`。構成が未確定のあいだは事前資料とは別の試作の資料）：I列（2026/10/26 から。見出しはシートによって「RXシナリオ構成」か「RXシナリオ構成（サービス）」で、`columnAliases` でどちらも読む）はプルダウンの複数選択（「A, B」）なので、
  1つの案件が複数のシナリオに入ります。満額で数えると合計が期待値合計を超えて構成比・計画との比較に使えないため、主の数字は**按分**
  （期待値 ÷ 選んだ数を各シナリオに配る。合計が期待値合計と一致する。`mtgScenarioTotals_` の `share`）にし、**関与**（含む案件の期待値をそのまま合計。重複あり。`full`）・
  件数・**うち単独**（そのシナリオだけを選んだ案件）を並べます。どちらかだけでは「主力のシナリオか（按分）」「多くの案件に乗る横断的なシナリオか（関与と按分の差）」が読めないためです。

  選択肢外のステータス・デリバリー担当なし（前回から受注で デリバリー担当 が空。新FMT にはこの列が無いので `columns.delivery` は空にしてあり、
  このときは種類ごと出さない（責任者別の表の列・「データなし」にも出さない）。列を作ったら見出しを書けば出る）。シートに列が無いなどでチェックできない種類は、
  Appendix ③ の責任者別の表で灰色の列にし、表の下に理由を書きます（下の「作れないところ」）。
  会議の前に入力を直してもらうためのもので、Appendix に置きます。種類の説明は置かず、案件ごとの一覧の「内容」に、何が当てはまったかを書きます。
  資料では「入力内容の確認事項」と書き、種類は `MTG_ALERT_LABELS` の名前で出します（未入力 → 必須項目未入力、資料なし → 商談記録未登録、更新なし → 長期未更新、

  数は「項目」（1つの案件に2つ当てはまれば2項目）で数え、当てはまる案件の数（`kpi.alertDeals`）・責任者の人数を添えます（「3項目（2案件・責任者 2名）」）。
- **受注月別の期待値**（`mtgQuarters_`）：進行中の案件を 受注月超過（受注月が今月より前）・今の四半期〜4Q（今期 = `fiscalStartMonth`（4月）から12か月。過ぎた四半期は出さない）・
  来期以降・受注月未入力 に分けます（受注月超過・来期以降・未入力は当てはまる案件があるときだけ）。受注月を過ぎた案件を過ぎた四半期に入れると、
  まだ受注できる見込みのように読めるため分けました。「受注月が今期の期待値」は今の四半期〜4Q の合計で、受注月超過の分は別に書きます。
  前の版にあった今期の帯（今期の受注・着地見込み・目標の達成率）は、前回からの変化を見る資料には要らないため置きません。
- 記録は追記なので、下から `logChunkRows` 行ずつ、読む期間（前回と `lookbackDays` 日前の古いほう）より前に届いたら止めます。サンプル・ダミーの記録は過去の日時で足されるので、止める判断には使いません。
- **確認用のダミーデータ**（`サンプルデータ.gs` の `addBusinessMtgDummyHistory()`）：資料の形を確かめるために、追跡シートの案件へダミーの変更の記録（イベントIDが `DMY-`）を足します。
  シートのセルの値は変えず、今の値になるまでの記録を足します：前回（会議の資料・基準の時刻。無ければ `firstDays` 日前）の1秒前に「前回の値」の行のスナップショット
  （前回より後の本物の変更があれば、その変更前の値を使い、本物の変化を隠さない）、前回より後に「前回の値 → 今の値」の記録（今の行のスナップショット）。

  停滞（ステータスを100日・70日前に変えた記録。本物のステータスの変更・案件ができた記録がある案件は、それより前の日付にしても停滞にならないので付けない）・

#### スライドの構成

見出しは固定（`MTG_TITLES`）、リード文は状態を事実として書きます（1つ目の文と、改行のあとの補足は行を分ける。大きさ・色（黒）はどのページも同じ）。

**言葉づかい**：配布するビジネス文書として、書き言葉（体言止め・「〜である」の調子）で書きます。話し言葉（「変わった」「増えた分」「当てはまったのは」「〜が空」）は使わず、
「変化のある」「増加・減少」「確認事項」「未入力」のように書きます。人数は「名」、参照先は「Appendix ① を参照」。該当が無いときは「〜なし」。

**空欄と推定**：資料には、シートと変更の記録にある値だけを書き、推定で補いません。
- 空欄は「未入力」と書きます（`MTG_OPTIONS.blankText`。「—」や 0 で済ませない）。得意先・案件名が空なら「（得意先未入力）」「（案件名未入力）」、
  ステータスの動きで前回に無かった案件は「（新規） ▶ …」、削除した案件の金額は「3 ▶ （削除）」。
- 該当する案件が無いときは「該当なし」（`MTG_OPTIONS.noneText`）。案件の金額が無いもの（得意先の予定）は「—」（対象外）と、2行目に「（得意先の予定）」。
- 空欄の金額は合計に含めず、含めていない件数を書きます（サマリーのリード文の補足「想定売上未入力 N件・期待値未入力 N件は、金額の合計に含めていない。」、
  パイプラインの変化「期待値未入力の N件は金額に含めていない」、Appendix ②「想定売上未入力の N件を除く」）。ステータスが空の案件は進行中に数え、そのことを書きます
  （「ステータス未入力の N件は進行中に含めている。」。`mtgBlankNote_`）。
- 金額の前回比べは、空と 0 を別の値にします（空 → 10 は「未入力 ▶ 10」）。
- 記録で分かる範囲だけを書きます：ステータスが変わった記録が無い案件の日数は「N日以上」（記録を読んだ期間の始まりからの日数。それより前は分からない）、
  記録の始まり・基準から45日たたない間は停滞を「まだ数えられない」、日数の記録が無ければ「記録なし」。

**作れないところ（データなし）**：シートに列が無い・変更の記録が無いなどで、資料の部分を作れない（数えられない）ときも、資料の型（ページ・表・行・列）は変えず、
その場所に「データなし」（`MTG_OPTIONS.gapText`）と理由を書きます（何が足りないかが資料を見て分かるように）。`mtgGaps_` が summary に
`gaps`（部分 → 理由）と `alertGaps`（入力内容のチェックの種類 → 理由）を作り、各ページが使います。作り終えた画面とログにも一覧を出します（`mtgGapList_`。同じ理由はまとめる）。
- 見た目：灰色（`gap` `#F2F2F2`）の地に点線の枠（`gapLine` `#A6A6A6`）の箱で、「データなし」（太字）と理由（`mtgEmptyBox_`）。表のセルは灰色の地に「データなし」（`mtgGapCell_`。
  列が無い項目は `mtgFieldCell_`）。数えられない件数・金額は「—」（0 と書かない）。チェックできない種類の列は、見出しを灰色にして「—」。
  空欄（「未入力」）・該当する案件が無い（「該当なし」。白の地に細い線の箱）とは分けます。
- 部分と理由：
  | 部分（`gaps` のキー） | 理由の例 | 出すところ |
  |---|---|---|
  | `changes` 前回からの変化 | 「変更履歴_差分」シートに変更の記録が無い | サマリーのリード文・前回比（「前回比 データなし」）・動きの表（見出しに理由、行は「データなし」）、パイプラインの変化の滝の図、前回から変化のある案件、Appendix ① |
  | `amount`・`weighted` 想定売上・期待値 | シートに「想定売上規模（百万）」の列が無い | サマリーの数字の箱、滝の図・グラフ（期待値）、表のセル。期待値が無ければ、期待値上位は想定売上の大きい順（リード文に書く） |
  | `orderMonth` 受注月 | シートに「受注月」の列が無い | サマリーの受注月超過の行、受注月別のグラフ、表のセル |
  | `stalled` 停滞 | 基準（10/16）から 45日未満のため、まだ数えられない（11/30 から数える）／変更の記録も「最終更新日時」の列も無く、ステータスが同じ日数が分からない | サマリーの停滞の行（停滞案件が1件も無いとき）、Appendix ② |
  | `record` 商談記録 | シートに「商談記録（ＵＲＬ）」の列が無い | サマリーの商談記録未登録の行 |
  | `activity`・`issue`・`owner` | シートに「活動状況」の列が無い | 表のセル（活動更新の行も） |
- 入力内容のチェックの種類（`alertGaps`）：予定日超過（「クレデンシャル履歴_記録」シートが無い）・受注月超過・商談記録未登録・更新なし（最終更新日時の列も変更の記録も無い）・
  金額の不整合・月の不整合（売上開始月・受注月の列が無い）・選択肢外のステータス（ステータスの列にプルダウンが無い）・デリバリー担当なし（`columns.delivery` に見出しを書いたのに列が無い。空なら使わないので出さない）。

見出しは名詞で短く（「前回から変化のある案件」「期待値上位案件の状況・課題」「停滞案件」「入力内容の確認事項」）。表の見出しは「前回▶今回」「滞留日数」「該当事項」「更新項目」など。

表紙：いただいたひな形（URL をスクリプトのプロパティ `MTG_TEMPLATE_URL` に入れる。.pptx なら Google スライドに変換して使う（`mtgTemplateSlides_`）。2026/10/17 の版は3枚：1枚目 緑＝表紙（統合版の表紙も）、2枚目 グレー＝扉、3枚目 紫（使わない。`templatePages.combined` を 3 にすると統合版の表紙に使う））の

`2026年 4月 17日` → 会議日（曜日つき）、`XXXX` → 空）。
ひな形を登録していなければ、ひな形と同じ絵柄（グラデーションに大きな「RX」）の画像を背景にし、同じ位置に同じ文字を描きます

その下に、出典（データの時点）と対象期間を白い小さな字で足します（「出典：「スーパー・GMS」シートおよび変更履歴（2026/10/15 16:00 時点）」
「対象期間：前回会議（10/9）の資料作成時（10/8 16:00）以降」。初回は「直近14日間（10/1〜。初回のため）」）。

  左の列は狭く（150pt）、右の列（文章）を広くしています。右上に2行で「担当営業：（アカウント責任者）」「BX担当：（BX担当）」（見出しの半分の大きさで、2行の高さが見出しの行と同じ。灰色の字・右寄せ）。該当事項は出しません。
- 課題・活動状況・次回アクションは、枠の下の灰色の帯に前回の内容を出します（見出しは「前回（10/30 会議）」。前回の会議の資料と比べないときは「前回」）。
  前回は、前回からの変化と同じ時点の値です（時点コピー・変更時点スナップショット・変更の記録。`mtgChange_` の base の issue・activity・nextAction）。
  今回と同じなら、帯に「今回と同じ（前回から更新なし）」と書き、枠の右上に黄色の「更新なし」の印を付けます（停滞が分かるように）。
  前回に無かった案件は「新規の案件のため、前回はありません」。帯の字は `report.prevSize`（7pt）で、入らなければ「…」で切ります。
- 右の文章の枠の字の大きさは、スライドの中で同じにします：どの枠にも収まるいちばん大きい大きさ（`report.maxSize` 8pt（枠の緑の見出しと同じ）から 0.5pt ずつ `report.minSize` 6.5pt まで。`mtgReportFit_`）。
  どの枠も文を省略しません（「…」で切らない。シナリオのバッジも「ほか N件」にしない）。入らなければ字を小さくし（下限 `report.minSize` 4pt）、それでも入らなければ全文のまま。
  左の列の枠・前回の帯・右上の担当・出典の行・商談記録も同じ。空の項目は灰色の「未入力」。
  期待値の前回からの増減は、数字の右の色付きの字（増は青「+20」・減は赤「▲12」・同じは灰色「±0」。バッジにはしない。`colors.plus`・`minus`）。RXシナリオの枠は、1行目に見込金額、その下に番号のバッジ。
  印・バッジ（更新なし・シナリオの番号）は、確度の段と同じ平らな四角（角を丸めない・枠の線なし。`mtgReportBadge_`）。
  期待値の枠は、数字の行と「前回」の行を高さを決めた箱に分ける（行の送りの見積もりに頼ると、実際のスライドで重なることがある）。
- 「前回」は、会議サマリの前回からの変化と同じ時点（表紙の対象期間の始まり。時点コピーか変更の記録）の値です。変化が無い案件は今の値と同じ、前回に無かった案件は「（新規）」。
  左下の出典の行は、どのシートの何行目の値をいつ読んだかだけ（「出典：「スーパー・GMS」シート 12行目（2026/11/06 10:00 時点）」。`mtgReportSource_`。8pt。
  試作の印・前回の時点・金額の単位は書かない。ダミーの記録を使ったときだけ先頭に【ダミーデータを含む】）。右下（ページ番号の左）に「商談記録：格納先リンク」（`mtgFrame_` の `footRight`）。
  「格納先リンク」は商談記録のセルのリンクへのハイパーリンクです。リンクは、セル全体・一部の文字のリンク、スマートチップ、`=HYPERLINK("URL", …)`、文字の中の URL から読みます
  （`mtgCellLinks_`。Sheets API で読むときは `hyperlink`・`textFormatRuns`・`chipRuns`）。2つ以上なら「格納先リンク①　②」（3つまで）。リンクが無ければセルの文字のまま。
- 報告フラグの列は、追跡範囲（`DIFF_RULES` の `ranges`。D3:AF）の外（AG など）に置きます。範囲の中に置くと、チェックのたびに差分の記録が増え、会議サマリの「その他更新」にも出るためです。
  列は `addBusinessMtgReportFlagColumn()` で足します（`report.flagColumn` の AG。ドキュメントロックの中で書く）。チェックボックスは入力規則だけを付け、値（FALSE）は書きません
  （値を書くとシートの最後の行が下まで伸び、行を読む処理が空の行まで読むため）。AG列に値がある・追跡範囲の中・AF列まで無い（列を増やすと追跡範囲 D3:AF が広がり、
  変更の記録の比べ方が変わる）シートには足しません。
  差分追跡は追跡シートの列の数（`gridColumns`）を覚えていて、変わると次の編集で「構成が変わった」として止まります（スクリプトで足した列には変更トリガーが動かない）。
  そのため、列を増やしたシートは、その場で比較基準を取り直します（`diffRebaselineSheet_`。値は変わらない）。まだ記録していない編集（取りこぼし回収の印）があるシートは、
  取り直すとその編集が記録されなくなるので足しません。報告フラグは行の内容（変更時点スナップショット）にも入れません（`diffSnapshotSkippedHeaders_`。ボタン列と同じ）。

#### スライドの作り方

- スライドは Slides API（拡張サービス「Google Slides API」。`appsscript.json` の `enabledAdvancedServices`）で作ります。
  表紙・扉のひな形があれば（`mtgTemplateId_()`。`MTG_OPTIONS.templateId`・スクリプトのプロパティ `MTG_TEMPLATE_URL`・前の版のドキュメントのプロパティ `MTG_TEMPLATE_ID` の順）、
  ひな形を保存先のフォルダにコピー（`makeCopy`）して、その中に作ります。ひな形が .pptx なら、Drive API v3 の `files.copy`（`mimeType` を Google スライドに。
  `UrlFetchApp` と `ScriptApp.getOAuthToken()`。拡張サービスを足さないため）で保存先のフォルダに変換し、元の ID・更新日時と一緒にスクリプトのプロパティ
  `MTG_TEMPLATE_CONVERTED` に覚えます（.pptx を更新したら変換し直し、前のものはゴミ箱へ）。
  表紙・扉・統合版の表紙には、ひな形のページ（`MTG_OPTIONS.templatePages`：1・2・3枚目）を使います（`mtgTemplatePlan_`。2回目からは `duplicateObject` で
  複製して `mtg_t{番号}`。使わないページは消す。扉のページが無ければ扉は描き、統合版の表紙のページが無ければ1枚目）。消す・複製するリクエストを先に送り、
  `Presentations.get` で読み直してから、ひな形のページの決まった文字（`MTG_OPTIONS.templateTexts`）を文字の枠ごとに書き換えます（`mtgTemplateTextRequests_`）。
  2026/10/17 のひな形は見出しとその下がどちらも `XXXXX` なので `replaceAllText` は使えず、枠の文字が決まった文字と同じ（X は5文字以上なら同じ）枠を、
  文字の大きい順・上から順に見出し → その下に当てます。書き換えは、新しい文字を先頭に入れて（`insertText`。元の文字の書式を引き継ぐ）から元の文字を消し
  （`deleteText` の `FIXED_RANGE`）、空なら文字を消します（`ALL`）。ほかのスライドは白紙のスライド（`BLANK`）を表紙の次から順に足し、
  最後に `updateSlidesPosition` で1枚目から順に決まった位置に動かします（ひな形のページ・複製は表紙の近くにあるため）。
  ひな形が無ければ、`Slides.Presentations.create`（`pageSize` 720 × 405pt）で新しく作って保存先のフォルダに移し、表紙・扉はひな形と同じ位置に白い字で描きます（`mtgTemplateFallback_`）。
  表紙・扉のページの背景は、いったん一色（表紙は緑 `cover`、扉はグレー `divider`。`updatePageProperties`）にし、最後にひな形と同じ絵柄の画像にします
  （扉はひな形があってもグレーの画像。`mtgCoverBackground_`。SlidesApp の
  `getBackground().setPictureFill()`。Slides API ではドライブのファイルやスクリプトで作った画像を背景にできないため。画像を付けたら `saveAndClose()` してから PDF にする）。
  画像は `mtgCoverPng_` がスクリプトの中で描いた PNG（1280 × 720px・約 50KB）です：左上から右下へ `#3A7D22` → `#8CD872`（26% までは `#3A7D22`。CSS の `135deg` と同じ向き）に、
  大きな「RX」（`#275316`。Liberation Sans Bold の字形の輪郭を `MTG_COVER.contours` に持ち、ひな形の位置・大きさで、はみ出した部分は切る）を重ねます。
  扉・統合版の表紙は同じ絵柄を `MTG_COVER.divider`・`MTG_COVER.combined` の色で描きます（`mtgCoverPng_('divider')`・`mtgCoverPng_('combined')`。紫は RX を `shift` だけ左）。
  RX は輪郭を横の線で塗り（1px を縦に4本・横は面積で数えて縁をなめらかに）、`mtgPng_`・`mtgZlib_`（deflate の固定ハフマン符号。同じ並びは1画素前・1行上・斜め上だけを探す）で
  PNG にします（画像のファイルを別に置かない・`Utilities` の圧縮に頼らない）。描くのは実行ごとに1回（`MTG_COVER_CACHE`）。
  画像を付けられなければ（権限など）、緑一色の背景のまま資料を作り、ログに残します。
  何枚かずつ（`batchRequests` 件まで）`batchUpdate`（白紙のスライド・テキストの箱・図形・表）で書きます（Slides API は1分あたりの書き込みの回数に上限があるため、まとめて送る）。
  最後に、足したスライドに付いたレイアウトの枠（ひな形の白紙のレイアウトにあるページ番号・日付・フッター）を消します（`mtgPlaceholderRequests_`。ページ番号が2つ出ないように）。
  ページへのリンク（部品の `link` にスライドの番号）は、すべてのスライドを作ったあとに、リンク先のページの ID で付けます（`updateTextStyle` の `link.pageObjectId`。
  まだ無いページへはリンクできないため。リンクにすると青の下線になるので、同じリクエストで字の色を戻し、下線を消す）。Google スライドの PDF の書き出しは
  ページへのリンクを残しますが、飛び先が「/XYZ null null 0」（縦の位置を変えない）なので、見る画面によってはページの頭に移りません。
  リンクのある資料（統合版）の PDF は、飛び先を同じ長さの「/Fit」（ページ全体）に置き換えてから保存します（`mtgPdfFitLinks_`。長さが同じなので相互参照表はそのまま）。
  Google ドライブのプレビュー画面は、PDF の中のページへのリンクに移らないことがあります（Chrome・Acrobat などで開けば移る）。
  資料を読む（`Presentations.get`）ときは、要る項目だけを `fields` で読みます（`MTG_SLIDES_FIELDS`。統合版（130ページほど）を丸ごと読むと
  「レスポンス コード: 413。メッセージ: response too large」で失敗したため）。
  表の列は 32pt 以上にします（それより狭いとエラーになる）。
  `getAs('application/pdf')` で PDF にして同じフォルダに保存します。`MTG_OPTIONS.keepSlides` が `false`（今の設定）なら Google スライドはゴミ箱に移します（ひな形なしで作ったスライドは、フォルダに動かさずにゴミ箱へ）。
  失敗したときは作りかけのスライドをゴミ箱に移し、会議日も記録しません。拡張サービスが無いときは、追加のしかたを案内して止めます。
  - スプレッドシートを PDF に書き出す方法（前の版）は A4 で、16:9 にできないためやめました（`UrlFetchApp` は、いまは Google チャットへの通知にだけ使う）。
  - Slides の権限（プレゼンテーション）が要ります。メニューは `requireAllScopes()` ですべての権限を確かめるので、入れたあとは利用者も1回承認し直します。

得意先・案件名は、`sheet` のシートの進行中で期待値の大きい案件を使い、案件が無いシートでは架空の名前にします。
タスク管理にシートで足した列（進捗状況・開始日／終了日（予定・実績））にも書きます（`SMP_OPTIONS.service.taskExtraColumns`。日付の列は日付で。見出しの無い列は書かず、
設定に無い列は終わりの画面に出す）。`removeServiceMtgSampleData()` は「【サンプル】」の行だけを消します。
サンプルを含む資料は、出典の行と表紙に【サンプルデータを含む】と出ます。

### 会議の日程と資料を作る画面（`MeetingSchedule.gs`・`MeetingRunDialog.html`）

- **日程を読む**（`importMeetingSchedules()`・`mschImport_`）：Google カレンダー（`MSCH_OPTIONS.calendarId`。空なら実行する人の既定のカレンダー）の、今日の `pastDays` 日前〜
  `aheadDays` 日後の予定を `CalendarApp` で読み、予定の名前に `MSCH_OPTIONS.titles` の言葉を含むものを RX Business Meeting・RX Service Meeting とみなします
  （全角・半角・大文字小文字・空白の違いは無視。RX Service を先に見る。断った予定・名前に `excludeWords` を含む予定は読まない。同じ会議・同じ日は1つ）。
  `mtgIndexEnsureRows_` で、インデックスに会議日と会議名の行を足します（ドキュメントロックの中。ある行はそのまま、`index.order` の位置に差し込む。`mtgIndexRow_`）。
  会議名の列には、予定の名前ではなく会議の名前（`MTG_OPTIONS.index.kind`・`SMTG_OPTIONS.index.kind`）を書きます（資料の行と同じ行を使うため）。
- **資料を作る画面**（`MeetingRunDialog`）：資料を作る関数（エディタから実行）は `mschOpenRunDialog_(kind, final)` で画面を開くだけです（`kind`：'business' 会議サマリ・
  'combined' 統合版・'service' RX Service Meeting）。画面は `getMeetingRunData` で、インデックスのその会議の日程（`mtgIndexMeetings_`。会議名が空の行は RX Business Meeting）と、
  作るシートの候補（会議サマリ：追跡シートと前回の資料の会議日。RX Service Meeting：リクエストの件数。0件は初めは選ばない）を読みます。
  会議日程をプルダウンで選び（初めは今日以降でいちばん近い会議日。一覧に無い日は日付を入力）、「次へ（確かめる）」で `checkMeetingRun`（確かめの文。統合版は作れない理由も）、
  「作成する」で `runMeetingMaterials` を呼びます（`mtgRunStart_`・`mtgCombinedStart_`・`smtgRunStart_`）。作っている途中の仕事があれば知らせを出し、「やめて新しく作る」に
  チェックを入れたときだけ作ります。結果の文は画面に出します（URL はリンク）。
- **画面が読み込み直されたとき**：スプレッドシートの画面の都合で、ダイアログのページが読み込み直されることがあり、そのときは初めの画面（選ぶ画面）に戻ります
  （画面のコードが初めの画面に戻すのは、読み込んだときと「戻る」だけ）。サーバーの `runMeetingMaterials` はそのまま続くので、「作成する」の途中・結果を
  作った人のユーザーのプロパティ（`MSCH_OPTIONS.runStateKey`。`mschRunState_`）に控え、`getMeetingRunData` の `run` で画面に返します。
  作っている途中なら画面は「資料を作っています（○:○○ から）」を出して `getMeetingRunState` を `pollSeconds` ごとに問い合わせ、終われば結果の画面を出します。
  作り終えてから `resultMinutes`（30分）のあいだは、選ぶ画面の上に結果（リンクつき）を出します。同じ人が作っている途中にもう一度「作成する」を押しても作りません
  （同じ資料を2回作らない）。途中のまま `runningMinutes`（7分。1回の実行は6分まで）を過ぎたものは、止まったとみなします。
  「作成する」の呼び出しが通信のエラーで返ってきたときも、作っている途中なら同じように待ちます。
- **時間の記録**：資料の中身を作る手順（変更の記録・スナップショット・ステータスの定義・クレデンシャル・前回の時点コピー・シートを読んでまとめる）と、
  スライドと PDF の時間を、手順が終わるたびに実行ログに書きます（`mschTimer_`。「実行数」で、どこで時間がかかったかを確かめる）。
- **比べる時点**（画面のプルダウン。`getMeetingRunData` の `points`）：空は前回の会議（シートごとに `mtgPreviousOf_`）。会議サマリは `mtgComparePoints_` の候補
  （時点コピー（`copy:<ID>`）：保存先のフォルダのスプレッドシートのうち、タイトルが時点コピーの形のもの（`mtgListCopies_`・`mtgParseCopyTitle_`。前の名前
  `formerCopyNames` も。前の版の「（会議日 …）」は資料作成時）と、シートの会議の記録にあるもの（同じコピーのシートをまとめる。記録に無いコピーは、選んだときに開いて
  シートを確かめる）。インデックスの会議日（`date:yyyy/MM/dd`。その日の 0時）。プルダウンでは `group` の見出しでまとめる）と、
  日時の指定（`at:yyyy/MM/dd HH:mm`）。`mtgResolvePoint_` で「前回」の形（`chosen: true`）にし、`mtgPreviousWith_` で全シートの前回を置き換えます
  （前回と同じ時点なら前回のまま。コピーに無いシートは `noCopy` で変更の記録から）。区切って続けても使えるよう、仕事（`job.point`）に残します。
  資料の言葉は `mtgFromWord_`（「前回」→「10/9」）・`mtgCopyWord_`・`mtgChosenText_`。RX Service Meeting は記録した会議の会議日（`smtgCheckPoint_`・
  `smtgPrevious_(list, meeting, point)`。前回と違えば `chosen`。言葉は `smtgPrevWord_`「選んだ会議」・「10/9比」）。
- **前回の会議**：前回の資料の記録（本番の会議日の記録・基準）が無ければ、会議日程の一覧の前の会議日（その日の 0時）からの変化を出します（RX Business Meeting。
  `mtgScheduledPrevious_`・`mtgPreviousOf_`。資料の期間は「前回会議（10/9）以降」。時点コピーは無いので、変更の記録から出す）。
- テストでは、画面の操作を `tests/lib/meeting-run.js` でまねます（`gas.promptAnswers` の [シートの番号, 会議日] で選び、`gas.confirmAnswer` で「作成する」）。

### 案件の行を足す（`addDealRows`。`test.gs`）

追跡シートは、データの1行目の配列の数式（`=ROW(B3:B76)-2`・`=IF(M3:M76="",,N3:N76*…)`）と入力規則が最後の行までの範囲で付いています。
`diffAddRows_` は、データの1行目の数式の範囲（`X3:X76` のうち、始まりがデータの1行目のもの）の最後の行を探し、その行の**上**に `insertRowsBefore` で足します
（範囲の中に足すので、数式・入力規則・条件付き書式の範囲が伸びる）。足した行には、すぐ上の行の書式と入力規則を `copyTo`（`PASTE_FORMAT`・`PASTE_DATA_VALIDATION`）で写し、
最後の行（下にずれた）に案件があれば `moveRows` で足した行の上に動かします（数式の列の計算した値は案件とみなさない）。
ドキュメントロックの中で行い、最後に `diffResyncRows_` で比較基準の行をそろえます（空の行・動かしただけの行は記録しない。止まっているシートは自動の立て直しに任せる）。

### 旧フォーマットからの転記（`LegacyMigration.gs`）

`migrateLegacyDeals()`（エディタから実行）は、URL で開いた旧フォーマットのスプレッドシートの `案件_{シート名}` から、`DIFF_RULES` のシートへ転記します。

- 列は見出しで対応させます（`MIG_OPTIONS.columns`。旧の見出しは1〜2行目で、下の行を優先。旧のデータは4行目から。3行目は入力の種類）。
  新のデータの1行目に数式がある列（No.・期待値。範囲の配列の数式）は、途中の行に値を書くと配列が壊れるので、書かない・消さない。
- 先にすべてのシートを読んで計画を作り（`migPlan_`。まだ書かない）、件数と、プルダウンの選択肢（一覧・範囲。`mtgListOptions_`）に無いため空欄にするセルの数を確かめてから、
  ドキュメントロックの中で、データの行を消して書きます（`migWrite_`。数式の列をよけた続きの列ごと。文字は `credText_` で数式にしない）。
  選択肢に無い値は書けない（スクリプトの書き込みも入力規則で止まる）ので空欄にして、セルの位置と旧の値を知らせます。
- 書いたあと `setupDiffTracking()` で比較基準を今の値にし（スクリプトの書き込みは編集トリガーが動かず、転記を変更として記録しないため）、
  `mtgRecordBaseline_` で会議サマリの基準を記録します（転記した案件を「新規」に数えない）。

### 列の保護（`自動入力部分のシート保護.gs`）

`protectSpecificColumnsWithLock()` を手動で実行すると、名前が `案件_` で始まるシートの P・R・T・X・AA・AB 列を
実行した人だけが編集できるように保護します。同じ説明の保護が既にあれば作りません。

## 判断の理由

- **比較の基準は「最後に取り込んだ値」**：承認済みの値ではありません。取り込みの間にあった途中の状態は残らないため、完全な監査証跡ではありません。数式は計算結果ではなく式で比べます。
- **シートの文字列は数式にならない方法で書く**：利用者の入力が `=` で始まると、そのまま `setValue` すれば数式として動きます。差分ログはリッチテキスト、記録シートは先頭の `'` で防ぎます。
- **ロックが取れない編集をエラーにしない**：同時に何人も編集すると、編集トリガーが重なってロック待ちになります。止めるより印を付けて回収するほうが、追跡を続けられます。
- **行の追加・削除では止めない、列の変化では止める**：行の増減は突き合わせで追えますが、列が動くと `DIFF_RULES` の列指定そのものがずれるため、人が確認してから取り直します。
- **行のずれは見分け列で確かめる**：並べ替え・ドラッグでの移動、トリガーより先に削除と追加が続いた場合は、シートの大きさが変わらないので行数では気づけません。そのまま比べると別の行の値が「変更前」になり、取りこぼし回収ではずれた行がすべて「変わった」と記録されてしまうため、得意先・案件名の位置で確かめます。全列を比べないのは、毎回の編集で読む量を小さくするためです。
- **追跡シートが多くても、関係するシートだけを読む**：トリガーは3つのままで全シートをまかなうため、1回の処理では、編集したシート・行数が変わったシート・操作したシート・印の付いたシートだけを読みます。印は全シートぶんを `getProperties()` 1回で読みます。
- **編集者は `e.user` から取る**：インストール型トリガーはトリガーの所有者の権限で動くので、`Session.getEffectiveUser()` は所有者を返してしまいます。
- **トリガーの所有者は1人（管理者）**：同じトリガーを複数人が設置すると二重に記録されます。設置する関数は「1つだけ存在する」ことを保証します。
- **メニューは「履歴サイドバーを開く」「権限を承認する（初回のみ）」だけ**：承認の画面は、本人がメニューなどから関数を実行したときにしか出せません（サイドバー・ボタンからは出せない）。
  そのため、利用者向けの入口として、サイドバーを開く項目と承認の項目をメニュー「🟩RXビジネスMTG用」に置きます（どちらも、まだ承認していない人には承認の画面が出る）。
  「権限を承認する」は `ScriptApp.requireAllScopes()` で、承認の画面で一部の権限を外した人にも承認し直してもらい、サイドバーを開き直します。
  管理者の作業（ボタン列の設定・サンプル履歴など）や選んだ行のモーダルを開く処理は、エディタから関数を実行します。
  メニューの名前は `CRED_OPTIONS.menuTitle`（🟩RXビジネスMTG用）・`SVC_OPTIONS.menuTitle`（🟪RXサービスMTG用）の1か所にだけ書きます。
  サイドバー・承認のページの案内に出す名前は、テンプレートの値（`menuTitle`）で渡します（HTML に名前を書かない）。
  管理者がエディタから実行する処理の確認・結果の画面（`ui.alert`・トースト）のタイトルも、機能ごとにメニューの名前にそろえます
  （差分追跡・ボタン列・履歴サイドバー・サンプル履歴は 🟩、サービスリクエスト・タスク管理は 🟪。差分追跡は `diffAdminTitle_()`）。
  編集した人に出す知らせ（差分追跡の停止・行の追加や削除の反映など）とモーダルを開けなかったときの知らせは、内容が分かる名前のままにします。
- **ボタンはチェックボックス＋インストール型 onEdit 1つ**：どの行から押したかが分かるよう各行のチェックボックスをボタンにし、承認の要るモーダルを開くためにインストール型の onEdit を使います。ボタン列が増えてもトリガーは増やしません。
- **モーダルの大きさ**：`showModalDialog` は開くときの大きさしか指定できないため、開いたあとに `google.script.host.setWidth()` でブラウザ幅の95%に広げ、次回のためにその大きさを覚えます。

## 画面のデザイン

  - 変更履歴の絞り込みのカード：期間・7日の帯、その下に区切り線と「項目」「変更の詳細」

- 追加した結果は、見出しのカードの中（件数の下）に出し、件数と一緒に見られるようにします（成功は `--teal-wash`、失敗は `#FCEDEC` の地と `--danger` の文字。× で閉じる）。
- 一覧のカード：1件ずつ、上にシート名のバッジ（「クレデン」のバッジと同じ色）とサブインダストリー（シート名と同じなら出さない）、得意先／案件名と右に「追加」（枠線 `#CFE3DC`・文字 `--cred`・高さ 28px）、
  その下にリクエストの文。リクエストの文は2行までにし（`-webkit-line-clamp`）、収まらないものだけに「もっと見る」（開くと「閉じる」）を出します。
  開いたものは、絞り込み・追加で一覧を描き直しても開いたままにします。探した語には印（`mark`）を付けます。中身に合わせた高さで、入りきらないときはカードの中でスクロールします。
- 追加している間は、押したボタンを `--cred` の塗りで「追加中…」にし、ほかの「追加」と再読み込みは押せなくします。
- 権限の承認のカード：読み込み・追加・一覧を開くのが権限で失敗したら、ほかのカードの代わりに出します（形・色は履歴のサイドバーの承認の案内と同じ。小見出しは `--danger` の点）。
  「承認する」は `getAuthorizationLink()` の URL（Google の承認の画面。取れなければ承認用のウェブアプリ）を新しいタブで開き、どちらも無ければメニュー「リクエストを追加」での承認を案内します。
  承認は済んでいるのに失敗するとき（`required: false`。複数のアカウントでログインしているなど）は、そのことを案内します。
  出している間は10秒ごと（「承認する」を押してから5分間は3秒ごと）に裏で読み直し、読めたらカードを閉じて一覧を出します（開き直さなくてよい）。

### 一覧のモーダル（`RequestListDialog`）

パネルの件数のバッジから開く、未登録・登録済みのリクエストの一覧です。ほかのモーダルと同じ大きさ（ブラウザ幅の95%。`credDialogSize_`・`saveCredentialDialogSize`）・見出しの形にしています。

- 見出し：小見出し「サービスリクエスト」の下に、タブ（未登録・登録済み。件数のバッジ付き。履歴のサイドバーのタブと同じセグメント）、右にキーワードの欄と再読み込み（取得した時刻は title）。
- 一覧は表で、見出しの行は上に固定します。未登録はシート（バッジ）・サブインダストリー・得意先・案件名・リクエスト、
  登録済みは行・サブインダストリー・得意先・案件名・リクエスト・判断（サービス化検討は `--teal-soft`、棄却は取り消し線）・サービス案・担当者。
  右端は操作の列で、未登録は「追加」（パネルと同じ枠線 `#CFE3DC`・文字 `--cred`）、登録済みは「削除」（枠線 `#F3CFCB`・文字 `--danger`）。
  「削除」を押すと、その場で「削除する」（`--danger` の塗り）と「やめる」に変わります。
- 追加・削除の結果は、見出しの下に知らせます（成功は `--teal-soft`、失敗は `#FCEDEC` の地と `--danger` の文字。× で閉じる）。
  処理している間は、押したボタンを「追加中…」「削除中…」にし、ほかの追加・削除と再読み込みは押せなくします。
- リクエストの文は3行までにし、収まらないものだけ「もっと見る」を出します。空の値は「—」。探した語には印（`mark`）を付けます。

### 書き方の決まり

- 画面に出す文字は `textContent` で入れます（HTML として解釈しない）。`innerHTML` 系は固定のアイコン（SVG）だけに使います。
- サーバーの関数は `google.script.run` から呼べるよう、末尾に `_` を付けません。
- `Loading.html`（アカウントプランシート作成）は別の機能の画面で、この決まりの前からある簡単な画面です。

## テスト

### ロジック（`npm test`）

`tests/lib/gas-mock.js` が Apps Script のモックです。リポジトリ直下の `*.gs` を Node.js の vm に1つのグローバルスコープとして読み込み、
`SpreadsheetApp`・`PropertiesService`・`LockService`・`ScriptApp`・`HtmlService` などをこのプロジェクトが使う範囲だけ再現します。

- `createGas()` でテスト1件ぶんの環境を作ります。`tests/lib/fixture.js` の `setupProject()` は、新FMT・新FMT2 を作って管理者のセットアップまで済ませます。
- 利用者の操作は `gas.edit(sheet, 'F3', '受注')`（編集イベントを返す）・`gas.change('INSERT_ROW')`・`gas.select(sheet, 'E4')` で再現します。
- スクリプトの書き込みは `gas.writes` に「ロックを持っていたか」と一緒に残るので、書き込みがロックの中かを確かめられます。
- `setValue` の文字列は手入力と同じく変換します（`'` で始まれば文字列のまま、`=` なら数式、日付・数字は日時・数値）。
- vm の中で作られた値は `plain()` で普通のオブジェクトにしてから `deepStrictEqual` で比べます。
- テストはシート名の設定に左右されません。モックが `DIFF_RULES` を `新FMT`（`requests: true`）・`新FMT2` に、リクエスト・タスク管理のシート名を `リクエスト`・`タスク管理` に置き換えます。
  本物の設定は `createGas({realSheetNames: true})` で読み、形と名前の重なりを `tests/project.test.js` で確かめます。
- 数式は計算しません（表示は空）。
- `ui.prompt` で続けて聞く処理（会議サマリのシートと会議日など）は、`gas.promptAnswers` に答えを順に入れます（空になったら `gas.promptAnswer`）。
- 外への送信（`UrlFetchApp.fetch`。会議サマリの Google チャットへの通知）は `gas.fetches` に残ります。応答のコードは `gas.fetchStatuses`（続けて呼ばれるときの順。空になったら `gas.fetchStatus`）、
  本文は `gas.fetchText` で決めます。時間主導のトリガーの設定（`atHour`・`everyDays`・`inTimezone` など）は、作ったトリガーの `options` に残ります。
- Google Slides API（拡張サービス）は `gas.decks` に作ったスライドと `batchUpdate` のリクエストを残します。有効にしていないプロジェクトは `createGas({noSlides: true})`、失敗は `gas.slidesError` で再現します。
- 使う API がモックに無ければ、モックに足してください。

### チェック（`npm run check`）

`scripts/check-syntax.js` が、`.gs`・`.html` がフォルダの中に無いか・構文・`.gs` と `.html` の同名・トップレベルの名前の重複・`onOpen` の数・
HTML ファイル名・メニューや `google.script.run` から呼ぶ関数の有無を確かめます。

### 画面（`.html`）

Playwright（Chromium）で HTML を開き、`google.script.run` をモックに差し替えると表示を確かめられます。

1. HTML の `<?= 名前 ?>` を値に置き換えて、一時ファイルに書き出します。
2. `page.addInitScript()` で `window.google = {script: {run, host}}` を入れます。`run` は `withSuccessHandler`・`withFailureHandler` を受け取り、
   呼ばれた関数名に応じてテスト用のデータを返す Proxy にします。`host` は `setWidth`・`setHeight`・`close` を空の関数にします。
3. `page.goto('file://…')` で開きます（`page.setContent()` では `addInitScript` が効きません）。
4. `#loading` が非表示になるのを待ってからスクリーンショットを撮ります。

Google Fonts が読み込めない環境では代わりのフォントで表示されるので、文字の幅は実際と少し違います。

### 会議サマリのスライド

`mtgSlides_(summary)` の戻り値（箱と表の部品の並び。位置と大きさは pt）を HTML の絶対配置に置き換え、1280 × 720px（1pt = 1280/720px）で Playwright のスクリーンショット・PDF にすると、
Google スライドに送らずに見た目を確かめられます。箱・セルの余白は Slides と同じ上下左右 7.2pt、行の送りは 1.2、字は BIZ UDPゴシック（Google Fonts の BIZ UDPGothic の TTF を `@font-face` で読む）にします。
ひな形が無いときの表紙は `mtgCoverPng_()`、扉は `mtgCoverPng_('divider')`、統合版の表紙は `mtgCoverPng_('combined')` の画像を背景に置きます。
RX Service Meeting の資料は `smtgSlides_(smtgCollect_(…), 会議日, false)` の戻り値を、`smtgWithPalette_` の中で `mtgSlideRequests_` にして同じように確かめます（表紙は `mtgCoverPng_('combined')`）。
文字の折り返しは `mtgWrap_` の見積もりで先に分けてあるので、HTML で行数が増えるところは見積もりが甘いところです。最後は本物のスライド（PDF）で確かめてください
（`pdftotext -bbox` で文字の位置を出すと、行の高さ・文字の幅を測れる）。
