# 運用手順

導入・日々の運用・設定の変更・トラブル対応の手順です。仕組みは [DESIGN.md](DESIGN.md) を参照してください。

> **シート名について**：シート名は設定で変えられます。このドキュメントでは、差分追跡の対象のシート（今の名前は「スーパー・GMS」「コンビニ」「百貨店」「化粧品・トイレタリー」「飲料・食品」「自動車販売」「住設」「地方銀行」「電鉄・不動産」「エネルギー」「生協」の11シート。前の名前は新FMT・新FMT2）を「新FMT」、
> リクエストを登録するシート（今の名前は「サービスリクエスト」）を「リクエスト」、タスクのシート（今の名前は「サービス案タスク管理」）を「タスク管理」と書きます。
> 今の名前と書いてある場所は、OPERATIONS.md の「シート名の一覧」を見てください。

関数を「実行する」とは、Apps Script エディタで関数を選んで「実行」を押すことです。
メニュー「🟩RXビジネスMTG用」には利用者向けの「履歴サイドバーを開く」「権限を承認する（初回のみ）」だけを置いているので、管理者の作業や選んだ行のモーダルを開く処理は、エディタから関数を実行します。
確認や結果の画面はスプレッドシートの側に出るので、スプレッドシートを別のタブで開いたまま実行してください。
**トリガーを設置する関数は、必ず管理者アカウント（トリガーの所有者）1人だけが実行してください。**
別の人が実行すると、同じトリガーが二重にでき、記録が二重になります。

## 最初の導入（管理者アカウントで）

1. リポジトリ直下の `.gs`・`.html` を Apps Script に反映します（「[clasp で同期する](#clasp-で同期する)」または「[エディタに貼り付ける](#エディタに貼り付ける)」）。
2. 追跡シート（`新FMT`・`新FMT2`）の2行目（見出し行）を確かめます。
   - `最終更新日時`・`得意先` の見出しが、それぞれちょうど1つある
   - ボタン列 `クレデンシャル`（セル内で改行）`オファリング登録` と `変更履歴` を使うときは、それぞれちょうど1つあり、**追跡範囲（`D3:AF`）の外**にある
     （ボタン列は無くてもかまいません。無いシートにはボタンを付けず、クレデンシャル・変更履歴はサイドバーから開きます）
   - 追跡範囲に結合セルが無い
3. `test.gs` の `DIFF_RULES` が、追跡したいシート・範囲になっているか確かめます。
4. `setupDiffTracking()` を実行し、権限を承認します。今の値が比較基準になり、差分追跡のトリガー3つが設置されます。
5. 次の関数を実行します。
   - `setupCredentialLauncher()`（ボタン列を設定・補充）
   - `setupChangeHistoryLauncher()`（変更履歴ボタン列を設定・補充）
6. 必要なら `protectTimestampColumns()` を実行し、最終更新日時の列を管理者だけが編集できるようにします。
7. 必要なら「[承認用のウェブアプリを用意する](#承認用のウェブアプリを用意する)」を行います（「承認する」ボタンは用意しなくても出ます。用意すると、ボタンの予備の行き先になります）。

### 利用者の権限の承認（初めて使う人）

履歴サイドバーは、各自がメニュー「🟩RXビジネスMTG用」→「履歴サイドバーを開く」で開きます（スプレッドシートを開いたときに自動では開きません）。
追跡しているシート（`DIFF_RULES` のシート。今は11のサブインダストリーのシート：スーパー・GMS、コンビニ、百貨店、化粧品・トイレタリー、飲料・食品、自動車販売、住設、地方銀行、電鉄・不動産、エネルギー、生協）を開いているときだけ開きます。ほかのシートでは「このシートでは開けません」と出ます。
初めて使う人がメニューを押すと Google の承認画面が出るので、承認してもらいます（1回だけで、2回目からは要りません）。

サービスリクエストの選択パネルも同じで、各自がメニュー「🟪RXサービスMTG用」→「リクエストを追加」で開きます（`サービスリクエスト` のシートを開いているときだけ）。
初めて使う人・一部の権限を外して承認した人は、メニューを押したときに Google の承認画面が出ます。承認すると、パネルが開きます。

使う人に要るのは、スプレッドシートの**編集の権限**と、この1回の承認だけです（閲覧・コメントだけの人にはメニューが出ません）。
`サービスリクエスト`・`サービス案タスク管理` のシートを保護して編集できる人を絞ると、ほかの人はパネルから追加・削除できなくなります。

承認の画面で一部の権限のチェックを外した人などは、サイドバー・パネルに「権限の承認が必要です」と出て読み込めません（ボタンから開くモーダルも読み込めません）。
そのときは次のどちらかで承認し直してもらいます。

- サイドバー・パネルの「承認する」ボタン：新しいタブで Google の承認画面が開くので、すべての項目にチェックを入れて承認してもらいます。
  承認が済んだらタブを閉じます。数秒でサイドバーに履歴が、パネルにリクエストが表示されます（開き直さなくてかまいません）。
- メニュー「🟩RXビジネスMTG用」→「権限を承認する（初回のみ）」、またはメニュー「🟪RXサービスMTG用」→「リクエストを追加」：表示される画面で承認します。

パネルに「読み込めません」と複数の Google アカウントの案内が出たときは、承認は済んでいます。1つのアカウントだけでログインした状態か、シークレットウィンドウで開き直してもらいます。

### 承認用のウェブアプリを用意する

「承認する」ボタンは、ふだんは Google の承認画面を直接開きます（用意は要りません）。その URL が取れないときの予備として、
同じプロジェクトのウェブアプリ（`HistorySidebar.gs` の `doGet`）を開くようにできます。
ウェブアプリを「アクセスしているユーザー」として動かすと、まだ承認していない人には Google の承認画面が出ます。ページは承認の状態を表示するだけで、シートは読み書きしません。
用意するときは、管理者が1回だけ次を行います（用意しなくても、URL が取れないときはメニューでの承認を案内します）。

1. Apps Script エディタの右上の「デプロイ」→「新しいデプロイ」を押します。
2. 「種類の選択」の歯車から「ウェブアプリ」を選び、次のようにして「デプロイ」を押します。
   - 説明：`RXビジネスMTG用の承認`（何でもよい）
   - 次のユーザーとして実行：**ウェブアプリにアクセスしているユーザー**
   - アクセスできるユーザー：**（組織名）内の全員**（スプレッドシートを使う人が全員組織内の場合。組織外の人もいるときは「Google アカウントを持つ全員」）
3. 表示された「ウェブアプリの URL」（`https://script.google.com/…/exec`）をコピーします。
4. `HistorySidebar.gs` の `HS_OPTIONS.authorizeUrl` に貼り付けて保存します（`…/exec` で終わる URL だけを使います。テスト用の `…/dev` は使えません）。

ウェブアプリはデプロイしたときの版のコードで動きます。**新しいサービスを使い始めるなど、権限が変わる変更をしたら**、
「デプロイ」→「デプロイを管理」→ 鉛筆のアイコン →「バージョン」を「新バージョン」にして「デプロイ」を押してください（URL は変わりません）。
古い版のままだと、ボタンから承認しても新しい権限が足りず、サイドバーが読み込めないままになります。

## 日々の運用

| こんなとき | すること |
|---|---|
| 追跡シートに行を足した | `setupChangeHistoryLauncher()` を実行し、最終行までボタンを補充する（クレデンシャルを使っているときは `setupCredentialLauncher()` も） |
| 案件の行が足りない（行を足したい） | エディタで `addDealRows()` を実行し、シートの番号と足す行の数を入力する（下の「案件の行を足す」）。手で足すときは、最後の行の**上**に足す（最後の行の下に足すと、No.・期待値の数式とプルダウンが足した行に届かない） |
| 行を追加・削除した | 何もしなくてよい（自動で記録し、追跡を続ける。削除と追加を続けて行っても、行のずれに気づいて突き合わせ直す） |
| 列を追加・削除した | 何もしなくてよい（その場で比較基準を取り直して記録を続ける。トーストで知らせる）。追跡する列の範囲（`DIFF_RULES` の `ranges`）が合っているかは確かめる |
| 行を並べ替えた・ドラッグで動かした | そのシートの次の編集のときに、行のずれに気づいて突き合わせ直す（移動しただけの行は記録しない）。`得意先`・`案件名` がどちらも同じ行が複数あると見分けられないため、並べ替えはなるべく避ける。おかしいときは `setupDiffTracking()` で比較基準を取り直す |
| 差分を確認した | `変更履歴_差分` の「確認済み」にチェックを入れる |
| 履歴サイドバーを開きたい | 追跡しているシートを開いて、メニュー「🟩RXビジネスMTG用」→「履歴サイドバーを開く」（サービス管理の「リクエストを追加」を開くと入れ替わるので、戻すときも同じメニューから） |
| 前の版の自動表示のトリガーが残っている（トリガーの一覧に `autoOpenHistorySidebar` がある） | 管理者が `removeHistorySidebarAutoOpen()` を実行する（実行しなくても、次に誰かが開いたときにそのトリガーは外れ、サイドバーは開きません） |

`setupDiffTracking()` を実行し直しても、これまでの記録（`変更履歴_差分`・`変更時点スナップショット`）は消えません。比較基準だけが取り直されます。

**クレデンシャル・オファリング履歴は一旦使っていません（2026/10 から）**：`CredentialHistory.gs` の `CRED_OPTIONS.enabled` が `false` の間は、
履歴サイドバーにクレデンシャルのタブを出さず（変更履歴だけ）、登録のモーダル・クレデンシャルのボタン列（`setupCredentialLauncher()`・`setupAfterSheetChange()` でも付けない）・
会議サマリの入力内容のチェック「予定日超過」（列ごと出さない）・サンプルのクレデンシャルも使いません。
`クレデンシャル履歴_記録` シートとこれまでの記録はそのまま残しています（消さないでください）。また使うときは `true` に戻して `CredentialHistory.gs` を貼り替えます。

### アカウントプランシートの作成

Apps Script エディタで `showLoadingDialog()`（`コード.gs`）を実行し、スプレッドシートに出る画面で処理するシート名を入力します。
メニュー「アカウントプランシート作成」は出していません。メニューから使うときは、`CredentialHistory.gs` の `CRED_OPTIONS.accountPlanMenu` を `true` にします（メニューの右端に「アカウントプランシート作成」→「作成開始」が出ます）。
E列が入力済みで M列が空の行ごとに、テンプレートをコピーして M列に URL を入れます。
5分たつと途中で止まるので、残りがあればもう一度実行してください（M列が空の行だけを続けて処理します）。
「他の処理が実行中のため…停止しました」と出たときも、少し待ってからもう一度実行すれば続きから処理します。

テンプレートのファイルと保存先のフォルダは、`コード.gs` の `executeCopyProcess()` の「設定項目」で変えます。

履歴サイドバーの得意先名の横の「アカウントプラン」ボタンは、`33シナリオ攻略先リスト` の E列（得意先）と M列（URL）を読んで、同じ得意先の URL を開きます。
URL を入れたあとは、サイドバーの「再読み込み」（または1分ほど待つ）で反映されます。シート名・列を変えたときは、`HistorySidebar.gs` の `HS_OPTIONS.accountPlan` を直してください。

### サンプルの履歴（画面の確認・説明用）

追跡シートで行を選んでから `addSampleHistory()` を実行すると、選んだ行の得意先にサンプルの履歴を追加します（複数行を選ぶと得意先ごとに追加。一度に20件まで）。
得意先が空の行（案件の無い行。スーパー・GMS なら 11行目以降）は飛ばします。案件のある行を1つも選んでいなければ、そう知らせて止めます。

- クレデンシャル 5件・オファリング 5件（クレデンシャルに紐づけ。実績・予定・期限超過を含む）
- 変更の記録 5件（過去2週間ほどの日時。その行の追跡範囲の、見出しのある列を使う）

追跡シートのセルの値は変わりません。サンプルは名称の先頭が「【サンプル】」、登録元・登録者・編集者が「サンプルデータ」、変更の記録のイベントIDが「SMP-」で始まります。
使い終わったら `removeSampleHistory()` を実行して、この印の付いた行だけを削除してください（本物の履歴は消えません）。
件数や内容は `サンプルデータ.gs` の `SMP_OPTIONS` で変えられます。

サンプルの変更の記録は、会議サマリには出ません（会議サマリはサンプルを数えない）。会議サマリの資料の形を確かめるときは、次のダミーデータを使います。

### 会議サマリの確認用のダミーデータ

エディタで `addBusinessMtgDummyHistory()` を実行し、シートの番号（スーパー・GMS など）を入力すると、そのシートの案件にダミーの変更の記録を足します。
確かめの画面に、どの案件にどの区分（前進・後退・延期・増額・減額・活動更新・新規・停滞・削除）を付けるかと、いつ以降の変化として出るか（前回の資料・基準の時刻）が出ます。

- 前回の資料・基準の「時点コピー」があるときは、前回からの変化はコピーと比べるので、ダミーの記録は前回からの変化には出ません（確かめの画面に出ます）。
- シートのセルの値は変わりません。今の値になるまでの記録（前回の時点の値と、そのあとの変更）を足すので、`previewBusinessMtgSummaries()` で作った資料の
  サマリー・パイプラインの変化・前回から変化のある案件・Appendix ①② に出ます。会議日は、ダミーの記録を足した時刻より後の日にしてください。
- 期待値上位の案件（新規を除く）には、「期待値上位案件の状況・課題（直近2か月の動き）」のページを確かめられるよう、前回より前の日付（17〜56日前）に、
  活動状況の書き足し・次回アクション（今の値が入っているとき）・ステータスの前進（停滞の案件を除く）・受注月の前倒しの記録も足します（確かめの画面に案件が出ます）。
  最後の値は前回の時点の値にそろえるので、前回からの変化・停滞は変わりません。
- 削除は、シートに無い架空の案件「ダミー商事／（ダミー）削除した案件」です。停滞は、ステータスを100日・70日前に変えた記録にします
  （その案件に、本物のステータスの変更や案件ができた記録があると停滞にならないので、そういう案件には付けません。付けられる案件が無ければ、確かめの画面にそう出ます）。
- ダミーの記録のイベントIDは「DMY-」、編集者は「ダミーデータ」です。履歴サイドバー・変更履歴の画面にも出ます。
  記録の形は差分追跡と同じです（変更履歴_差分の9列：空欄は「（空欄）」、想定売上は「数値 -> 数値」、日付の受注月は「日時 -> 日時」で `2026/08/01 00:00` の形、
  行の追加・削除は「（行全体）」に追跡範囲の列の「見出し: 値」。変更時点スナップショットの8列：行の内容は見出しと表示の値の JSON）。
  行を選ぶ必要はありません（`addSampleHistory()` とは別の関数です）。
- ダミーを使った資料には、出典の行と表紙に【ダミーデータを含む】と出ます。本番（`createBusinessMtgSummaries()`）の確かめの画面にも出るので、配る資料を作る前に
  `removeBusinessMtgDummyHistory()` で消してください（「DMY-」の行だけを消します。本物の記録は消えません）。
- もう一度 `addBusinessMtgDummyHistory()` を実行すると、そのシートの前のダミーを消してから入れ直します。区分は `サンプルデータ.gs` の `SMP_OPTIONS.dummy` で変えられます。

### リクエスト → サービス案 → タスク の流れ

1. メニュー「🟪RXサービスMTG用」→「リクエストを追加」で選択パネルを開き、新FMT の「サービスのリクエスト」（Z列）から検討するリクエストを選んで `リクエスト` シートに足す
   （足したリクエストはパネルから消え、すべて足すとパネルは「すべて登録済みです」になる）
2. リクエストをもとにサービス案を考える：`リクエスト` の「サービス案」に、考えたサービス案の名前を付ける
   （複数のリクエストに同じ名前を付けると、1つのサービス案にまとまる）。サービス化しないリクエストは「棄却」にする
3. サービス案ごとの検討の進捗を、`タスク管理` シートのタスクで管理する（タスクは「SR-0001 会員の購買分析をしたい」の形で、リクエストを選んで対応付ける）

### リクエスト（サービス案のもと）

新FMT のリクエストのうち、検討するものを `リクエスト` シートに選び、リクエストをもとにサービス案を考える・棄却するためのシートです。
サービスは最初から決まっているものではないので、サービスの一覧のシートは作りません。リクエストに付けたサービス案の名前がサービス案になります。

`リクエスト` シートの1行が1件のリクエストで、列は左から次のとおりです。

- ID：SR-0001 から順に、追加したときに自動で振ります（番号は使い回さず、重複もしません。下の「ID」）
- 選択パネルで選ぶと入る列：サブインダストリー・得意先・案件名・リクエストした営業（アカウント責任者部署・アカウント責任者・BX部署・BX担当）・リクエスト
- 人が入力する列：判断（未判断・サービス化検討・棄却のプルダウン）・サービス部門からのフィードバック・サービス案・
  サービス部門として対応する主管本部・担当者（判断のほかは自由に入力）

前の版の「メモ」「追加日」の列は使いません。`setupRequestSheet()` を実行すると、確認してから削除します（「いいえ」なら残します）。
足りない列は、前からあるシートでは決まった位置に差し込みます（営業の4列は案件名の右、フィードバックは判断の右、主管本部はサービス案の右、担当者は主管本部の右。ほかの列の値はそのまま）。
営業の4列は、取り込み元の見出し（アカウント責任者部署・アカウント責任者・BX部署・BX担当）から読みます。見出しが無いシートのリクエストは、空のまま登録します。

**用意する（管理者が1回）**：`setupRequestSheet()` を実行します。シートが無ければ作り、見出しと判断のプルダウンを付けます（行は足しません）。
前の版の A〜D のプルダウンと、候補を作っていた非表示の `__REQUEST_LISTS` シートがあれば外します（選択パネルを開いたときにも外します）。
`ServiceManagement.gs` を差し替えたときも、`setupRequestSheet()` を1回実行してください。

**使い方**：

1. メニュー「🟪RXサービスMTG用」→「リクエストを追加」で、選択パネル（右のサイドバー）を開く
   - メニューが出ないときは、スプレッドシートを開き直してください。初めて使うときは、権限の承認を求められることがあります
   - パネルには、新FMT（`requests: true` のシート）のリクエストのうち、まだ `リクエスト` に無いものだけが出ます。開くたびに新FMT の最新を読みます
     （パネルを開いたまま新FMT を書き換えたときは、右上の再読み込みを押してください）
   - 「サブインダストリー」→「得意先」→「案件名」で絞り込めます（左で選んだものに合う値だけが右に出ます）。キーワード（得意先・案件名・リクエストの文字）でも探せます
   - サブインダストリー・得意先・案件名が空のリクエストも出ます（そのまま追加できます）
   - 上の「未登録」「登録済み」のバッジを押すと、一覧を大きなモーダルで確かめられます（登録済みは行番号・判断・サービス案・担当者も出ます。
     取り込み元に見つからないものには「取り込み元に無し」の印が付きます）
   - モーダルからも、未登録のリクエストを「追加」できます。登録済みの「削除」→「削除する」で、そのリクエストの行をシートから削除できます
     （判断・サービス案・担当者などの入力も行ごと消えます。削除したリクエストは未登録に戻ります）
2. 検討するリクエストの「追加」を押すと、`リクエスト` シートの最後の行の下に、サブインダストリー・得意先・案件名・リクエストが入ります
   - 判断・サービス部門からのフィードバック・サービス案・主管本部・担当者は自動では入りません。必要に応じて入力してください
   - ほかの人が先に同じリクエストを追加していたときは、追加せずに知らせます
3. リクエストを読んでサービス案を考え、「サービス案」に名前を入力し（自由に入力）、判断を「サービス化検討」にする
4. 同じサービス案にまとめるリクエストには、同じ名前を入力する（全角・半角と空白の違いは同じ名前とみなします。コピーして貼り付けると確実です）
5. サービス化しないリクエストは、判断を「棄却」にする（サービス部門からの理由は「サービス部門からのフィードバック」へ）
6. サービス案ごとの検討の進捗は、`タスク管理` でそのリクエスト（ID）を選んだタスクで管理する

**ID**：

- 登録したリクエストには「SR-0001」のような ID が付きます。会議などで指すときは、行番号ではなく ID を使ってください（並べ替えても変わりません）。
- 番号は、シートにある ID とこれまでに振った番号を見て、いちばん大きい番号の次を振ります。手で書いた ID とも、削除した行の ID とも重なりません。
- 行をコピーして ID が重なったときや、ID を消した・形の違う値を書いたときは、パネルを開いたときに下の行へ新しい番号を振り直し、右下に知らせます（上の行の ID はそのまま）。
- ID の列は書き換えないでください（書き換えた ID がほかと重なると、振り直されます）。

- `リクエスト` シートの行は、並べ替え・フィルタ・削除をしてかまいません（プルダウンが付いていないので、ずれることはありません）。行を削除すると、そのリクエストはまたパネルに出ます。
- A〜D を手で書き換えることもできますが、新FMT と同じ得意先・案件名・リクエストでないと、別のリクエストとして扱われます（パネルに元のリクエストがまた出ます）。
- 登録した行は、パネルを開いたとき（と `setupRequestSheet()` のとき）に新FMT に合わせて直ります。
  - 新FMT でサブインダストリー・リクエストした営業（アカウント責任者部署・アカウント責任者・BX部署・BX担当）を変えると、同じ行も変わります
    （新FMT が正です。`リクエスト` のシートでこれらの列を直しても、パネルを開くと新FMT の値に戻るので、直すときは新FMT で直してください）。
  - 新FMT でリクエスト・得意先・案件名を書き換えた・消したときは、行はそのまま残ります（メモは付けません）。書き換えたリクエストは、新しいリクエストとしてパネルに出ます。
    取り込み元に見つからない行は、エディタで `diagnoseRequestSources()` を実行すると行番号が出ます。見直して不要なら、行を削除してください。
  - 前の版でスクリプトが「リクエスト」のセルに付けたメモ（「取り込み元に見つかりません」など）は、パネルを開いたときに外します（自分で書いたメモはそのまま）。
- サービス案ごとのリクエストは、`リクエスト` シートで「サービス案」の列にフィルタをかけると一覧できます。
- サービス案の名前は、`リクエスト` の「サービス案」を書き換えるだけで変えられます（`タスク管理` はリクエストの ID で選ぶので、直さなくてかまいません）。
- 前の版のシート（見出しが「サービス」）は、`setupRequestSheet()` を実行すると「サービス案」に書き換わります（「取り込み日」は「メモ」「追加日」と同じく、確認してから削除します）。入っている行はそのまま「登録した行」として使います。
  前の版で全件を取り込んでいた場合は、すべて登録した状態（パネルが「すべて登録済みです」）になっています。
  エディタで `removeUntouchedRequests()` を実行すると、手を付けていない行（判断が「未判断」か空で、フィードバック・サービス案・主管本部・担当者が空）を、件数を確かめてから削除し、そのリクエストをパネルに戻せます
  （判断・フィードバック・サービス案・主管本部・担当者のどれかが入っている行は残ります）。
- 前の版で作った `サービス` シートは使いません。不要なら削除してください。
- リクエストを読むシートは、`test.gs` の `DIFF_RULES` で `requests: true` を付けたシートです（今は11のサブインダストリーのシートすべて。見出しの行も `DIFF_RULES` の `headerRow`）。
  新FMT2 も読むときは、`DIFF_RULES` の新FMT2 に `requests: true` を足して `test.gs` を貼り付け、`setupRequestSheet()` を実行してください。
  読むシートには「サブインダストリー」「得意先」「案件名」「サービスのリクエスト」の見出しが1つずつ必要です
  （「アカウント責任者部署」「アカウント責任者」「BX部署」「BX担当」は無くてもかまいません。`diagnoseRequestSources()` で、無いシートが分かります）。
- 見出し・選択肢は、`ServiceManagement.gs` の `SVC_OPTIONS` で変えられます。

### タスク管理（サービス案の検討の進捗）

`タスク管理` シートで、サービス案ごとの検討の進捗をタスクとして管理します。今は1行ずつ手で追加します。

列は サービス案・タスク・本部・担当者・状況（未着手・対応中・完了）・メモ です（本部は担当者とセットで自由に入力）。
「サービス案」は、`リクエスト` に登録したリクエストを「SR-0001 会員の購買分析をしたい」の形（ID とリクエスト）で選ぶプルダウンです。

- 選択パネルでリクエストを追加すると、すぐに選べるようになります（削除したリクエストは選べなくなります）。長いリクエストは40文字で「…」と切ります。
- 候補は非表示の `__TASK_CHOICES` シートにスクリプトが書きます。手で書き換えないでください（書き換えても、パネルを開いたときなどに戻ります）。
- 選んだあとにリクエストの文が変わったときは、パネルを開いたときに同じ ID の今の文に書き換えます。
- 前の版（サービス案の名前で選んでいた）のタスクは、パネルを開いたとき（か `setupTaskSheet()` のとき）に、そのサービス案のリクエストが1件だけならそのリクエストに書き換えます。
  同じサービス案のリクエストが複数あるものはそのまま残り、セルの右上が赤くなります。件数が右下に出るので、プルダウンから選び直してください。
- リクエストを削除すると、そのリクエストを選んでいたタスクも、セルの右上が赤くなります（タスクは消えません）。必要なら選び直してください。

**用意する（管理者が1回）**：`setupTaskSheet()` を実行します。`タスク管理` シートが無ければ作り、見出しとプルダウンを付けます。
すでにシートがある場合は、見出しは書き換えず、足りない列だけを足します（本部は「タスク」のすぐ右＝担当者の左に、ほかは右端に）。入力済みのタスクは消えません。

**前の版のシートから移すとき**：前の版のシート（A〜C列が「サブインダストリー」「得意先」「案件名」の連動プルダウン）で `setupTaskSheet()` を実行すると、
その3列を削除してよいかを聞かれます。「はい」で3列を削除し、「サービス案」の列を左端に置きます。
D列以降（タスク・担当者・状況・メモ）の値はそのまま残り、左に詰まります。右端の「サービス」の列は「サービス案」に名前が変わって左端に移ります。
「いいえ」なら3列は残ります（使いません。不要になったら削除してください）。

**期限の列をやめたとき（2026/10）**：「期限」の列があるシートで `setupTaskSheet()` を実行すると、その列を削除してよいかを聞かれます。「はい」で削除します（入っている期限の値は消えます。ほかの列はそのまま）。「いいえ」なら残ります（使いません）。スプレッドシートの画面に出せないとき（エディタだけで実行）は聞けないので残します。

- 行の並べ替え・追加・削除は自由にしてかまいません（タスク管理シートは差分追跡の対象外です）。
- 列は見出しで探すので、列の並びは手で変えてもかまいません。
- 見出し・状況の選択肢は `TaskManagement.gs` の `TASK_OPTIONS` で変えられます。

### 会議サマリ（会議の事前資料のスライドと PDF）

RX Business Meeting（パイプライン会議）の事前資料（16:9 の Google スライドと PDF）を、サブインダストリー（追跡シート）ごとに作ります。
会議の前に配り、参加者が通読してから会議に臨むための資料です。

- 資料には、シートと変更の記録から分かる事実だけを書きます。論点・決めてほしいこと・支援の要否などは、各サブインダストリーのリーダーが会議で話すことなので、資料には入れません。
- 見出しはどのサブインダストリーでも同じで、状態は見出しの下のリード文に書きます。言葉の意味・数え方は `docs/DESIGN.md`（会議サマリの「数え方」）にあります。
- 緑を基調にしたトンマナです（表紙はいただいたひな形と同じ絵柄（緑のグラデーションに大きな「RX」）、扉は同じ絵柄のグレー、統合版の表紙も緑、表は緑の見出し）。
  Appendix のページは、扉に合わせて表の見出しなどをグレーにしています（ラベルの色はそのまま。`MTG_OPTIONS.appendixColors` を `null` にすると緑）。文はすべて自動で作ります。
  どのサブインダストリー・会議日の資料かは、いちばん下の出典の行に出ます（試作は【試作】）。データの時点と対象期間は表紙に出ます。
  配布する資料なので、言葉は書き言葉にそろえています（「前回から変化のある案件」「停滞案件」「入力内容の確認事項」など）。

表紙（会議の名前・サブインダストリー・会議日・出典（データの時点）・対象期間）のあとに、本編（5つのセクション。入りきらない表や「直近2か月の動き」はセクションの中のページが増えます）

1. サマリー：合計の数字（進行中案件・想定売上合計・期待値合計（どれも前回比）・入力内容の確認事項（項目の数と、案件・責任者の数））、
   前回以降の動き（今回のステータスごと：A 受注済み／B クロージング中／C 提案中・選定対応中・稟議対応中／D ヒアリング中・課題整理中／創注 仮検討／失注・保留・削除。
   名前の後ろに何が変わったか（「前回 C-提案中」・新規・受注月・期待値・活動更新）。案件ごとに1回だけ数えるので、合わせると変化のある案件の件数。
   2026/10/19 から区分（前進・後退・延期など）はやめ、ステータスで表します）と現在の状態（受注月超過／停滞（同一ステータス45日以上）／商談記録未登録）
   ごとの件数・想定売上・案件の名前。停滞は、前回以降に更新の無い案件だけ名前を出します（「うち前回以降の更新なし N件」）
2. 計画に対する積み上げ：今年度（4月〜3月）の売上開始月ごとの期待値を、左から月の順に積み上げた滝の図。月の段は確度
   （ステータスの「-」の前。A・B・C・D・創注。濃い緑ほど確度が高い。どれでもなければ灰色の「未設定」）で塗り分けます。最後に合計（確度別）・計画・計画との差
   （不足は ▲・灰色の点線、超えた分は +）。計画の高さに点線の横線を引くので、どの月で計画に届くかが分かります。リード文は合計・計画との差（達成率）・最大の月・確度A・B の割合。
   - 計画はサブインダストリーごとに 400百万円（33シナリオ ダッシュボードと同じ。`MeetingSummary.gs` の `MTG_OPTIONS.plan.amount`。シートごとに変えるときは
     `plan.plans` に `{'スーパー・GMS': 500}` のように書く）。統合版は全サブインダストリーの計画の合計（11シートなら 4,400）で、全サブインダストリーの状況の次のページです。
   - 売上開始月は、日付か「2026/09」の形の文字のときだけ月とみなします（パイプライン管理シート・ダッシュボードと同じ）。「26/09」「2026年度後半期」などの文字・空欄の案件と、
     今年度の外の案件、失注・保留の案件は積み上げに入れず、右に区切って「積み上げに含まない（参考）」として、時期未定・〜26/3（今年度より前）・27/4〜（来年度以降）・
     失注・保留の4本の棒（確度別の塗り分け。期待値と件数）で出します。リード文にはその合計の件数と期待値を書きます。月の列に出したいときは、売上開始月を日付で入れ直してください。
   - 使わないときは `plan.enabled` を `false` にします。
3. パイプラインの変化：前回からの期待値の増減（新規・期待値増・復帰・期待値減・受注・失注・保留・削除。受注は白抜き）と、
   ステータス別・受注月別（受注月超過・今の四半期〜4Q・来期以降・受注月未入力）の期待値
4. 前回から変化のある案件：サマリーの動きの表と同じ、今回のステータスの順（確度 A → 創注 → 失注・保留・削除。その中は想定売上の大きい順。区分の列は無し）に
   7件まで、ページに入る分だけ（活動状況が長いと6件など）。載せきれなければ、載せた件数と、全件は Appendix ① にあることをリード文に書きます。その他の項目だけ更新した案件は、件数だけ（「ほかに、その他の項目のみの更新 N件」）
5. 期待値上位案件の状況・課題：進行中の案件を期待値の大きい順に10件（入りきらなければ「（続き）」のページ。ステータスの滞留日数・受注月・活動状況・活動における課題・該当事項）。
   該当事項は、判定の中身をそのまま文で書きます（単語だけだと何を見て判定したか分からないため）：
   「ステータスが 52日 変わっていない（45日以上で停滞）」「受注月 2026/9 を過ぎても受注になっていない」「受注月を後ろにずらした記録 2回（過去180日）」。
   活動状況・課題は途中で切らずに全文を載せます（長いと文字を 7pt まで小さくし、それでも入らなければ行を伸ばします。1ページに入らない案件は「（続き）」のページに載ります）。
   シートに「RXシナリオ構成」の列（案件名の右の I列。プルダウンの複数選択。見出しが「RXシナリオ構成（サービス）」のシートも読む（`MTG_OPTIONS.columnAliases`）。J列は「サービス価格」）があれば、案件名の下に小さく選んだシナリオを「・」でつないで出します
   （空なら「RXシナリオ：未入力」。列の無いシートは今のまま）
   - 続けて「期待値上位案件の状況・課題（直近2か月の動き）」（同じセクションのページ。案件は同じ10件・同じ順）：変更の記録から、直近2か月（2か月前の同じ日から）の
     ステータス・受注月・期待値・活動状況・次回アクションの変更を、日付つきで新しい順に出します（同じ日の同じ項目の変更は1つにまとめ、活動状況などの文は書き足した部分だけ。

   - 変更の記録が始まった日より前の動きは出ません（リード文に「変更の記録は M/d からのため、それより前の動きは出ない」と書きます。2か月分がそろうまで）。

活動状況などの長い文：期待値上位案件の状況・課題と Appendix ①・② は全文を載せます。前回から変化のある案件は、文字を小さくしても入らなければ「…」で切ります（全文は Appendix ①）。

2. Apps Script のエディタの左の「プロジェクトの設定」（歯車）→ いちばん下の「スクリプト プロパティ」→「スクリプト プロパティを追加」で、
   プロパティ `MTG_TEMPLATE_URL`、値にその URL を入れて「スクリプト プロパティを保存」します（エディタで `setMeetingTemplate()` を実行して URL を貼り付けてもよい）。
3. `previewBusinessMtgSummaries()` で、表紙・扉を確かめてください。
   .pptx なら、最初に作るときに Google スライドに変換し（保存先のフォルダに「会議サマリのひな形（表紙.pptx から変換）」ができる）、それを使います。
   .pptx を差し替えて更新したら、次に作るときに変換し直します（前に変換したものはゴミ箱へ）。変換したものは消さないでください（消したら、次に作るときに変換し直します）。

- 1枚目は各サブインダストリーと統合版の表紙、2枚目は扉（Appendix）に使います（`MTG_OPTIONS.templatePages`）。3枚目（紫）は使いません
  （統合版の表紙を紫にするときは `templatePages.combined` を 3 に、`MTG_OPTIONS.combined.coverTone` を `'combined'` にする）。2枚目が無ければ扉はグレーの絵柄で描きます。
- 決まった文字を、文字の枠ごとに書き換えます：大きい `XXXXX`（見出し）→ サブインダストリー（統合版は「全サブインダストリー」、扉は「Appendix」）、
  小さい `XXXXX`（その下）→ 「RX Business Meeting　事前資料」（試作は【試作】。扉は空）、`2026年 4月 17日` → 会議日（扉は空）、`XXXX` → 空。
  ひな形を直すときは、この文字をそのまま残してください（変えたら `MTG_OPTIONS.templateTexts` も合わせる）。字の大きさ・位置・色・字体は、ひな形のとおりになります。
- 本編・Appendix は、ひな形のページの大きさ（いただいたひな形は 960 × 540pt）に合わせて拡大して描きます。
- ひな形のファイルは、管理者（`createBusinessMtgSummaries()` を実行する人）が開けるところに置いてください。別のファイルにしたら、`MTG_TEMPLATE_URL` の URL を書き換えます。
- `MTG_TEMPLATE_URL` を消す（`setMeetingTemplate()` で空欄）と、ひな形なしで作ります（表紙・扉はひな形と同じ色の画像を背景に描く）。
  スクリプトのプロパティなので、コードを貼り直しても消えません（前の版の `setMeetingTemplate()` の登録（ドキュメントのプロパティ `MTG_TEMPLATE_ID`）は、`MTG_TEMPLATE_URL` が空のときだけ使う）。

**予定（会議の2日前に配る）**：

参加者が会議の前に通読できるように、**会議の2日前に配ります**。入力の締切は3日前です（例：金曜 9:00 の会議）。

| いつ | だれが | すること |
|---|---|---|
| 会議の週の月曜（締切の前） | 管理者 | `previewBusinessMtgSummaries()` で試作し、Appendix ③ の入力内容の確認事項を各営業リーダーに伝える |
| 火曜 17:00（3日前） | 各営業リーダー | 入力の締切。確認事項を直す（ステータス・期待値・受注月・活動状況は締切までに） |
| 水曜の午前（2日前） | 管理者 | `createBusinessMtgSummaries()` で本番を作り、中身を確かめて、`notifySubBusinessMtgSummaries()` でサブインダストリーごとの Google チャットに知らせる |
| 金曜 9:00 | 参加者 | 通読してから会議に臨む |

- **配ったあとは作り直さないでください**。本番を作ると、その時刻が次の会議の資料の起点になります。作り直すと起点が動き、配った版と作り直した時の間の変化は、どの資料にも出なくなります
  （作り直したときは、作り直した版を配り直してください）。締切のあとの入力は、次の会議の資料に「前回からの変化」として出ます。
- **配るのは PDF です**（文は事実だけ）。2026/10 から Google スライドは残しません（`MTG_OPTIONS.keepSlides: false`。PDF を作ったあとゴミ箱に移す）。
  推進リーダーが説明を書き足す運用にするときは `keepSlides` を `true` にし、配る前に Google スライドに書き足して「ファイル」→「ダウンロード」→「PDF」で書き出したものを配ってください。
  説明や判断は、会議でリーダーが話すのが基本です。
- **保存先のフォルダ**（`MTG_OPTIONS.folderId`。今は指定のフォルダ）には、試作の PDF（と、`keepSlides` が `true` なら編集できる Google スライド）も入ります。参加者に共有するときは、そのことに注意してください。
  実行するアカウント（管理者）が、そのフォルダに書き込める必要があります。
- **「案件ステータス」「受注月」の列は数式にしないでください**（数式で計算された値の変化は変更の記録に残らないため）。
  「期待値調整済想定売上規模」は数式でかまいません（スーパー・GMS は `想定売上 × 定義_ステータスの率`）。前回の期待値は、変更時点スナップショット（その時点の計算した値）から取り、
  無いときはシートの数式と同じ計算をします。

**エディタから実行するとき**：会議サマリの関数は、入力・確かめの画面をスプレッドシートに出します。スプレッドシートを開いたまま、そのスプレッドシートの
「拡張機能」→「Apps Script」から開いたエディタで実行し、画面はスプレッドシートのタブで答えてください（エディタを script.google.com から直接開くと、
「スプレッドシートの画面に、入力・確かめの画面を出せません」と出て止まります）。`setBusinessMtgBaseline()` だけは、画面に出せないときも
確かめずにすべての追跡シートに基準を記録し、結果を実行ログに書きます。

**会議の日程を先に出す（Google カレンダーから）**：エディタで `importMeetingSchedules()` を実行すると、Google カレンダー（実行する人の既定のカレンダー。
`MeetingSchedule.gs` の `MSCH_OPTIONS.calendarId` で変えられる）の、今日の365日前〜400日後の予定から、名前に「RX Business Meeting」「RX Business MTG」
「RX Service Meeting」「RX Service MTG」などを含む予定（`MSCH_OPTIONS.titles`。全角・半角・空白の違いは無視。断った予定・「中止」の付いた予定は読まない）を探し、
`INDEX_会議資料` に会議日と会議名の行を足します（ある行はそのまま。何度実行してもよい）。資料を作る画面の「カレンダーから読み込む」でも同じことをします。
- 初めて実行するときは、Google カレンダーを読む権限の承認を求められます。承認したら `reinstallDiffTriggers()` を実行してください（権限が変わったため）。
- カレンダーで日を変えた会議は、新しい日の行を足し、前の日の行は残します（資料が無ければ、手で消してかまいません）。

**作るとき**：

1. エディタで `createBusinessMtgSummaries()` を実行すると、スプレッドシートに「会議サマリを作る」画面が出ます。
2. **会議日程**をプルダウンで選びます（`INDEX_会議資料` の RX Business Meeting の日程。初めは今日以降でいちばん近い会議日。作成済みの日には「作成済み」）。
   一覧に無いときは「カレンダーから読み込む」を押すか、「一覧に無い日を入力…」で日付を選びます。
   **比べる時点**も選べます（初めは「前回の会議（自動）」。シートごとに、前回の資料を作った時点の値と比べる）。選んだ時点は、選んだすべてのシートに使います：
   - 見出し「時点コピー」の下：保存先のフォルダ（下の「時点コピー」）にある時点コピー（その時点のシートの値）と比べます。
     「2026/10/16 18:30（資料作成時・会議日 10/23・11シート）」は本番の資料を作ったとき、「（日次）」は毎日のコピー、「（基準）」は `setBusinessMtgBaseline()` のときに保存したものです
     （前々回の会議からの変化・先週の月曜からの変化を見たいときなど）。コピーに無いシートは、その時刻から変更の記録で比べます。
   - 見出し「会議日から」の下：「○月○日 の会議日（0時）から」は、その日の 0時から変更の記録で比べます。
   - 「日時を指定…」：指定した日時から、変更の記録で比べます（変更の記録が始まる前の変化は出ません。確かめの文に出ます）。
   候補は、選んだ会議日より前のものだけ出ます。前回と違う時点を選ぶと、資料の「前回比」「前回から変化のある案件」などは「10/9比」「10/9以降に変化のある案件」のように、
   その時点の日付で書きます（対象期間に「（選んだ時点）」）。会議日の記録・次の会議の起点は変わりません（本番なら今の値を保存し、次の会議はそれと比べます）。
3. **作る資料**（シート）を選びます（初めはすべて。前回の資料の会議日も出ます）。
   **サブインダストリーごとに作ってもかまいません**（1つだけ選ぶと、そのシートだけ作る。会議日の記録・時点コピー・会議のフォルダへの格納・インデックスも
   そのシートの分だけ）。本番なら終わりの画面に、この会議日の本番の資料がまだできていないサブインダストリーが出ます。すべてそろうと、統合版の作り方を案内します。
4. 「次へ（確かめる）」を押すと、確かめの文が出ます：会議日（曜日）、シートごとの対象期間（前回の会議の資料を作った時・基準・直近14日間のどれからか。
   前回の資料の記録が無くても、会議日程の一覧に前の会議日があれば、その会議日から）、同じ会議日の資料を作成済みならその日時。
   合っていれば「本番として作成する」を押します（「戻る」で選び直せます。「閉じる」なら作らず、会議日も記録しません）。作り終えると、画面に結果が出ます。
5. 保存先のフォルダ（`MTG_OPTIONS.folderId`。指定が無ければスプレッドシートと同じフォルダの中の「会議サマリ」フォルダ）に、
   シートごとに `会議日（yyyyMMdd）_サブインダストリー名_RX Business Meeting用資料.pdf`（例：`20261023_スーパー・GMS_RX Business Meeting用資料.pdf`）が
   保存されます（`MTG_OPTIONS.fileName`。Google スライドは PDF を作るためだけに使い、残さない）。同じ名前の古い版（作り直す前のもの）はゴミ箱に移します（30日間は戻せます）。
   PDF は、**会議のフォルダ**（下の「会議のフォルダへの格納」）に移して格納します（保存先と会議のフォルダに同じ PDF を2つ置かない。格納できなければ保存先に残る）。
   スプレッドシート全体を、別のスプレッドシート「時点コピー_実行日時（資料作成時・会議日 …）」にコピーします（下の「時点コピー」）。
   次の会議の資料の「前回からの変化」は、このコピーと比べて出します（差分追跡が止まっていた間の変更も出る）。コピーは消さないでください。
   終わると、シートごとの PDF の URL と件数（変化のある案件・停滞・確認事項）、保存先のフォルダの URL、コピーの URL が出ます。
   中身を確かめてから配ってください。文は数から決まった言い回しです。
6. 中身を確かめたら、`notifySubBusinessMtgSummaries()` でサブインダストリーごとの Google チャットに知らせます（下の「サブインダストリーごとの Google チャットへの通知」）。

- 前回の時点コピーと比べたときは、終わりの画面に「前回からの変化は「時点コピー_…」と比べました。」と出ます。

**時点コピー**：スプレッドシート全体（すべてのシート・数式・書式・プルダウン）を、別のスプレッドシート「時点コピー_保存した日時（いつ保存したか）」にコピーしたものです。
資料の変化は、比べる時点の時点コピーの追跡シートと今のシートを比べて出します。スプレッドシートの控え（復旧用）にもなります。
- 追跡シートの数式（No.・期待値）は同じファイルの中のシート（定義_ステータス）だけを参照するので、コピーでも保存した時点の値のままです。
- 「得意先マスタ」の IMPORTRANGE は、コピーでは「アクセスを許可」するまで #REF! になります（比較には使いません。控えから戻すときだけ許可してください）。
- コピーにはスクリプトも入ります（トリガーは入らないので、勝手には動きません。開くとメニューは出ます）。コピーでは関数を実行しないでください。
- すべてのシート（変更の記録・クレデンシャルの記録も）が入るので、保存先のフォルダは共有しないでください。
- **戻すとき**：時点コピーを開き、戻したいシートのタブを右クリック →「別のワークブックにコピー」→ このスプレッドシートを選び、値を必要なところに写します
  （追跡シートに貼り付けると変更として記録されます。2,000セルを超える貼り付けは記録されないので、少しずつ貼るか、あとで `diagnoseDiffState()` で確かめてください）。
- 保存先：`MTG_OPTIONS.copyFolderId` のフォルダ（空なら保存先のフォルダの中の「時点コピー」フォルダ。前の版で作った「会議時点のコピー」フォルダは、そのまま使います）。
- タイトルの（）で、いつ保存したかが分かります（`MTG_OPTIONS.copyKinds`）：
  - `（資料作成時・会議日 2026-10-23）`：本番の資料を作ったとき（`createBusinessMtgSummaries()`）。次の会議の資料はこれと比べます。
  - `（日次）`：毎日（下の「日次の時点コピー」）。
  - `（基準）`：`setBusinessMtgBaseline()`・旧フォーマットからの転記のとき。
- 前の版の名前「会議時点のコピー_…（会議日 …）」のファイルも、資料作成時の時点コピーとして選べます（名前を変えなくてかまいません）。
- 資料を作る画面の「比べる時点」には、このフォルダの時点コピーがすべて出ます（新しい順）。資料作成時・基準のコピーは消さないでください（次の会議の資料の比較の相手）。

**日次の時点コピー**：毎日、スプレッドシート全体を時点コピー（日次）にコピーし、比べる時点として選べるようにします（毎日の控えにもなります）。
1. 管理者のアカウントでエディタから `installDailySheetCopy()` を実行します（毎日 5時台に `saveDailySheetCopy` を動かすトリガーを1つ作る。何度実行しても増えない）。
2. すぐに1つ保存するときは `saveDailySheetCopy()` を実行します。
3. 90日（`MTG_OPTIONS.dailyCopy.keepDays`）より古い日次のコピーは、保存のたびにゴミ箱に移します（資料作成時・基準のコピーは消しません）。時刻は `dailyCopy.hour`。
4. やめるときは `uninstallDailySheetCopy()`（トリガーを外す。保存したコピーは残る）。
  「変更の記録が無い変更 N件」と出たら、その間に差分追跡が止まっていた可能性があります。`diagnoseDiffState()` で確かめてください（資料には出ています）。
- 初めて本番を作るとき・コピーの機能を入れたあと初めて作るときは、前回のコピーが無いので、今までどおり変更の記録から出します。
- 会議日と作った日時は、シートごとに記録します（同じ会議日で作り直しても、「前回から」は変わりません）。前回の会議の記録が無ければ、直近14日の変化です。
- 会議日を打ち間違えた・本番を作ったが会議が無くなったときは、`removeBusinessMtgRecord()` で、その会議日の記録を取り消します（資料のファイルは消しません。要らなければドライブで消す）。
**会議のフォルダへの格納**：サブインダストリーごとのフォルダ（中に `260819_RX Business Meeting_第4回` のような会議ごとのフォルダがある）を、
`test.gs` の `DIFF_RULES` の各シートの `meetingFolder` に URL で書いておきます。本番の資料を作ると、その中の、名前が会議日の `yyMMdd_` で始まり、
会議の名前（RX Business Meeting）を含むフォルダ（10/23 なら `261023_RX Business Meeting_…`）に PDF を移します（同じ名前の古い版はゴミ箱へ。試作は移しません）。
会議のフォルダが無ければ `261023_RX Business Meeting_第5回` のように作ります（第何回かは、前の同じ会議のフォルダの回数＋1。作りたくないときは `MTG_OPTIONS.createMeetingFolder` を `false`）。
RX Service Meeting の資料も、同じフォルダの中の `261113_RX Service Meeting_第3回` のようなフォルダに入ります（第何回は会議ごとに数えます）。
会議の名前を含まない前の版のフォルダ（`261023_第5回会議`）は、RX Business Meeting のフォルダとして使い続けます（名前を直してもかまいません）。
回数が合わないときは、作られたフォルダの名前をドライブで直してください（先頭の `yyMMdd_` と会議の名前で探すので、ほかは変えてかまいません）。

- 今はテストのため、11シートとも `test.gs` の `TEST_MEETING_FOLDER`（資料の保存先と同じフォルダ）にしています。
  本番のフォルダが決まったら、各シートの `meetingFolder` をそれぞれのフォルダの URL に書き換えます。

- 終わりの画面に「会議のフォルダ「261023_RX Business Meeting_第5回」に格納しました」と出ます。
- 格納できなかったとき（`meetingFolder` が空・フォルダを開けない・会議のフォルダがまだ無い・同じ日付のフォルダが2つある・書き込めない）は、
  「※ 会議のフォルダに格納できませんでした（理由）」と出ます。資料は保存先のフォルダにあり、会議日も記録しています（作り直さなくてよい）。
  理由を直して（会議のフォルダを作るなど）、エディタで `storeBusinessMtgSummaries()` を実行し、シートと会議日を入力すると、保存先の本番の PDF を会議のフォルダに移します
  （もう会議のフォルダにあれば、インデックスだけ書き直します）。

**統合版（全サブインダストリーの資料）**：すべてのサブインダストリーの資料を `createBusinessMtgSummaries()`（試作なら `previewBusinessMtgSummaries()`）で作ったあとに、
エディタで `createBusinessMtgCombinedSummary()` を実行し、画面で会議日程を選ぶと、全サブインダストリーの資料を1つにまとめた資料
（`20261023_全サブインダストリー_RX Business Meeting用資料.pdf`）を作ります（資料を作る関数とは分けてある。1回の実行の6分の上限に収めるため）。
本番の資料がすべてのサブインダストリーでそろうと（一度に作っても、サブインダストリーごとに作っても）、終わりの画面で案内します。

- 中身：表紙（緑）→ 目次（各サブインダストリーの表紙のページ。名前かページ番号を押すと、そのページに移る。ブラウザの Google ドライブのプレビュー画面では
  リンクは動かないので、ダウンロードして Acrobat などで開く。目次にもそう書いてある）→「全サブインダストリーの状況」（サブインダストリーごとの進行中案件・期待値合計・増減・変化のある案件・停滞・確認事項と、その資料のページ。合計つき）→
  「計画に対する積み上げ（全サブインダストリー）」と、その2ページ目「計画に対する積み上げ（サブインダストリー別）」（達成率の高い順の横棒（確度別）と計画の点線、
  積み上げ・達成率・計画との差・確度A・B の割合・時期未定。合計つき）→
  各サブインダストリーの資料（個別の資料の表紙と本編。扉と Appendix ①〜③ は入れません。全件の一覧は各サブインダストリーの資料で見ます。`DIFF_RULES` の順）。
  ページ番号は資料全体の通し番号です。
  中身はそのときのシートの値で作り直します（前回からの変化は、個別の資料と同じく前回の会議時点と比べる）。資料を作ったあとにシートを直したら、その分は統合版にだけ出ます。
- すべてのシートにその会議日の本番の記録があれば本番として、`MeetingSummary.gs` の `MTG_OPTIONS.combined.meetingFolder` のフォルダの中の会議のフォルダ
  （`261023_RX Business Meeting_第5回` など。無ければ作る）に格納し、インデックスの「全サブインダストリー」の列に書きます。今はテストのため、各サブインダストリーと同じテストのフォルダにしています
  （本番のフォルダが決まったら URL を書き換える）。会議日・時点コピーは記録しません。
- 実行の条件：すべてのサブインダストリーに、その会議日の本番の資料（PDF）があること（「INDEX_会議資料」のその会議日の行に空のセルが無いこと）。
  足りないときは「統合版を作れません。…まだできていないサブインダストリーがあります」と、足りないサブインダストリーを出して、何も作らずに終えます（試作も作りません）。
  `createBusinessMtgSummaries()` で本番の資料を作ってから、もう一度実行してください。
- 個別の資料を作り直したあとに統合版も合わせるときも、これを実行します。
- 資料を自動で続けて作っている途中（下の「6分の上限」）は実行できません。`showBusinessMtgSummariesResult()` で終わったのを確かめてから実行してください。
- 格納できなかったときは、`storeBusinessMtgSummaries()` で「全サブインダストリー」（シートの一覧のいちばん下）を選ぶと格納します。
- 作らないときは `MTG_OPTIONS.combined.enabled` を `false` にします。

**RXシナリオ構成別の期待値（試作の別の資料）**：RXシナリオ構成（I列）の中身が決まるまでは、事前資料には入れず、別の関数で作ります。
エディタで `createBusinessMtgScenarioSummary()` を実行し、シートの番号を入力して（空欄ならすべて）、確かめの画面で「はい」を押すと、
保存先のフォルダ（会議のフォルダではない）に `20261021_RXシナリオ構成別の期待値_試作.pdf` を作ります。会議日の記録・会議のフォルダ・インデックスは変えません。

- 対象は進行中の案件（受注・失注・保留は除く）の期待値です（期待値が空の案件は 0 として件数に入れる）。「RXシナリオ構成」（または「RXシナリオ構成（サービス）」）の列が無いシートは除き、確かめの画面に出します。
  選んだシートのどれにも列が無ければ止めます。
- 複数選んだ案件の数え方（同じ案件を2つのシナリオに満額で数えると、合計が期待値合計より大きくなるため、次の3つを並べて出します）：
  - **按分**：期待値を選んだシナリオの数で等分して配る（「A, B」で 10 なら A に 5・B に 5）。シナリオの合計が期待値合計と一致するので、構成比・計画との比較に使います。
  - **関与（重複あり）**：そのシナリオを含む案件の期待値をそのまま合計（A にも B にも 10）。そのシナリオが関わる案件の大きさを見るときに。足し合わせると期待値合計より大きくなります。
  - **件数・うち単独**：そのシナリオを選んだ案件の数と、そのシナリオだけを選んだ案件の数。
  - 空欄の案件は「未設定」（いちばん下・灰色）にまとめます。プルダウンの選択肢に無い値（手で入れたものなど）も、そのまま1つのシナリオとして数えます。
- 中身：表紙（緑。「参考資料【試作】」）→ 全サブインダストリー（シナリオごとの按分の横棒（確度別の塗り分け）と、按分・関与・件数・うち単独）→
  サブインダストリー別（サブインダストリー × シナリオの按分の表。行の合計はそのサブインダストリーの期待値合計）→
  組み合わせ（選ばれた組み合わせ（単独も）ごとの件数・期待値（按分しない）・主な案件。期待値の大きい順に15件まで）。
- 区切りは、プルダウンの複数選択が入れる「,」（と改行）です。設定は `MeetingSummary.gs` の `MTG_OPTIONS.columns.scenario`（列の見出し）と `MTG_OPTIONS.scenario`。
- 構成が決まって事前資料に入れるときは、この資料のページ（全サブインダストリー・サブインダストリー別）を統合版や各サブインダストリーの資料に組み込みます。

**6分の上限（区切って自動で続ける）**：Apps Script の1回の実行は6分までです（入力・確かめの画面を出している時間も含む）。11シートの資料と格納・インデックスは
6分近くかかるので、`createBusinessMtgSummaries()`・`previewBusinessMtgSummaries()` は、次の仕事（資料1つ・時点コピーと会議日の記録・格納1つ）が
上限を越えそうなら、そこで区切って、残りを約1分後に自動で続けます（時間主導のトリガー `continueBusinessMtgSummaries`。1回きりで、終わったら消える）。

- 区切ったときは、終わりの画面に「時間がかかるため、ここで区切りました。…残りは約1分後に自動で続けます：…」と、そこまでに作った資料が出ます。
- 続きが終わったら、エディタで `showBusinessMtgSummariesResult()` を実行すると、ふだんの終わりの画面と同じ結果が出ます（途中なら進み具合）。実行ログにも出ます。
- 本番の会議日の記録・時点コピーは、資料を全部作れてから行います（作り始めた時刻で記録するので、区切っても対象期間は同じ）。
- 続いている途中に `createBusinessMtgSummaries()` などを実行すると、「やめて、新しく作りますか？」と聞きます（「はい」なら続きをやめて、新しく作る）。
- 続きが途中で止まったら（エラー）、`showBusinessMtgSummariesResult()` に「途中で止まりました：（理由）」と出ます。作り直してください。
- 区切る目安は `MTG_OPTIONS.run`（上限 `limitMs` 320秒、資料1つ 35秒などの見積もり）です。

- 会議名（B列）は「RX Business Meeting」か「RX Service Meeting」（2026/10/17 に見出しを「種別」から「会議名」に改めました。前の見出しのシートは、次に書くときに書き換えます）。

  （`MeetingSummary.gs` の `MTG_OPTIONS.columns.delivery` が空）。列を作ったら、その見出しを `columns.delivery` に書くと出るようになります。

**サブインダストリーごとの Google チャットへの通知（webhook）**：

サブインダストリーごとのスペースに、次の2つを別々に送れます（どちらもエディタから実行。確かめの画面（送り先と、1つ目のシートに送る文）で「はい」を押すと、すぐに送ります。自動では送りません）。

1. 最初に1回（管理者）：`setBusinessMtgSubChats()` を実行し、シートの番号（空欄ならすべて）を選んで、シートごとに webhook の URL を貼り付けます
   （空欄なら今のまま、「削除」と入力すると外す）。最後に、登録したスペースへ確かめのメッセージを送れます。
2. `remindBusinessMtgUpdate()`：**管理フォーマットの更新のお願い**。会議日（空欄なら会議日程の一覧の次の会議）とシートを選びます。
   文には、会議日程・更新の締め切り（会議日の2日前の 17:00。`MTG_OPTIONS.subChat.deadlineDays`・`deadlineTime`）・更新していただきたい項目・
   今の入力状況（進行中の案件の数と、必須項目が未入力・受注月を過ぎている・最終更新から30日以上たっている案件の数。0件のものは書かない）・管理フォーマットのシートのリンクが入ります。
3. `notifySubBusinessMtgSummaries()`：**事前資料のご案内**。会議日とシートを選ぶと、その会議日の本番の事前資料（会議のフォルダの PDF）のリンクを、

- 2つの文は同じ形です（題「【RX Business Meeting】 …（サブインダストリー）」、1行目に会議日程と会議の名前、太字の「▼ 見出し」）。
  事前資料のご案内は、レビュアーの方々（ご一読いただきレビュー観点を整理）と発表者の方々（発表内容のご準備）へのお願い・会議日程・事前資料のリンク、
  更新のお願いは、更新期限・更新していただきたい項目・今の入力状況・会議日程・管理フォーマットのリンクです。
- 文は `MTG_OPTIONS.subChat.remind`・`summary` で変えられます（`{meeting}`・`{name}`（サブインダストリー）・`{date}`・`{deadline}`・`{now}`・`{stats}`・`{sheet}`・`{file}`）。
- webhook の URL はスクリプトのプロパティ（`MTG_SUBCHAT_` ＋ シート名）に残します（コードやシートに書かない。画面・ログにも鍵は出しません）。
- 送れなかったスペースがあっても、ほかのスペースには送り、終わりの画面に理由を出します。
- Google チャットへの通知は、この2つ（`remindBusinessMtgUpdate()`・`notifySubBusinessMtgSummaries()`）だけです（2026/10/19 に、全体のスペースへの通知
  `notifyBusinessMtgSummaries()`・`setBusinessMtgChat()` はやめました。前の版の設定（スクリプトのプロパティ `MTG_CHAT_WEBHOOK`・`MTG_CHAT_URL`）と
  自動通知のトリガー（`mtgNotifyScheduled`）は、`setBusinessMtgSubChats()` を実行したときに消えます）。

**案件の行を足す（`addDealRows()`）**：

追跡シートは No.・期待値の列が3行目の数式で最後の行（76行目など）まで計算し、プルダウンも最後の行まで付いています。
最後の行の下に行を足すと、足した行には数式もプルダウンも届きません。`addDealRows()` はほかに影響しない位置に行を足します。

1. エディタで `addDealRows()` を実行し、シートの番号（空欄ならすべて）と足す行の数（1〜500）を入力します。
2. 数式の範囲の最後の行の**上**に足すので、数式・プルダウン・条件付き書式の範囲が一緒に伸びます。足した行の書式・プルダウンは、すぐ上の行と同じにします。
3. 最後の行に案件が入っていれば、その案件を足した行の上に動かします（空の行が案件の間に入らないように）。
4. 変更履歴には何も記録しません（空の行・動かしただけの行は記録しない）。差分追跡は止まりません。

**旧フォーマットから案件を転記する（`migrateLegacyDeals()`）**：

旧フォーマットのスプレッドシートの「案件_{サブインダストリー名}」シートの案件を、同じ名前のシートに転記します（`LegacyMigration.gs`）。

1. スプレッドシートの「拡張機能」→「Apps Script」から開いたエディタで `migrateLegacyDeals()` を実行し、旧フォーマットのスプレッドシートの URL を貼り付けます
   （実行するアカウントが閲覧できること。中身は実行した人の環境で読むだけです）。
2. シートごとの件数（と、選択肢に無いため空欄にするセルの数）が出ます。「はい」で転記します。**転記するシートの今の行は消えます（上書き）**。
3. 列は見出しで対応させます：得意先・案件名・先方部門・先方担当役職・先方担当氏名・提案開始日・活動状況・次回アクション・想定売上規模（百万）・受注月・売上開始月は同じ見出しへ、
   営業担当 → アカウント責任者、ステータス → 案件ステータス。サブインダストリーにはシートの名前を入れます。
   No.・期待値（数式の列）は書きません。企画担当・提案シナリオ・マーケなどの配分・サービス配分チェック・備考は転記しません（`MIG_OPTIONS.columns`）。
   旧に無い列（RXシナリオ構成・サービス価格・活動における課題・商談記録・BX部署など）は空欄になります。提案シナリオは RXシナリオ構成のプルダウンの選択肢と違うので入れません。
   シートの列の並びが変わっても（2026/10/26 に4列を消して A〜AA になった）、見出しで対応させるのでそのまま使えます。
4. 得意先マスタに無い得意先・定義に無いステータスは書けないので空欄にし、終わりの画面と実行ログにセルの位置と旧の値を出します。
   得意先マスタなどに足してから、もう一度実行すると入ります（何度実行しても、上書きなので同じ結果になります）。
5. 転記したあと、差分追跡の比較基準を取り直し（転記を変更として記録しない）、会議サマリの基準を記録します（下の「基準の記録」を自動で行う）。
- 旧のシートが無いサブインダストリーは転記せず、そのままです。旧の案件の数がシートの行より多いときは、そのシートは転記しません（行を足してからもう一度）。

**旧フォーマットから案件を移したとき（基準の記録）**：

案件をまとめて貼り付けると、貼り付けた行は「前回より後に追加された案件」になり、次の資料ですべて「新規」に数えられます（期待値の増減の「新規」も大きくなります）。
シートの列や期待値の数式を作り替えたときも、前回の値に作り替えの途中の値が使われ、ステータスが同じでも期待値の増減が出ます
（2026/10/5 にスーパー・GMS を作り替えたため、基準を記録しないまま最初の資料を作ると、10/2 ごろの値と比べた増減が出ます）。
これを避けるため、移行・作り替えが終わったら基準を記録してください。

1. 追跡シートに列を足した・消したときは、先に `DIFF_RULES` を確かめて `setupDiffTracking()` を実行します（列を足すと、そのシートの差分追跡は止まります）。
2. 旧フォーマットから案件を貼り付けます。
3. 貼り付けがすべて終わったら、エディタで `setBusinessMtgBaseline()` を実行し、シートの番号を入力して「はい」を押します（空欄ならすべてのシート）。
   スプレッドシートの画面に出せないとき（エディタをスプレッドシートから開いていないなど）は、聞かずにすべての追跡シートに記録し、結果を実行ログに書きます。
4. 次に作る会議サマリは、基準より後の変化だけを出します（期間は「基準（MM/dd HH:mm に記録）以降」）。基準より後に会議の資料を作ったら、その次からは前回の会議からに戻ります。

- 基準はシートごとに1つです。もう一度実行すると、今に置き換えます。会議日は記録しません。
- 貼り付けた案件の停滞の日数は、貼り付けた時から数えるので「N日以上」と出ます（旧フォーマットでいつからステータスが同じかは、記録に無いため）。
  最終更新日時も貼り付けた時になるので、「更新なし」は貼り付けてから30日たつまで出ません。

### RX Service Meeting の事前資料（サービス改善の会議のスライドと PDF）

RX Service Meeting（サービス改善。第二週の金曜）の事前資料を、「サービスリクエスト」と「サービス案タスク管理」のシートから、サブインダストリーごとに作ります
（全サブインダストリーをまとめた資料も作れます）。紫を基調にしたトンマナで、表紙はひな形の3枚目（紫）です（ひな形が無ければ同じ絵柄で描きます）。書くのはシートから分かる事実だけです。

表紙のあとに、サマリー（数字と前回比・前回以降の動き・議題と資料のページ）→ サービス案の一覧 → 顧客・業界の広がり（サービス案 × サブインダストリー）→
サービス案（1つずつ。元になったリクエスト・サービス部門からのフィードバック・案件のステータスと期待値・タスク）→ 判断待ちのリクエスト、扉のあとに
Appendix ① リクエスト・② タスク・③ 入力内容の確認事項。

- サブインダストリーの資料には、そのサブインダストリーの案件のリクエストと、それを含むサービス案が載ります。サービス案のタスクと、ほかのサブインダストリーへの広がりは、サービス案全体を載せます。
- サービス案は、リクエストの「サービス案」に入れた名前でまとめます（同じ名前のリクエストが1つのサービス案。判断が「棄却」のリクエストは数えない）。
- タスクは、タスク管理の「サービス案」（「SR-0001 …」）の ID でサービス案に結び付けます。
- 期待値は、リクエストの元になった案件（得意先＋案件名）全体の期待値です。サービスの売上ではありません。

**作る（管理者がエディタから）**：

1. `ServiceMeeting.gs`・`MeetingSummary.gs`・`サンプルデータ.gs` を貼り付けて保存します（Google Slides API の拡張サービスは会議サマリと共通）。
2. データがまだ無いときは、`addServiceMtgSampleData()` でサンプルのリクエスト13件・タスク7件を入れます（下の「サンプルで試す」）。
3. `previewServiceMtgSummaries()` を実行すると画面が出ます。会議日程（`INDEX_会議資料` の RX Service Meeting の日程。先に `importMeetingSchedules()` で
   カレンダーから読み込んでおく）をプルダウンで選び、作る資料（初めは、リクエストのあるサブインダストリーすべてと全サブインダストリー）を選んで作ります。
   **比べる会議**も選べます（初めは前回の会議。本番の資料を作って記録した会議の、その時点の判断・タスクの状況・件数と比べる。前回と違う会議を選ぶと、資料は
   「選んだ会議（10/9）以降の動き」「10/9比」のように書きます）。
   試作の PDF（`…_スーパー・GMS_RX Service Meeting用資料_試作.pdf` など）が会議サマリの保存先にできます。会議日は記録しません。
4. 本番は `createServiceMtgSummaries()`。画面で選び、確かめの文（会議日・前回の会議・作る資料）を見て「本番として作成する」を押すと、PDF を保存して「INDEX_会議資料」の会議名「RX Service Meeting」の行の、
   そのサブインダストリー（全サブインダストリー）の列に書き、すべて作ったら会議日とその時点の判断・タスクの状況・件数を記録します。
   次の会議の資料は、今回からの変化（新規リクエスト・判断の変更・完了したタスク・新しいタスク）と前回比を出します。
5. 6分に収まらないときは区切って、約1分後に自動で続けます（トリガー `continueServiceMtgSummaries`）。結果は `showServiceMtgSummariesResult()` で見られます。

- 同じ会議日で本番を作り直すと、記録を置き換えます（次の会議の起点が今になります）。配布したあとは作り直さないでください。
- 本番の PDF は、RX Business Meeting と同じフォルダ（各サブインダストリーの `meetingFolder`、全サブインダストリーは `MTG_OPTIONS.combined.meetingFolder`）の中の、
  `261113_RX Service Meeting_第3回` のような会議のフォルダに格納します（無ければ作ります。第何回は RX Service Meeting のフォルダだけで数えます）。
- 議題と見るページの対応・色は `SMTG_OPTIONS`（`agenda`・`colors`）で変えられます。

**サンプルで試す**：

1. `addServiceMtgSampleData()` を実行し、確かめの画面で「はい」を押します。「サービスリクエスト」と「サービス案タスク管理」の最後の行の下に、サンプルを書きます
   （リクエストの先頭に「【サンプル】」。ID は続きの番号。得意先・案件名は各サブインダストリーのシートの進行中の案件を使い、案件が無いシートでは「サンプル○○」の架空の名前）。
   タスクは、進捗状況・開始日／終了日（予定・実績）の列にも入ります（日付は今日から前後の日。完了は実績の開始・終了、対応中は実績の開始まで）。
   ほかにシートに足した列があれば、終わりの画面に「サンプルを入れていない列」として出ます（`サンプルデータ.gs` の `SMP_OPTIONS.service.taskExtraColumns` に足すと入ります）。
   架空の名前のリクエストは、資料の Appendix ③ に「元の案件が見つからない」と出ます。主管本部・担当者の無いサービス案・サービス案の無いリクエスト・担当者の無いタスクも、
   確認事項の見本としてわざと入れています。
2. `previewServiceMtgSummaries()` で資料を作って確かめます（出典の行と表紙に【サンプルデータを含む】と出ます）。
3. 終わったら `removeServiceMtgSampleData()` を実行します（「【サンプル】」の付いたリクエスト・タスクの行だけを消します）。サンプルの ID の番号は使い回しません。
- サンプルを入れたまま本番を作らないでください（確かめの画面にも出ます）。

### 列の保護

`protectSpecificColumnsWithLock()` を実行すると、名前が `案件_` で始まるシートの P・R・T・X・AA・AB 列が、実行した人だけ編集できるようになります。
新しい「案件_」シートを足したら、もう一度実行してください（既にある保護は作り直しません）。

## 設定を変えるとき

- **追跡範囲（`DIFF_RULES` の `ranges`）**：ボタン列を含めないでください。変えたら `setupDiffTracking()` を実行します。
- **追跡するシートを増やす**：`DIFF_RULES` にシートを足し、そのシートにも上の見出しを用意してから `setupAfterSheetChange()` を実行します（「[シートを足した・名前を変えたあと](#シートを足した名前を変えたあと)」）。シートが増えてもトリガーは3つのままです（1回の処理で読むのは、関係するシートだけ）。行のずれに気づけるよう、`得意先`・`案件名` の見出しは追跡範囲の中に置いてください。
- **行を見分ける列（`DIFF_ROW_OPTIONS.keyHeaders`）**：行のずれの検知と突き合わせに使う列の見出しです（既定は `得意先`・`案件名`）。見つからない見出しは使わず、1つも無いシートではずれの検知をしません。
- **入力項目（`CRED_OPTIONS.fields`）**：`label` が `クレデンシャル履歴_記録` の見出しになります。見出しを変えるときは、古い見出しを `renamedColumns` に書くと、次に開いたときに書き換えて使い続けます。
- **シートの名前を変える**：下の「[シート名の一覧](#シート名の一覧)」を見て、書いてある場所も同じ名前に直してください。
- **権限が変わる変更をした**（新しいサービスを使い始めたなど）：エディタで関数を一度実行して再承認し、`reinstallDiffTriggers()` を実行します。承認用のウェブアプリを用意している場合は、デプロイも新しいバージョンにします（「[承認用のウェブアプリを用意する](#承認用のウェブアプリを用意する)」）。

### 出力先・素材（スクリプトのプロパティ）

資料・ファイルを置くフォルダと、資料のもとにする素材（ひな形）は、コードを書き換えずに、スクリプトのプロパティで指定できます。プロパティがあればコードの設定より優先し、消せばコードの設定に戻ります。
値はフォルダ（素材はファイル）の URL（ドライブで開いたときのアドレス欄）か ID です。コードを貼り直しても消えません。

1. エディタの左の「プロジェクトの設定」（歯車）→ いちばん下の「スクリプト プロパティ」→「スクリプト プロパティを編集」→「スクリプト プロパティを追加」
2. 下の表のプロパティの名前と、フォルダの URL を入れて「スクリプト プロパティを保存」
3. エディタで `showOutputFolders()` を実行し、入れたプロパティの項目に「スクリプトのプロパティ「…」：設定あり（これを使用）」、
   「使っているもの：○ フォルダ（ファイル）の名前」と出ることを確かめる（読むだけ。フォルダは作らない）。
   ○ は「フォルダ（ファイル）を開ける」という意味です。プロパティを入れていない項目は「未設定 → コードの設定（…）を使用」と出て、コードの設定のフォルダが ○ になります

| プロパティの名前 | 出力先 | 無いとき（コードの設定） |
|---|---|---|
| `MTG_SAVE_FOLDER` | 事前資料などの保存先（資料を作る場所。試作・シナリオ構成別の資料・RX Service Meeting の資料もここ） | `MeetingSummary.gs` の `MTG_OPTIONS.folderId` |
| `MTG_MEETING_FOLDER_<シート名>`（例：`MTG_MEETING_FOLDER_スーパー・GMS`） | そのサブインダストリーの事前資料の格納先（この中の会議のフォルダ「yyMMdd_RX Business Meeting_第N回」に本番の PDF を格納する） | `test.gs` の `DIFF_RULES` の `meetingFolder` |
| `MTG_MEETING_FOLDER_全サブインダストリー` | 統合版の格納先 | `MTG_OPTIONS.combined.meetingFolder` |
| `MTG_COPY_FOLDER` | 時点コピー（会議時点・日次のスプレッドシートのコピー。履歴のファイル）の保存先 | `MTG_OPTIONS.copyFolderId`（空なら保存先の中の「時点コピー」） |
| `AP_DEST_FOLDER` | アカウントプランシートの保存先 | `コード.gs` の `AP_OPTIONS.destFolderId` |
| `MTG_TEMPLATE_URL`（素材） | 事前資料の表紙・扉のひな形（Google スライドか .pptx。RX Service Meeting も同じひな形の3枚目） | `MTG_OPTIONS.templateId`（空）。無ければ表紙・扉はコードで描くので、素材が無くても作れる |
| `AP_TEMPLATE_FILE`（素材） | アカウントプランシートのひな形（スプレッドシート） | `コード.gs` の `AP_OPTIONS.templateFileId` |

**事前資料の格納先をまとめて入れる**：サブインダストリーごとのフォルダ（「01.スーパー・GMS」〜「11.生協」と「00.全サブインダストリー」）を1つの親フォルダの中に作ってあれば、
エディタで `setBusinessMtgMeetingFolders()` を実行し、親フォルダの URL を貼り付けます。フォルダの名前の先頭の番号を除いた名前がシート名と同じフォルダを対応させ、
対応を確かめる画面で「はい」を押すと、`MTG_MEETING_FOLDER_<シート名>` に入れます（今の値は置き換え、対応するフォルダの無いシートは今のまま）。

全サブインダストリーで同じ格納先を使う（テストの間など）ときは、プロパティを11個入れる代わりに、`test.gs` の `DIFF_RULES` の `meetingFolder`（`TEST_MEETING_FOLDER`）に書きます
（全シート共通のプロパティ `MTG_MEETING_FOLDER` は、コードの設定と役割が重なるので置いていません。入れても使いません）。

- 値がフォルダの URL・ID として読めない、または実行するアカウントが開けないときは、どのプロパティかを書いて止めます（本番の格納は資料を保存先に残して知らせます）。
- 格納先を変えても、前の格納先に置いた資料は動きません。インデックス（`INDEX_会議資料`）を新しい格納先から書き直すときは `rebuildBusinessMtgIndex()` を実行します。
- 表紙などの素材は、上の2つのひな形だけです（画像・フォントなどのファイルは使いません。ひな形が無いときの表紙・扉の絵柄はコードで描きます）。
- チャットの webhook（`MTG_SUBCHAT_<シート名>`）もスクリプトのプロパティです（鍵を含むので `showOutputFolders()` には出しません。`setBusinessMtgSubChats()` で登録）。

### シートを足した・名前を変えたあと

追跡するシート（`DIFF_RULES`）を足した・名前を変えたあとは、管理者アカウントで `setupAfterSheetChange()`（`test.gs`）を1回実行します。次の4つを順に行います。

1. 差分追跡（`setupDiffTracking()`）：今の値を比較基準にし、トリガーを用意する
2. クレデンシャルのボタン列（`setupCredentialLauncher()`）
3. 変更履歴のボタン列（`setupChangeHistoryLauncher()`）
4. サービスリクエスト（`setupRequestSheet()`）：見出し・判断のプルダウンを整え、登録した行を `requests: true` のシートに合わせる

- 始める前に、`DIFF_RULES` のすべてのシートを確かめます（読むだけ）。シートが無い・見出しが足りない・ボタン列が追跡範囲（`ranges`）に入っているときは、
  **何も変えずに**、直す点をまとめて画面に出します。直してからもう一度実行してください。
  - 見出しの行（`headerRow`）に `最終更新日時`・`得意先` がちょうど1つずつ
  - ボタン列（`クレデンシャル`（セル内で改行）`オファリング登録`・`変更履歴`）は無くてもかまいません。あるシートにだけボタンを付けます（2つ以上あると止めます）。
    どのシートにも無ければ、ボタン列の設定は省きます
  - `requests: true` のシートは、さらに `サブインダストリー`・`案件名`・`サービスのリクエスト`
- 終わると、設定したシートと、サービスリクエストの件数（「…のリクエスト N件のうち M件を登録しています」など）を画面に出します。
- スプレッドシートの画面に出せないとき（エディタを script.google.com から直接開いた・スプレッドシートを閉じた）も止めずに設定し、
  結果は実行ログに書きます（直す点があればエラーで止まり、何も変えません。サービスリクエストの使わなくなった列は、聞けないので残します）。
- 途中で止まったときは、どこまで済んだかを出します。原因を直して、もう一度実行してください（何度実行しても、トリガーやボタンが二重になることはありません）。
- 1つ目の手順で比較基準を今の値にし直すので、実行する前の取りこぼし（まだ記録していない変更）は差分として残りません。
- 1つずつの関数（`setupDiffTracking()` など）は、これまでどおり単独でも実行できます。

### 記録のセル数を減らす（前の版の記録の移し替え）

差分の記録は、セル数の少ない形で書きます（`変更履歴_差分` は9列、`変更時点スナップショット` は8列で、行の内容を1つのセルにまとめる）。
前の版の記録（`差分`・`確認済み` の列、見出しごとの列）は、管理者が一度だけ移し替えます。

1. 「ファイル」→「コピーを作成」で、スプレッドシートの控えを取ります。
2. 編集の少ない時間に、`compactDiffRecords()` を実行します（移し替えの間は、差分の記録を待たせます）。
   - `変更履歴_差分` の `差分`・`確認済み` の列を削除します。
   - `変更時点スナップショット` の前の版の行を `行の内容` にまとめ（値は変わりません）、見出しごとの列を削除します。
   - 記録のシート・比較基準（`__CHAR_DIFF_*`）・`クレデンシャル履歴_記録` の、使っていない右の列・下の行を削除します。
3. 最後に、移し替えた行数とセル数の変化が出ます。「途中で止めました」と出たときは、もう一度実行してください（続きから行います）。
4. 変更履歴の画面・サイドバーで、前の記録がこれまでどおり出ることを確かめます。

移し替える前でも、新しい記録は新しい形で足され、前の版の記録もそのまま読めます。`diagnoseCellUsage()` で前後のセル数を比べられます。

## clasp で同期する

[clasp](https://github.com/google/clasp) を使うと、リポジトリと Apps Script エディタの中身をコマンドで同期できます。

どの方法で同期する場合も、Apps Script のファイルはリポジトリ直下に置いてください。フォルダに入れるとエディタのファイル名にフォルダ名が付き（`src/HistorySidebarView` など）、モーダル・サイドバーが「HTML ファイルは見つかりませんでした」で開けなくなります。

### 準備（最初の1回）

```bash
npm install -g @google/clasp   # または npx @google/clasp …
clasp login
cp .clasp.json.example .clasp.json
```

`.clasp.json` の `scriptId` に、Apps Script エディタの「プロジェクトの設定」→「ID」を入れます（`rootDir` は `.` のまま）。
`.claspignore` で、push するファイルを Apps Script のファイル（`.gs`・`.html`・`appsscript.json`）だけに絞っています。消さないでください（`tests/` の `.js` まで送ると、プロジェクト全体が動かなくなります）。
`npx clasp status` で、push されるファイルの一覧を確かめられます。

### 変更を反映する手順

**`clasp push` はエディタ側の中身をリポジトリの内容で置き換え、リポジトリに無いファイルはエディタから消します。** 必ず次の順で行ってください。

1. `npx clasp pull` でエディタの最新を取り込む
2. `git status`・`git diff` で、エディタ側だけで変わっていた所が無いか確かめる（あればコミットしておく）
3. 変更を入れ、`npm run check` と `npm test` を通す
4. `npx clasp push` で反映する
5. 必要なら、上の「設定を変えるとき」の関数（`setupDiffTracking()` など）を実行する

ファイル名は、エディタ側の名前に合わせています（`test.gs`・`Changehistory.gs` など）。
名前を変えると、`clasp pull` で古い名前のファイルも戻ってきて、同じ関数が2つになります。変えるときはエディタ側でも同じ名前に変えてください。

## エディタに貼り付ける

clasp を使わない場合は、変更したファイルの中身をエディタの同じ名前のファイルに貼り付けて保存します。

- ファイルを新しく作るときは、`.gs` は「スクリプト」、`.html` は「HTML」で、拡張子を除いた同じ名前にします。
- `.gs` と `.html` に同じ名前は付けられません。
- 古い版のファイルを残したまま新しいファイルを足すと、同じ名前の関数・定数が2つになって動かなくなります。

## トラブル対応

### 確かめるための関数

- `diagnoseDiffTriggers()`：トリガーの一覧と、差分追跡の3つがそろっているか
- `diagnoseDiffState()`：セル数と上限、追跡シートごとの状態（停止していないか、シート名・`DIFF_RULES`・最終更新日時の列・行数・列数が保存時と同じか、比較用シートがあるか、取りこぼし・行の確かめが残っていないか）と、最後に次にすること
- `diagnoseCellUsage()`：シートごとのセル数（空のセルも含む）を多い順に。スプレッドシートは1ファイル1,000万セルまで（結果は画面にも出ます）
- `diagnoseServiceLock()`：選択パネルの「追加」が「他の処理が実行中です」で止まるときに。サービス管理のロックが新しい版（差分追跡と別）か、今サービス管理・差分追跡のロックが使われているか（使っている処理も）を出します（読むだけ）
- `diagnoseTaskChoices()`：サービス案タスク管理の「サービス案」の候補（ID とリクエスト）が更新されないときに。動いているコードの版（前の版の関数が残っていないか）・候補にするリクエストの数・候補のシート（`__TASK_CHOICES`）が今のリクエストと合っているか・プルダウンの参照先（先頭・真ん中・最後の行）・最後に候補を合わせた時刻・シートの保護を出します（読むだけ。直すときは `setupTaskSheet()`）
- `setBusinessMtgBaseline()`：旧フォーマットからの移行など、案件をまとめて貼り付けたあとに。今を会議サマリの基準として記録し、次の資料で貼り付けた案件を「新規」に数えないようにします（今の値を「時点コピー_…（基準）」に保存し、次の資料はそれと比べます）
- `addDealRows()`：追跡シートに案件の行を足すときに（数式・プルダウンの範囲の中に足すので、No.・期待値の計算とプルダウンが足した行にも届く。変更履歴には記録しない）
- `migrateLegacyDeals()`：旧フォーマットのスプレッドシート（「案件_{サブインダストリー名}」シート）から、案件を同じ名前のシートに転記するときに（上書き。URL を入力する）
- `rebuildBusinessMtgIndex()`：会議資料のインデックス（`INDEX_会議資料`）を、会議のフォルダにある本番の PDF から書き直すときに（前の形式（行＝サブインダストリー）からの切り替えも）
- `createBusinessMtgCombinedSummary()`：統合版（全サブインダストリー）を作るときに（すべてのサブインダストリーの資料を作ったあと・個別の資料を作り直したあと）。画面で会議日程を選びます
- `createBusinessMtgScenarioSummary()`：RXシナリオ構成別の期待値の資料（試作。按分・関与・組み合わせ）を作るときに。シートを選びます（会議日・インデックスは変えません）
- `installDailySheetCopy()`・`saveDailySheetCopy()`・`uninstallDailySheetCopy()`：日次の時点コピーを始める・今すぐ1つ保存する・やめるときに（上の「日次の時点コピー」）
- `importMeetingSchedules()`：Google カレンダーから RX Business Meeting・RX Service Meeting の日程を読み、`INDEX_会議資料` に会議日と会議名の行を足すときに（資料を作る画面の会議日程の一覧になります。予定の名前の言葉は `MSCH_OPTIONS.titles`）
- `showBusinessMtgSummariesResult()`：会議サマリを区切って自動で続けたときの結果（途中なら進み具合）を見るときに
- `storeBusinessMtgSummaries()`：本番の資料を作ったときに会議のフォルダに格納できなかったとき、フォルダを用意してから。シートと会議日を入力すると、保存先の PDF を会議のフォルダに格納します
- `setBusinessMtgMeetingFolders()`：事前資料の格納先を、親フォルダの中のサブインダストリーごとのフォルダから、スクリプトのプロパティにまとめて入れるときに（親フォルダの URL を入力する）
- `showOutputFolders()`：資料・ファイルの出力先（保存先・事前資料の格納先・時点コピー・アカウントプランシート）と素材（ひな形）について、使っている設定（スクリプトのプロパティかコードか）と開けるかを確かめるときに（読むだけ。上の「出力先・素材（スクリプトのプロパティ）」）
- `setMeetingTemplate()`：会議サマリの表紙・扉のひな形（Google スライドか .pptx）の URL を、スクリプトのプロパティ `MTG_TEMPLATE_URL` に入れる・外すときに（空欄なら外す。プロジェクトの設定で直接入れてもよい）
- `previewBusinessMtgSummaries()`：会議サマリの形・中身を確かめるときに。スライドと PDF を作りますが、会議日は記録しません（同じ会議日の本番で、試作から解消した入力内容の確認事項の数を出します）
- `setBusinessMtgSubChats()`：サブインダストリーごとの Google チャットのスペースの webhook を登録する・変える・外すときに（「削除」で外す）
- `remindBusinessMtgUpdate()`：管理フォーマットの更新のお願いを、サブインダストリーごとのスペースに送るときに（会議日・締め切り・今の入力状況・シートのリンク）
- `notifySubBusinessMtgSummaries()`：その会議日の本番の事前資料のリンクを、サブインダストリーごとのスペースに送るときに
- `removeBusinessMtgRecord()`：会議サマリの会議日の記録を取り消すときに（会議日を打ち間違えた・会議が無くなった）。シートと会議日を入力し、「はい」で取り消します（基準の記録・資料のファイルは残す）
- `addBusinessMtgDummyHistory()`：会議サマリの資料の形を確かめるために、シートの案件にダミーの変更の記録を足すときに（シートの値は変わらない。上の「会議サマリの確認用のダミーデータ」）
- `removeBusinessMtgDummyHistory()`：ダミーの変更の記録（「DMY-」）を消すときに。配る資料を作る前に実行します
- `diagnoseRequestSources()`：サービスリクエストの選択パネルにリクエストが出ないときに。シートごとに、読む対象か（`requests: true`）・見出しがあるか・リクエストのある行の数と、パネルに出ないもの（登録済み・ほかと同じリクエスト）の数。「サービスのリクエスト」が何列にあるかも出し、どのシートにもリクエストが無ければそう書きます（列を足して位置が変わっても、見出しで探すので読めます）。前の版の `__REQUEST_LISTS` が残っていれば、`setupRequestSheet()` を案内します（結果は画面にも出ます。エディタをスプレッドシートから開いていないときは実行ログだけ。`diagnoseServiceLock()`・`diagnoseTaskChoices()` も同じ）

結果は実行ログに出ます。

### よくあるメッセージ

| メッセージ・症状 | 原因と対処 |
|---|---|
| 「「…」の変更履歴の記録を一時的に止めました。5分ほどで自動で再開します（…）」 | 比較基準が使えなかった（比較用シートが消された・構成が違う）。何もしなくてよい（5分ごとの取りこぼし回収が自動で再開する）。非表示の `__CHAR_DIFF_*`・`__TASK_CHOICES` は消さない |
| 実行ログに「「…」の差分追跡は止まっています（理由：…）」（前の版はエラーで `Tracking is not initialized or is paused`） | そのシートが止まっている間の編集。エラーにはならず、立て直したあとに記録する。5分たっても続くときは `diagnoseDiffState()` で「自動の立て直しに失敗」の理由を見て直す（すぐに直すときは `setupDiffTracking()`） |
| `diagnoseDiffState()` に「自動の立て直しに失敗」 | 止まったシートを取りこぼし回収が立て直せなかった（見出しの「最終更新日時」が無い・結合セルなど。理由が出る）。直すと、30分以内に自動で再開する |
| 「差分追跡の設定が「…」の途中で止まりました：…」 | `setupDiffTracking()` の途中のエラー（コロンの後ろが原因）。すべての追跡シートの記録が止まっているので、原因を直して（一時的なエラーならそのまま）もう一度実行する |
| 「比較用シートを作ると、スプレッドシートのセル数が上限（1,000万）を超えます」 | `diagnoseCellUsage()` で多いシートを確かめ、使っていないシート・行・列を削除してから `setupDiffTracking()` を実行する（このときは何も止めていない） |
| 「…の列が変わったので、変更履歴の比較基準を取り直しました」（前の版は「…の列構成が変わったため差分追跡を停止しました」） | 列の追加・削除。何もしなくてよい（記録は続く）。追跡範囲（`DIFF_RULES` の `ranges`）が合っているかは確かめる |
| `Exactly one timestamp header is required` | 見出し行に `最終更新日時` が無い、または2つ以上ある |
| 「…の追跡範囲（…）に結合したセルがあります」（前の版は `Merged cells are not supported`） | 追跡範囲に結合セルがある。結合を解除する |
| `Edit exceeds 2000 tracked cells.`（前の版） | 一度に2,000セルを超える貼り付け。今の版は止めずに、5分ごとの取りこぼし回収で記録する（編集者は「不明（取りこぼし回収）」） |
| `Log sheet has unexpected headers` | `変更履歴_差分` の1行目が変わっている。バックアップを取り、見出しを元に戻す |
| 「…が DIFF_RULES の ranges に含まれています」 | ボタン列が追跡範囲に入っている。範囲から外して `setupDiffTracking()` を実行し、もう一度ボタン列を設定する |
| 「他の処理が実行中です。少し待ってからもう一度お試しください。」 | ほかの書き込みと重なった。少し待って保存し直す |
| 「この履歴は他の人が先に変更しています」「…得意先が変わっています」 | 開いたあとに、ほかの人の編集や並べ替えがあった。モーダルを閉じて開き直す |
| 開いたときに履歴サイドバーが出ない | 自動表示はやめました。メニュー「🟩RXビジネスMTG用」→「履歴サイドバーを開く」で開く |
| 「このシートでは開けません。…のシートで開いてください。」 | 追跡していないシートを開いている。出ているシート（スーパー・GMS など）に切り替えてから、もう一度メニューを押す |
| サイドバー・パネルに「権限の承認が必要です」と出る・モーダルが読み込めない | まだ承認していない（足りない権限がある）。サイドバー・パネルの「承認する」か、メニュー「🟩RXビジネスMTG用」→「権限を承認する（初回のみ）」（パネルはメニュー「🟪RXサービスMTG用」→「リクエストを追加」でもよい）で承認する |
| 「承認する」ボタンが出ない（メニューで承認する案内の文だけ） | 承認の画面の URL が取れなかった。案内のとおりメニューから承認する。ボタンを出したいときは承認用のウェブアプリを用意し、`HS_OPTIONS.authorizeUrl` に `…/exec` で終わる URL を入れる |
| パネルに「読み込めません」と複数のアカウントの案内が出る | 承認は済んでいるが、別のアカウントとして動いている。1つのアカウントだけでログインした状態か、シークレットウィンドウで開く |
| ほかの人がパネルから追加・削除できない（保護の知らせが出る） | `サービスリクエスト`・`サービス案タスク管理`・`__TASK_CHOICES` のシートが保護されている。保護を外すか、使う人を編集できる人に入れる |
| 「承認する」で開いたタブに「一部の権限が承認されていません」 | 承認画面で外したチェックがある。そのページの「もう一度承認する」で、すべてにチェックを入れて承認する |
| 「承認する」で承認したのに、サイドバーが読み込めないまま | ウェブアプリのデプロイが古い版で、権限が足りていない。デプロイを新しいバージョンにする。急ぐときはメニューから承認する |
| 承認したのに「権限の承認が必要です」と出る | ブラウザで複数の Google アカウントにログインしていると、別のアカウントとして動くことがある。シークレットウィンドウか、1つのアカウントだけでログインした状態で開く |
| ボタンを押してもモーダルが開かない | 全員で開かないときは `diagnoseDiffTriggers()` で `onCredentialLauncherEdit` があるか確かめ、無ければボタン列の設定を実行する |

### 古い版から上げるとき

**オポチュニティキャンバスをやめた（2026/10/26）**：Apps Script のエディタで `OpportunityCanvas.gs` と `OpportunityCanvasDialog`（HTML）を削除し、
`HistorySidebarView.html` を貼り付けてください（サイドバーの「キャンバス」ボタンが無くなります）。`clasp push` で反映するときは、この2つは自動で消えます。

**会議時点のコピーを「時点コピー」にした（2026/10/17）**：`MeetingSummary.gs`・`MeetingSchedule.gs`・`MeetingRunDialog.html` を貼り付けてください。
新しく保存するコピーの名前は「時点コピー_日時（資料作成時・会議日 …）」になり、中身は追跡シートの値だけではなくスプレッドシート全体のコピーになります。前の名前のコピー・フォルダはそのまま使えます（名前を変えなくてかまいません）。
毎日のコピーも比べる時点に使うときは、`installDailySheetCopy()` を実行します。

**会議資料の作り方を画面にした（2026/10/17）**：資料を作る関数（`createBusinessMtgSummaries()`・`previewBusinessMtgSummaries()`・`createBusinessMtgCombinedSummary()`・
`createServiceMtgSummaries()`・`previewServiceMtgSummaries()`）は、番号・会議日を入力する代わりに画面（`MeetingRunDialog`）を開き、会議日程をプルダウンで選ぶようになりました。
`MeetingSchedule.gs`・`MeetingRunDialog.html`（HTML）を新しく作り、`MeetingSummary.gs`・`ServiceMeeting.gs` を貼り付けてください。
最初に `importMeetingSchedules()` を実行して、カレンダーの会議の日程を `INDEX_会議資料` に読み込みます（カレンダーの権限を承認したら `reinstallDiffTriggers()`）。
`INDEX_会議資料` の見出し「種別」は、次に書くときに「会議名」に書き換わります。

**会議の名前を「MTG」から「Meeting」に改めた（2026/10/17）**：会議の名前を RX Business Meeting・RX Service Meeting にしました（表紙・出典の行・会議のフォルダの名前・
インデックスの会議名・チャットの文に出ます）。前の名前のフォルダ（`261023_RX Business MTG_第5回` など）は同じ会議のフォルダとしてそのまま使い、第N回も続きから数えます
（`MTG_OPTIONS.formerMeetingNames`・`SMTG_OPTIONS.formerMeetingNames`）。インデックスの会議名が前の名前（RX Business MTG）の行は、次にその行に書くときに今の名前に書き換えます
（`index.formerKinds`）。フォルダの名前は自動では変えないので、そろえたいときはドライブで直してください。

**会議サマリの関数名を改めた（2026/10/17）**：RX Service Meeting の資料と見分けられるよう、RX Business Meeting の会議サマリの関数名に `BusinessMtg` を入れました。
設定・記録（スクリプト・ドキュメントのプロパティ）はそのまま使えます。`MeetingSummary.gs`・`サンプルデータ.gs` を貼り付けたあとは、新しい名前で実行してください。

| 前の名前 | 今の名前 |
|---|---|
| `createMeetingSummaries()`・`previewMeetingSummaries()` | `createBusinessMtgSummaries()`・`previewBusinessMtgSummaries()` |
| `createCombinedMeetingSummary()` | `createBusinessMtgCombinedSummary()` |
| `storeMeetingSummaries()`・`rebuildMeetingIndex()` | `storeBusinessMtgSummaries()`・`rebuildBusinessMtgIndex()` |
| `setMeetingBaseline()`・`removeMeetingRecord()` | `setBusinessMtgBaseline()`・`removeBusinessMtgRecord()` |
| `showMeetingSummariesResult()`・`continueMeetingSummaries()`（トリガー） | `showBusinessMtgSummariesResult()`・`continueBusinessMtgSummaries()` |

| `addMeetingDummyHistory()`・`removeMeetingDummyHistory()` | `addBusinessMtgDummyHistory()`・`removeBusinessMtgDummyHistory()` |

`setMeetingTemplate()`（表紙・扉のひな形）は RX Business Meeting と RX Service Meeting で共通なので、名前は変えていません。
会議サマリを区切って自動で続けている途中（`showBusinessMtgSummariesResult()` で「作っている途中」と出るとき）は、終わってから貼り付けてください
（前の名前の続きのトリガーは、貼り付けたあとは動きません。動かなかったときは、作り直すと外れます）。

差分ログの列構成が古い版（編集者メールアドレスの列が無い）のときは、`upgradeDiffTrackingV3()` を1回実行します。比較基準はそのままで、列だけを足します。
`DIFF_RULES` も変えた場合は、代わりに `setupDiffTracking()` を実行してください。
